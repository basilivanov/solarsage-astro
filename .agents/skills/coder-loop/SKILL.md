# Цикл «архитектор/ревьюер → кодер в tmux astro2»

Моя роль в этом режиме — архитектор и ревьюер. Код пишет кодер: **Gemini 3.6 Flash в opencode**, запущен в tmux-сессии **`astro2`** (окно `opencode`, cwd `/opt/solarsage-astro`). tmux-сервер работает от root, поэтому все команды tmux — через `sudo`.

## Декомпозиция задачи — обязательна

Кодерская модель ограниченно удерживает широкий контекст. Никогда не передавать
ей большое end-to-end ТЗ целиком как одну задачу.

- Одна coder-итерация — одна локальная цель или один подсистемный срез, обычно
  1–3 основных файла плюс их узкие тесты.
- У каждого среза свои критерии приёмки и одна targeted-команда проверки.
- Каждый срез сначала должен быть закончен и отревьюен; только после этого
  выдаётся следующий.
- В coder prompt передавать контекст только текущего среза. Master-ТЗ остаётся у
  архитектора и не заменяет локальное ТЗ кодеру.
- Не объединять в одной итерации registry, logger API, transport, массовую
  миграцию callsites и весь набор тестов.
- Соседние проблемы кодер сообщает в отчёте, но не поглощает в текущий scope.
- Для большой задачи завести master-план и нумерованные локальные ТЗ, например
  `01_..._TZ.md`, `02_..._TZ.md`; кодеру отправлять только очередной файл.
- Исключение допустимо лишь для действительно атомарного изменения, которое
  нельзя проверить или принять по частям.

Шаблон маленького среза:

```text
Цель: один наблюдаемый результат.
Разрешённые файлы: точный список.
Не трогать: соседние подсистемы и unrelated changes.
Критерии: 2–5 проверяемых пунктов.
Проверка: одна targeted-команда.
Ничего не коммить и не пушить — коммит делает ревьюер.
```

## Постановка задачи кодеру

Один из двух способов (по размеру задачи):

1. **ТЗ в `docs/work/`** — для нетривиальных задач. Пишу файл `YYYY-MM-DD_<slug>_TZ.md` с контекстом, файлами, критериями приёмки и явным запретом коммитить. В tmux отправляю короткое сообщение со ссылкой на ТЗ.
2. **Прямое сообщение в tmux** — для мелких задач:

```bash
sudo tmux send-keys -t astro2 "<текст задачи>"
sudo tmux send-keys -t astro2 Enter
```

В тексте задачи всегда указывать: что сделать, какие файлы трогать/не трогать, критерий готовности и «**ничего не коммить — коммит делает ревьюер**».

После отправки проверить `sudo tmux capture-pane -t astro2 -p | tail -15`, что сообщение ушло и работа началась.

## Ожидание и мониторинг

- Жду **180 секунд** (`sleep 180`), затем смотрю `sudo tmux capture-pane -t astro2 -p | tail -40`.
- Если работа ещё идёт — жду повторными циклами, не дёргаю кодера.
- НЕ запускать `sleep 180` в foreground без необходимости на глазах у пользователя без предупреждения — предупредить одной строкой.

## Разбор зависаний

Если кодер остановился или завис в тулколе:

1. Послать слово `продолжай` (send-keys + Enter).
2. Если не помогло — дважды Escape:
   ```bash
   sudo tmux send-keys -t astro2 Escape
   sudo tmux send-keys -t astro2 Escape
   ```
   затем снова `продолжай`.

## Постановка ТЗ кодеру по GRACE canon §10.7

Локальное ТЗ (файл `NN_..._TZ.md` или прямое сообщение в tmux) обязано покрывать 11 элементов canonical controller packet; пропуск элемента = неполный packet:

1. **packet title** — имя среза;
2. **Phase / Wave** — волна/проект (например `W-NAMED-PROMO-CAMPAIGN`);
3. **Modules** — затронутые module IDs (`M-...`);
4. **goal** — один ограниченный наблюдаемый результат;
5. **exact write scope** — точный список разрешённых файлов;
6. **frozen / out-of-scope** — явно запрещённые соседние поверхности;
7. **must-preserve invariants** — что нельзя сломать (контракты, API, поведение соседей, принятые assertions);
8. **verification commands** — одна targeted-команда проверки;
9. **expected evidence** — что приложить в отчёт (файлы, вывод проверки);
10. **escalation rule** — «нужен соседний scope → стоп, доложить, новый packet»;
11. **no-commit rule** — «ничего не коммить и не пушить — коммит делает ревьюер».

Ревьюер считает packet неполным и возвращает доразмещение, если отсутствуют `Frozen / Out Of Scope`, `Must Preserve`, `Verification` или `Escalation`. Для мелких задач в прямом сообщении допустимо сжатие, но элементы 5–8 и 11 обязательны всегда.

## Ревью и приёмка

Когда кодер закончил:

1. `git status --short` и `git diff` — смотрю полный диф. Проверяю, что нет чужих/рантайм-файлов (`.grace/`, `grace.db`, `skills/`, `.profile.lock` и т.п.).
2. Сверяю с критериями приёмки из задачи.
3. Нужные корректировки делаю **сам** (мелкие правки быстрее, чем новый круг делегации), либо отправляю доработку кодеру с конкретным списком замечаний.
4. Прогоняю релевантные проверки: `npx vitest run` (unit), `cd apps/api && source .venv/bin/activate && python -m pytest tests/ -q` (backend) — по затронутому контуру.

## Коммит и пуш

Пользователь в этом режиме **явно делегировал коммит и пуш** после принятия работы — подтверждение каждый раз спрашивать не нужно. Правила:

- Коммичу только файлы задачи, не `git add -A` вслепую.
- Conventional Commits по стилю репозитория (`fix(scope): ...`, `feat(scope): ...`, смотреть `git log --oneline`).
- Пуш в `main` (`git push origin main`), если пользователь не сказал иное.

## Отчёт пользователю

Коротко: что сделал кодер, что поправил сам на ревью, результат проверок, SHA коммита, статус пуша.

## Prod-error фиксы от авто-runner'а

PR'ы с label `prod-fix` приходят от авто-runner'а (`scripts/prod-errors/fix_runner.py`, headless opencode в git worktree), а не от tmux-кодера. К ним применимы те же правила срезов: ревью полного diff, проверка, что затронуты только разрешённые файлы и нет ослабления тестов, прогон релевантных проверок перед мержем. Мерж и деплой — ручной батч владельца; после деплоя `python3 scripts/prod-errors/resolve_after_deploy.py <sha>`.
