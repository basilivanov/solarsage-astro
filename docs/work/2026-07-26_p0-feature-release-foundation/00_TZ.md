# ТЗ: P0 foundation для безопасного и быстрого тестового rollout новых фич

- Дата: 2026-07-26
- Статус: pre-implementation contract
- Audit baseline HEAD на момент финальной сверки: `afedf25`
- Приоритет: P0, выполнить до следующей новой продуктовой фичи после synastry
- Роль исполнителя: кодер
- Роль владельца rollout: архитектор/владелец продукта

## 0. Authority и назначение документа

Это ТЗ определяет короткий foundation, после которого новые фичи можно
включать по схеме `off -> allowlist -> on` без отдельной frontend-сборки,
нового image и ручного обхода канонического deploy path.

Документ не заменяет:

- `AGENTS.md` — runtime/deploy/security canon;
- `docs/PRODUCTION_RUNBOOK.md` — production operations;
- `grace/verification-matrix.md` — общие slice/UC gates;
- текущие synastry-ТЗ и незавершённую реализацию synastry.

При конфликте в пределах этого P0 действует следующий порядок:

```text
AGENTS.md / production invariants
  > публичные API/DB contracts
  > это ТЗ
  > исторические work-документы и старые rollout-инструкции
```

P0 должен быть реализован несколькими небольшими PR/коммитами по срезам из
раздела 11. Один giant diff запрещён.

## 1. Почему P0 нужен сейчас

### 1.1. Новые фичи уже не изолированы от общих проблем

Synastry уже имеет route, API, credits, generation pipeline и UI. Следующие
фичи будут повторять одни и те же инфраструктурные решения: auth bootstrap,
feature availability, locked state, rollout и rollback. Без общего минимального
контракта каждая новая фича добавит ещё один несвязанный env flag, hook и набор
скрытых production routes.

## 4. Непереговорные инварианты

1. UI никогда не является authorization boundary.
2. `off` и `allowlist` должны применяться на каждом прямом feature API route.
3. Rollout state меняется без нового image и без restart API/frontend.
4. Missing feature row означает `off` — fail closed.
5. Feature allowlist хранит внутренний `users.id`, не raw Telegram ID.
6. Raw Telegram ID допустим только как operator CLI input; он не хранится в
   rollout tables, не выводится обратно и не попадает в structured logs.
7. Удаление пользователя каскадно удаляет его allowlist membership.
8. Выключение feature не удаляет reports, credits или другие product data.
9. Предыдущий image обязан безопасно игнорировать новые rollout tables.
10. Fixture shell не монтирует auth/session provider и не делает product API
    запросов.
11. `SOLARSAGE_V2_FRONTEND_ENABLED` не выбирает payload и должен исчезнуть.
12. V2 rollback — только previous immutable image, не flag fallback на V1.
13. Боевые `prod-orchestrator.sh`, `prod-smoke.sh` и canonical Compose остаются.
14. Никаких `any`, `@ts-ignore`, нового `ignoreBuildErrors` или ослабления Zod/
    Pydantic contract ради зелёного build.
15. Новые/существенно изменённые файлы соблюдают GRACE canon и правдивый
    `owned_tests`.

## 5. Целевая архитектура P0

```text
TelegramProvider
  -> AuthSessionProvider (ровно один auth machine)
       -> Grace authenticated shell
            -> feature page
                 -> GET /api/<feature>/capabilities
                      -> FeatureRolloutService
                           -> feature_rollouts
                           -> feature_rollout_users
                 -> остальные /api/<feature>/*
                      -> require_feature_access
                           -> тот же FeatureRolloutService

Operator CLI (внутри active api container)
  -> set-mode / allow-user / remove-user / status
  -> DB commit
  -> следующий request видит новое состояние без deploy/restart
```

Rollout registry является инфраструктурным механизмом доступности, но не
заменяет entitlement/credits. Feature endpoint обязан пройти обе проверки:

```text
rollout enabled for user
AND
existing product entitlement/quota/business invariant
```

## 7. P0-B: backend-owned feature rollout registry

### 7.1. DB schema

Добавить следующую Alembic revision после фактического migration head на момент
реализации. Если head всё ещё `0025_synastry_schema`, рекомендуемое имя:

```text
0026_feature_rollout
```

Таблица `feature_rollouts`:

| Column | Contract |
|---|---|
| `feature_key` | `varchar(64)` PK, lowercase `[a-z][a-z0-9_]{0,63}` |
| `mode` | `varchar(16)` NOT NULL, CHECK `off|allowlist|on` |
| `created_at` | timezone-aware timestamp NOT NULL |
| `updated_at` | timezone-aware timestamp NOT NULL |

Таблица `feature_rollout_users`:

| Column | Contract |
|---|---|
| `id` | UUID PK |
| `feature_key` | FK `feature_rollouts.feature_key`, `ON DELETE CASCADE` |
| `user_id` | FK `users.id`, `ON DELETE CASCADE` |
| `created_at` | timezone-aware timestamp NOT NULL |

Constraints:

- UNIQUE `(feature_key, user_id)`;
- индекс `(user_id, feature_key)` для request check;
- migration не seed-ит runtime rows; service трактует отсутствие строки как
  `off`, а первая `set-mode` операция делает idempotent upsert;
- скрытых `on` defaults запрещены;
- downgrade удаляет только новые таблицы, но production rollback не запускает
  downgrade автоматически.

Новые модели допустимо временно добавить в `apps/api/app/db/models.py`, потому
что текущий Alembic registry построен вокруг него. Расширять этот P0 до полного
split моделей запрещено; будущий models refactor должен перенести их механически.

### 7.2. Domain contract

Создать `apps/api/app/services/feature_rollout_service.py`.

Публичные сущности:

```python
FeatureRolloutMode = Literal["off", "allowlist", "on"]
FeatureAccessReason = Literal[
    "enabled_globally",
    "allowlisted",
    "feature_off",
    "not_allowlisted",
]

@dataclass(frozen=True)
class FeatureAccessDecision:
    enabled: bool
    reason: FeatureAccessReason

class FeatureRolloutService:
    async def decide(self, feature_key: str, user_id: UUID) -> FeatureAccessDecision: ...
    async def set_mode(self, feature_key: str, mode: FeatureRolloutMode) -> ...
    async def allow_user(self, feature_key: str, user_id: UUID) -> ...
    async def remove_user(self, feature_key: str, user_id: UUID) -> ...
    async def status(self, feature_key: str) -> ...
```

Допустимы иные имена private helpers. Поведение обязательно:

- unknown `feature_key` отклоняется closed registry, а не создаётся из typo;
- P0 registry содержит только `synastry`;
- missing row -> `feature_off`;
- `off` -> deny всем;
- `allowlist` -> allow только по UNIQUE membership;
- `on` -> allow всем authenticated users;
- allow/remove idempotent;
- `status` для отсутствующей строки возвращает effective mode `off`,
  `allowlistedUserCount=0`, `updatedAt=null` и не создаёт запись;
- `allow-user` до первой явной `set-mode` операции завершается non-zero и не
  создаёт rollout row; скрытая инициализация режима через membership запрещена;
- mode change и membership mutation имеют один transaction owner и один commit;
- request check не делает commit;
- P0 не добавляет in-memory cache: DB change виден следующему request;
- exceptions не содержат raw Telegram/user ID.

### 7.3. Operator CLI

Создать `apps/api/app/cli/feature_rollout.py` по pattern существующего promo CLI.

Команды:

```text
python -m app.cli.feature_rollout status --feature synastry
python -m app.cli.feature_rollout set-mode --feature synastry --mode off|allowlist|on
python -m app.cli.feature_rollout allow-user --feature synastry --telegram-user-id <id>
python -m app.cli.feature_rollout remove-user --feature synastry --telegram-user-id <id>
```

CLI requirements:

- `allow-user/remove-user` разрешают Telegram ID в `users`, но rollout table
  хранит только `users.id`;
- unknown Telegram user -> non-zero, без создания fake user;
- stdout JSON не возвращает Telegram ID, internal UUID или список allowlist;
- `status` возвращает только `feature`, `mode`, `allowlistedUserCount`,
  `updatedAt`;
- stderr не содержит input ID;
- structured event `feature.rollout_changed` содержит только feature,
  operation, resulting mode и affected count;
- event сначала добавить в `grace/canon/observability.xml` §8.5, затем
  синхронно перегенерировать `apps/api/app/core/logging_events.py` и
  `lib/log/events.gen.ts`; проверка —
  `python3 scripts/check_logging_guardrails.py`;
- CLI не имеет delete-feature и bulk-import в P0.

Production invocation — только внутри active `solarsage-api` container по
отдельному `docs/FEATURE_ROLLOUT_RUNBOOK.md`, тем же санкционированным паттерном,
что promo CLI:

```bash
docker exec -i solarsage-api python -m app.cli.feature_rollout \
  status --feature synastry
```

Это фиксированный operator command, а не альтернативный deploy path. Не
создавать shell wrapper, systemd unit или orchestrator subcommand.

### 7.4. API enforcement: synastry — первый consumer

`GET /api/synastry/capabilities` остаётся доступным любому authenticated user и
возвращает новый closed enum:

```python
rollout_state: Literal["enabled", "disabled", "not_allowlisted"]
```

Mapping:

| Domain decision | API `rolloutState` |
|---|---|
| `enabled_globally`, `allowlisted` | `enabled` |
| `feature_off` | `disabled` |
| `not_allowlisted` | `not_allowlisted` |

При disabled/non-allowlisted:

- `canCalculate=false`;
- `hasUnlockedAccess=false`, `activePartnerCount=0`, `creditBalance=0`;
- `maxPartners` сохраняет публичный статический limit;
- capability response не читает partner/report bodies;
- response не раскрывает allowlist или чужие identifiers.

Все остальные synastry routes должны зависеть от одного shared enforcement
dependency и при deny отвечать:

```json
{
  "detail": {
    "code": "FEATURE_UNAVAILABLE",
    "reason": "disabled|not_allowlisted"
  }
}
```

HTTP status: `403`. Это относится к:

- `/api/synastry/quota`;
- `/api/synastry`;
- `/api/synastry/partners`;
- `/{partner_id}` и status;
- aspect drilldown;
- feedback;
- delete.

Enforcement выполняется до spend, report creation, sidecar/LLM call и mutations.
Existing ownership, quota, idempotency и refund contracts остаются вторым слоем
проверок после rollout.

### 7.5. Frontend enforcement/presentation

`SynastryScreen` сначала вызывает capabilities:

- `enabled` -> только тогда загружает partners;
- `disabled|not_allowlisted` -> `data-testid="synastry-screen"`,
  `data-state="locked"`, стабильная locked card без Add CTA;
- capability transport error -> `data-state="error"`, не fail-open;
- loading -> `data-state="loading"`, `role="status"`/`aria-busy`;
- direct 403 из любого action маппится в locked state, а не generic alert.

Readings catalog:

- не показывает synastry в `available` до capability `enabled`;
- при disabled/not_allowlisted перемещает synastry в `coming` и открывает
  существующий `InDevOverlay`, не навигируя на `/synastry`;
- failure capability check не делает synastry доступной;
- остальные Natal/Horary/Election cards не ждут synastry transport бесконечно.

Pydantic остаётся source of truth; после schema change выполнить contract
generation. Generated TS/Zod руками не менять.

### 7.6. Acceptance P0-B

- missing row -> synastry locked;
- `off` -> два разных пользователя locked;
- `allowlist` -> allowlisted пользователь enabled, контрольный пользователь
  locked;
- `on` -> оба enabled;
- direct POST неallowlisted пользователя -> 403 и ноль spend/report rows;
- mode switch виден следующим request без restart/deploy;
- remove-user немедленно закрывает feature, но не удаляет его reports;
- повторный allow/remove idempotent;
- CLI/status/logs не раскрывают IDs;
- frontend не вызывает partners API в locked state.

## 14. Rollout procedure

### 14.1. Dev host

1. Deploy code/migration по каноническому dev-host process из `AGENTS.md`.
2. Убедиться, что initial `synastry` state = `off`:

   ```bash
   cd /opt/solarsage-astro/apps/api
   .venv/bin/python -m app.cli.feature_rollout status --feature synastry
   ```

3. Через CLI установить `allowlist`:

   ```bash
   cd /opt/solarsage-astro/apps/api
   .venv/bin/python -m app.cli.feature_rollout \
     set-mode --feature synastry --mode allowlist
   ```

4. Добавить тестового Telegram user:

   ```bash
   cd /opt/solarsage-astro/apps/api
   .venv/bin/python -m app.cli.feature_rollout \
     allow-user --feature synastry --telegram-user-id <id>
   ```

5. Перезагрузить страницу без restart API/frontend: capability должен стать
   `enabled`.
6. Проверить control Telegram user.
7. После acceptance вернуть `off` либо оставить `allowlist` по решению owner.

### 14.2. Production

До deploy обязательны:

- backup/migration marker по orchestrator contract;
- active и recorded previous SHA известны;
- previous SHA V2-capable и проходит full V2 smoke;
- подтверждено, что rollback image не содержит неожиданно открытый unguarded
  synastry API. Если содержит — rollout BLOCK до owner mitigation.

Порядок:

1. Migrate target SHA.
2. Deploy target SHA с rollout default `off`.
3. Full smoke, включая V2 identity и отсутствие chat/dev routes.
4. Проверить fail-closed state:

   ```bash
   docker exec -i solarsage-api python -m app.cli.feature_rollout \
     status --feature synastry
   ```

   Ожидаемый mode: `off`.

5. Перевести feature в allowlist mode:

   ```bash
   docker exec -i solarsage-api python -m app.cli.feature_rollout \
     set-mode --feature synastry --mode allowlist
   ```

6. Добавить только утверждённых canary users:

   ```bash
   docker exec -i solarsage-api python -m app.cli.feature_rollout \
     allow-user --feature synastry --telegram-user-id <id>
   ```

7. Real synastry E2E и Bugsink/log review.
8. Расширение allowlist — отдельное owner решение.
9. `on` — только после продуктовой acceptance:

   ```bash
   docker exec -i solarsage-api python -m app.cli.feature_rollout \
     set-mode --feature synastry --mode on
   ```

### 14.3. Feature kill switch

Первый rollback feature-инцидента:

```bash
docker exec -i solarsage-api python -m app.cli.feature_rollout \
  set-mode --feature synastry --mode off
```

Это не требует image rollback и не удаляет данные.

Image rollback выполняется только при code/runtime regression после feature off.
Никаких DB downgrade во время обычного rollback.

## 15. Technical pre-mortem gates

### Gate 1 — current production уже имеет unguarded synastry

Симптом: rollback на recorded previous image снова открывает feature всем.

Проверка: authenticated route probe + active/previous SHA evidence до deploy.

Mitigation: не включать allowlist rollout, пока owner не подтвердит safe previous
image или отдельный route quarantine. Не маскировать риск UI-флагом.

### Gate 2 — operator env flag вместо DB rollout

Симптом: изменение allowlist требует restart, но `deploy` того же SHA является
proven no-op в `prod-orchestrator.sh`.

Mitigation: rollout state хранится в DB и читается request-time. Не добавлять
ручной `docker compose up` и не расширять orchestrator в P0.

### Gate 3 — capability есть, direct endpoint не защищён

Симптом: скрытый UI, но прямой POST создаёт spend/report.

Проверка: endpoint matrix для каждого decorator в `api/synastry.py`.

Mitigation: один shared dependency на всех routes кроме capabilities; mutation
test доказывает zero writes при deny.

### Gate 4 — rollout и entitlement смешаны

Симптом: allowlisted user обходит credits/purchase или платящий пользователь
автоматически становится allowlisted.

Mitigation: rollout decision — первый независимый gate; существующие quota,
ownership, spend и access rules остаются неизменными и выполняются после него.

### Gate 5 — auth provider ломает fixture/start_param

Симптом: fixture начинает логиниться либо promo/referral intent обрабатывается
дважды.

Mitigation: shell выбирает fixture до provider; StrictMode + start_param tests
считают реальные fetch/claim calls.

### Gate 6 — remove `ignoreBuildErrors` маскируется чужим WIP fix

Симптом: P0 diff затрагивает незавершённую synastry implementation и смешивает
две задачи.

Mitigation: green clean baseline — admission gate slice 5; никаких suppressions.

### Gate 7 — удаление harness затрагивает production entrypoint

Симптом: вместе с test harness удаляется orchestrator/smoke либо active manifest
перестаёт валидироваться.

Mitigation: exact deletion list из P0-E; `rg`, `bash -n`, namespace checks и
production path review после удаления.
