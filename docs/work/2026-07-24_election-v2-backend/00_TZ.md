## 2. Факты для narrative (engine v2)

`election_engine.py`: scan возвращает помимо best_days/avoid_days ещё `facts` для LLM и фронта:

- `event`: {category, sub, label (RU sub label)}
- `days`: полный список оценённых дат (не только топ-3): date, score, label, moon_sign, moon_sign_ru, waxing, phase_pct (int), voc_fraction, voc_intervals (до 2, формат "HH:MM-HH:MM" UTC), mercury_retro
- `best_days`/`avoid_days` — как сейчас, но каждый день дополнить теми же полями (moon_sign_ru, phase_pct, voc_intervals)
- `personal`: натальные факты юзера для связки — из профиля (`UserProfile`): natal_moon_sign (вычислить через sidecar natal на дату/время/город рождения; закешировать в `natal_chart_cache` если уже там есть — посмотри как натальный контекст получает natal context service, переиспользуй), natal_moon_sign_ru, resonates (bool: день-мoon_sign == natal_moon_sign для hero-дня), personal_day_score для hero-дня (через существующий per-day скоринг НЕ вызывай — слишком тяжело; вместо этого просто `resonates` и натальный знак)

Сигнатуру scan расширить параметром `natal_moon_sign: str | None`. Сервис вычисляет его до вызова engine (через natal chart cache/sidecar — найди, как это делает natal context service, и переиспользуй их кэш).

## 3. LLM narrative — `apps/api/app/services/llm/election.py`

По образцу `services/llm/horary.py` (OpenRouter structured outputs, strict json_schema, 2 попытки). Промпт (RU, аудитория — женщины без астрологического бэкграунда, тёплый уверенный тон, без слов «хорар/электив», без выдуманных фактов — только переданные):

Вход: event label, список best_days (до 3) с фактами, avoid_days (до 3) с фактами, personal (natal_moon_sign_ru, resonates).

Выход (строгая схема `ElectionNarrative`):
```json
{
  "hero_reason": "1-2 предложения: почему лучший день подходит под событие (факты дня)",
  "hero_personal": "Астрологически: 1-2 предложения — связка дня с натальной Луной юзера (если resonates=false, мягко: как день ложится на его знак)",
  "hero_plain": "Простыми словами: 1-2 предложения — что такое Луна в <знаке> и кто им управляет, человеческий смысл для события",
  "hero_hours": "1 предложение про лучшие часы из voc_intervals (или что весь день чист)",
  "day_notes": [{"date": "YYYY-MM-DD", "note": "1-2 предложения про этот день: сильные/слабые стороны"}],
  "avoid_notes": [{"date": "YYYY-MM-DD", "note": "1-2 предложения: доказательство (voc/аспект) + практическое следствие"}]
}
```
`day_notes` ровно на каждый best_day, `avoid_notes` ровно на каждый avoid_day (валидация длин и дат — boundary-функция `validate_election_narrative` в `app/schemas/election.py` по образцу `validate_horary_llm_blocks`).

## 4. Интеграция в `election_service.run_search_task`

Порядок: status=processing → sidecar lunar-window → natal_moon_sign (кэш/sidecar) → engine.scan → LLM narrative (2 попытки) → сохранить `election_results.payload_json` = `{event, facts, days, best_days, avoid_days, narrative}` → status=done. LLM-фейл после 2 попыток → failed + refund (существующий путь). События: `election.search_succeeded`, `election.search_failed` (уже есть); добавить payload reason только тип ошибки.

## 5. Совместимость API

`ElectionSearchRead.result` сейчас passthrough dict — оставить (фронт заберёт facts+narrative). Схема ответа ломаться не должна для старого фронта: старые поля best_days/avoid_days с reasons сохранить (reasons = engine-строки как сейчас — они остаются facts-подложкой).

## Подводные камни

- LLM получает ТОЛЬКО факты из engine, тексты из воздуха запрещены промптом; fallback-шаблонов не делаем — LLM fail = search failed + refund.
- `event_type` обратной совместимости: старые записи в БД с flat id (`date`) должны читаться (при чтении не валидировать по канону).
- voc_intervals в фактах — UTC, формат "HH:MM-HH:MM".
- НЕ коммитить. НЕ трогать фронт, прототип, другие LLM-сервисы.
