## Architecture Decisions

### Ownership

Implement profection calculation in the sidecar activation layer path because it depends on natal houses, resolved house system, house cusp signs, and deterministic period calculation.

API remains a validator/merger for sidecar activation layers in W3.2. API must not independently recalculate profections in this wave.

### Sign rulers

Use traditional sign rulers for profections:

```text
Aries       -> MARS
Taurus      -> VENUS
Gemini      -> MERCURY
Cancer      -> MOON
Leo         -> SUN
Virgo       -> MERCURY
Libra       -> VENUS
Scorpio     -> MARS
Sagittarius -> JUPITER
Capricorn   -> SATURN
Aquarius    -> SATURN
Pisces      -> JUPITER
```

Do not use modern rulers for profection lords.

### Annual profection formula

Use local target date in `target_tz`.

```python
age = completed_years_between(birth_local_date, target_local_date)
annual_house = (age % 12) + 1
```

Age zero activates house 1, age one activates house 2, etc.

Determine `lord_of_year` from the sign on the profected house cusp using the resolved natal houses returned by sidecar house calculation.

### Monthly profection formula

Use monthly profections stepping from the annual profected house.

1. Determine the current annual profection year start: the most recent birthday local date at or before `target_local_date`.
2. Count completed monthly anniversaries from that annual year start to `target_local_date`.
3. Use calendar-month addition with day clamp for months that do not have the birth day.
4. Monthly step 0 starts at the annual house.

```python
monthly_house = ((annual_house - 1 + completed_month_steps) % 12) + 1
```

Determine `lord_of_month` from the sign on `monthly_house` cusp using traditional rulers.

### Strength

Use `grace/canon/activation_rules.v1.yml` period strengths:

```text
annual_profection: 0.75
monthly_profection: 0.45
```

If the canon file is missing a value, fail test/dev clearly rather than silently choosing a different product weight.

### Activation shape

Generate at minimum four period activations:

```text
annual_profection house: profected_house
annual_profection planet: lord_of_year
monthly_profection house: monthly_profected_house
monthly_profection planet: lord_of_month
```

Optional, if cleanly implemented and tested:

```text
annual_profection planet: natal planets in annual profected house
```

Do not add optional natal-planets-in-house if it introduces ambiguity or weak tests.

Required fields:

- `technique`: `annual_profection` or `monthly_profection`
- `technique_family`: `profection`
- `target_type`: `house` or `planet`
- `target_key`: house number string or uppercase planet key
- `kind`: `profected_house`, `lord_of_year`, `monthly_profected_house`, `lord_of_month`
- `phase`: `period`
- `polarity`: `neutral`
- `strength`: canon period strength
- `house`: profected house for house activations
- `target_planet`: uppercase ruler for planet activations
- `evidence`: explicit and frame-readable
- `debug`: include all period calculation inputs/outputs listed below

Stable id examples:

```text
annual_profection__HOUSE__10
annual_profection__LORD_OF_YEAR__MARS
monthly_profection__HOUSE__6
monthly_profection__LORD_OF_MONTH__JUPITER
```

Index requirements:

- house activations must be referenced in `by_house[house]`;
- ruler activations must be referenced in `by_planet[PLANET]`;
- all index refs must point to an existing `activations[].id`.

### Evidence examples
