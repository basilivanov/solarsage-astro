# Wave 13 TZ — Dynamic Day Scoring, Evidence, and Access Clarity

## Context

User-facing problem from Telegram WebApp screenshots on 2026-07-08:

- `Конкретно сегодня` texts sound templated.
- `Аспект дня` is unclear and sometimes not an actual aspect.
- For `basil_ivanov` the week looks almost static: e.g. `1 благоприятно / 8 осторожно`.
- Sunday 2026-07-12 is not cached/shown as full access and looks like a broken Sunday calculation.

Architect audit findings:

- `today_payloads_cache` for `basil_ivanov` has cached old summaries for 2026-07-08..2026-07-11:
  - `top_planet.summary = "особая тема дня"`
  - `top_flag.title = "Аспект дня"`
  - `top_flag.summary = "особое влияние дня"`
  - `lunar_phase.summary = "подводи итоги"`
- Code already changed some summaries, but `TODAY_CONTENT_VERSION` stayed `3`, so old payloads remain valid.
- Direct recalculation through production path, bypassing `today_payloads_cache`, matched cached `sphere_scores` for `basil_ivanov` on 2026-07-08..2026-07-11. The numbers are not frontend mocks.
- `normalize_day()` currently includes full natal signals before transit aspects. Static natal signals dominate day sphere scoring and top signal selection.
- `ScoringService._calculate_sphere_scores()` uses only aspect signals and `planet_in_house` signals. For day scoring, there are no current transit planet-in-house signals; only natal planet-in-house signals are present.
- `TodayInterpretationService` sends weak evidence to LLM:
  - most rows only get `Скор сферы <key>: <score>`;
  - fallback aspect evidence only gets `Аспект планеты <planet>`, without aspect type, target planet, orb, or strength.
- `DaySummaryBlock` builds the top flag from `signals[0]`, not from the top daily aspect/top flag. `signals[0]` is often a static natal signal, so the UI gets generic `Аспект дня`.
- Access for `basil_ivanov`:
  - referral ledger: 2026-06-28..2026-07-11, 14 inclusive days.
  - 2026-07-12 is outside access and returns `locked`.
  - `can_access_day()` reports `referral_days_left = (end_date - target_date).days`, while `get_summary()` reports `+1`. This causes misleading "0/3 days left" style displays.

## Goal

Make `/day/[date]` backend-owned day interpretation genuinely day-dynamic, cache-safe, and explainable:

- no production runtime mocks;
- no frontend hardcoded forecast texts;
- day sphere verdicts must be based on current day signals, not static natal baseline alone;
- LLM must receive enough real evidence to produce non-template texts;
- `Аспект дня` must be an actual top daily aspect or omitted/renamed;
- cache invalidation must force regeneration after this semantic contract change;
- access display must be consistent and must explain why Sunday 2026-07-12 is locked for `basil_ivanov`.

## Non-goals

- Do not change the 3001 visual oracle layout.
- Do not reintroduce mock APIs or runtime frontend fixtures.
- Do not fake personalized text on the frontend.
- Do not grant extra access days silently as a data patch.
- Do not rewrite the whole astrology canon.

## Required Architecture

### 1. Split natal baseline from day signals

Keep natal context as baseline/context, but day verdicts must be driven by day signals.

Implement one explicit day-signal path, for example:

- `NormalizationService.normalize_day()` may still return combined signals if other code depends on it.
- Add or expose a clear filtered set for day scoring:
  - transit-to-natal aspects: `planet` starts with `Transit_`;
  - current transit planet-in-natal-house signals;
  - future-proof lunar/retrograde/day-event signals if already modelled as `AstroSignal`.

Do not let static natal `planet_in_house`, `planet_in_sign`, and natal aspects dominate:

- `day_status`;
- `sphere_scores` used by `ConcreteAdvice`;
- `top_flags`;
- `day_summary` facts.

Natal data can still be passed to LLM as context/evidence, but not as the primary daily verdict score.

### 2. Add transit planet-in-house day signals

Today currently computes transit planet houses for chart rendering, but scoring does not receive them.

Add normalized day signals for each transit planet:

- `type = "planet_in_house"`
- `planet = "Transit_<Planet>"`
- `house = <natal/current house computed from transit longitude and natal houses>`
- `sign = <transit sign if available>`
- `strength` should be deterministic; start conservatively at `1.0` unless canon has a better weight.

This is important so Moon movement and current planet houses can change daily sphere scoring.

### 3. Make scoring evidence explainable

`ConcreteAdviceEvidence` should carry real reasons, not only a numeric score.

For each concrete advice row, include the best available evidence:

- for score-based rows: top contributing day signals for the mapped backend sphere;
- for aspect rows: planet, target_planet, aspect_type, orb, strength, title;
- for planet-in-house rows: planet, house, sign when known, strength, title;
- keep evidence restricted to facts actually present in calculation.

Update backend schema and `lib/contracts/today.ts` if new evidence fields are needed. If backend contracts are generated in this repo, regenerate them using the existing project flow; do not hand-edit generated artifacts unless that is the local pattern.

The LLM prompt/validation should continue preventing invented planets/aspects/houses, but after this change it should be allowed to mention real evidence because evidence contains the real facts.

### 4. Fix `DaySummaryBlock`

`day_summary.facts` must not use generic stale labels.

Requirements:

- `top_flag` fact must come from the top daily aspect/top flag, not `signals[0]`.
- If there is a daily aspect, title should be concrete, e.g. `Луна оппозиция Плутон`.
- Summary should explain type/tone, e.g. `напряжённый аспект`, `поддерживающий аспект`, or a similarly factual label.
- If no daily aspect exists, do not show `Аспект дня`; use a factual alternative only if there is a real non-aspect day signal.
- `top_planet.summary` must stop using generic `особая тема дня`. Use factual wording derived from the real source, or omit the summary.
- `lunar_phase.summary` must use current code semantics (`убывающая фаза`, etc.) after cache invalidation.

### 5. Cache invalidation

Bump `TODAY_CONTENT_VERSION` from `3` to `4`.

Update tests that intentionally assert the current version.

After implementation, old cached payloads with content_version `3` must be ignored and regenerated.

### 6. Access clarity

Fix the off-by-one inconsistency:

- `can_access_day()` and `get_summary()` must agree on inclusive days left.
- For an active access window ending on 2026-07-11, July 8 should report 4 inclusive days left if the UI means "including today".
- July 11 should report 1 inclusive day left, not 0, if the day is still accessible.

Do not silently extend `basil_ivanov` to Sunday. The correct output for 2026-07-12 with the current ledger is locked because access ends on 2026-07-11. Add/adjust tests to make this explicit.
