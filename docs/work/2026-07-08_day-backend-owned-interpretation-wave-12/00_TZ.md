## Goal

Finish the `/day` architecture so every forecast/interpreted text rendered on the day screen is owned by the backend payload and generated from real SolarSage/scoring context. The frontend must only render the contract. It must not contain local forecast-copy templates for sphere advice, chart planet interpretations, or compact day-summary recommendations.

This wave is not a visual redesign. Keep the Wave 11 / 3001 visual shell and interactions.

## Current Problem

The day pipeline already calculates and caches real data in `today_payloads_cache.payload_json`:

- `day_status`
- `top_flags`
- `sphere_scores`
- `planet_influences`
- `day_chart`
- `important_today`
- `reading`
- `why_this_happens`
- `notes`

But the current frontend still creates some forecast text locally:

- `components/today/concrete-day-advice.tsx`
  - `SPHERE_ADVICE_TEXTS`
  - `buildConcreteAdviceRows()`
  - local verdict/text selection from `sphereScores`, `topFlags`, `planetInfluences`
- `components/today/day-chart.tsx`
  - `planetDescription()`
  - local house/planet theme interpretation
- `components/today/day-summary-card.tsx`
  - `STATUS_META.line`
  - `PLANET_THEME`
  - local lunar action copy such as "подводи итоги"

These are not runtime mocks, but they are still product forecast templates in the frontend. That violates the architecture target.

- Do not reintroduce runtime mocks or `USE_FIXTURES`.
- Do not add a DB migration for this wave unless you prove it is necessary. `today_payloads_cache.payload_json` is JSON text and can store the new payload shape.

## Required Architecture

### Backend is responsible for:

1. deterministic calculation and verdict selection;
2. selecting evidence from real calculated signals;
3. calling LLM only to write human text from that evidence;
4. validating LLM output before caching;
5. caching the final payload, including all frontend-visible forecast text.

### LLM is responsible for:

1. wording;
2. short practical interpretation;
3. using only facts passed by backend.

LLM must not calculate astrology, decide verdicts, invent planets/houses/aspects, or invent unavailable evidence.

### Frontend is responsible for:

1. rendering;
2. expand/collapse state;
3. visual styling and accessibility;
4. static UI chrome labels only.

Frontend may keep static UI text like:

- `Конкретно сегодня`
- `Разбор дня`
- `Карта дня`
- `свернуть`
- `все 12 сфер`
- tab labels
- chart legend labels

Frontend must not keep product forecast templates like:

- "Дела идут со скрипом..."
- "Сократи траты..."
- "Сегодня акцент через ..."
- "день на твоей стороне..."
- planet/theme recommendation copy.

#### `ConcreteAdviceBlock`

```python
ConcreteAdviceVerdict = Literal["good", "caution", "avoid", "neutral"]
ConcreteAdviceConfidence = Literal["high", "medium", "low"]
ConcreteAdviceEvidenceKind = Literal[
    "sphere_score",
    "aspect",
    "planet_in_house",
    "day_status",
    "lunar",
    "important_today",

class ConcreteAdviceEvidence(CamelModel):
    kind: ConcreteAdviceEvidenceKind
    title: str
    weight: float | None = None
    planet: str | None = None
    target_planet: str | None = None
    aspect_type: str | None = None
    orb: float | None = None
    strength: float | None = None
    sphere_key: str | None = None

class ConcreteAdviceRow(CamelModel):
    key: Literal[
        "work",
        "money",
        "documents",
        "relationships",
        "sport",
        "communication",
        "health",
        "decisions",
        "travel",
        "creativity",
        "study",
        "shopping",
    ]
    label: str
    icon_name: str
    rank: int
    verdict: ConcreteAdviceVerdict
    confidence: ConcreteAdviceConfidence

class ConcreteAdviceCounts(CamelModel):
    good: int

    avoid: int

class ConcreteAdviceBlock(CamelModel):
    rows: list[ConcreteAdviceRow]
    counts: ConcreteAdviceCounts
```

### 3. Deterministic verdict selection

Backend must compute `verdict` before LLM.

Required behavior:

- Every response has exactly 12 rows.
- Row order is fixed by product order.
- `counts` is derived from rows.
- Strong mapped sphere score drives the row first.
- If no mapped sphere score exists, use evidence from top signals / planet influences / day status.
- If evidence is weak, use `neutral` with `confidence="low"`, but still provide a row.
- Never use a frontend fallback to fabricate advice.

Recommended threshold semantics:

- `score >= 6.0` -> `good`
- `score <= 3.0` -> `caution`
- severe negative evidence from tense aspect or void Moon may become `avoid`
- otherwise `neutral`

If existing scoring semantics prove different, document the exact thresholds in the agent report and tests.

### 4. LLM wording for concrete advice

Add a new LLM method in the existing LLM service:

```python
async def generate_concrete_advice(
    self,
    contexts: list[dict],
) -> dict[str, str] | None:
    ...
```

Input context per row must include:

- product key;
- Russian label;
- verdict;
- confidence;
- evidence list;
- day status;
- top relevant signal titles;
- no raw `Transit_` / `Natal_` prefixes.

Prompt requirements:

- Return JSON only.
- Keys must be the 12 product keys.
- Values must be Russian strings.
- 1 sentence per sphere.
- 7-18 words per sentence.
- No Latin alphabet words.
- No unsupported planet/aspect/house facts.
- Tone: practical Telegram microcopy, direct on "ты".
- Do not compute astrology.

Validation:

- JSON must parse.
- All 12 keys must be present.
- Values must be non-empty Russian strings.
- Reject values containing `Transit_`, `Natal_`, or Latin alphabet words.
- Reject values that mention planets/aspects not present in the row evidence.

On LLM failure:

- Do not insert old frontend product templates.
- Return non-forecast unavailable text for affected rows:
  - `Рекомендация временно недоступна.`
- Mark those rows `confidence="low"`.
- Do not hide the block.
- The report must say whether fallback path is cached; preferred behavior is to cache only if at least 9/12 rows have valid LLM text. If fewer than 9 rows are valid, raise generation failure and let existing API error handling surface it.

### 5. LLM wording for compact day summary

Remove frontend-owned recommendation line from `DaySummaryCard`.

Backend must produce:

- `day_summary.status_label`
  - `steady` -> `Ровный день`
  - `supportive` -> `Поддерживающий день`
  - `tense` -> `Напряжённый день`
- `day_summary.status_line`
  - generated by LLM or backend semantic service from `day_status`, top signals, and sphere scores;
  - no frontend hardcoded lines like `день на твоей стороне — действуй`.
- `day_summary.facts`
  - `top_planet` fact if planet influence exists;
  - `lunar_phase` fact if lunar/calendar data is available in backend context;
  - `void_moon` fact if available;
  - `top_flag` fact from existing backend `top_flags[0]`.

If lunar data is currently only fetched by frontend calendar, do not block this wave on moving calendar lunar into day payload. For this wave, backend summary may omit lunar facts unless available in `TodayService` context. Frontend must still not invent lunar action text.

### 6. Chart planet interpretations

Backend must populate `day_chart.transit_planets[].interpretation`.

Interpretation text must be based on:

- planet name;
- sign;
- house;
- strongest relevant aspects involving that planet from `day_chart.aspects`;
- day status if needed.

Frontend `DayChart` must remove `planetDescription()`.

If interpretation is missing for a planet:

- render `Интерпретация временно недоступна`;
- do not build a local phrase from house/planet dictionaries.

### 7. Wire into TodayService and cache

Modify:

```text
apps/api/app/services/today_service.py
```

Required sequence on cache miss:

1. build natal/transits/signals;
2. score;
3. build semantic layer;
4. generate headline/reading/notes/why as today;
5. build `day_chart`, `planet_influences`, `sphere_scores`, `important_today`;
6. call `TodayInterpretationService.build(...)`;
7. build `TodayPayload` with `day_summary`, `concrete_advice`, updated `day_chart`;
8. cache final payload with `_cache_payload()`.

Required cache behavior:

- bump `TODAY_CONTENT_VERSION` from `2` to `3`;
- bump `TodayMeta.contract_version` from `2` to `3`;
- bump `prompt_version` from `1` to `2` if any LLM prompt changes;
- do not bump `calculation_version` unless scoring/calculation semantics change;
- no bulk cache deletion required because `_get_cached_payload()` already rejects old content versions.
