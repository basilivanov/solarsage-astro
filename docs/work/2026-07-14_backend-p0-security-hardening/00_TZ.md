## 4. Архитектурное решение: runtime security policy

### 4.1. Новая единая policy

Создать `apps/api/app/core/runtime_security.py`.

Модуль должен быть единственным местом, которое отвечает за:

- нормализацию `APP_ENV`;
- определение deployed/local среды;
- разбор и строгую проверку `CORS_ALLOWED_ORIGINS`;
- решение, можно ли монтировать internal routes;
- fail-closed валидацию security-critical deployed settings.

Требуемые публичные сущности:

```python
@dataclass(frozen=True)
class RuntimeSecurityPolicy:
    environment: Literal["development", "test", "staging", "production"]
    deployed: bool
    cors_allowed_origins: tuple[str, ...]
    internal_routes_enabled: bool

def build_runtime_security_policy(settings: Settings) -> RuntimeSecurityPolicy:
    ...
```

Допускается другое имя private helpers, но один публичный builder и immutable result обязательны.

### 4.2. Нормализация APP_ENV

Поддержать только такие входы:

| Raw | Canonical |
|---|---|
| `dev`, `development` | `development` |
| `test` | `test` |
| `stage`, `staging`, `preview` | `staging` |
| `prod`, `production` | `production` |

Trim и case-insensitive обязательны. Любое неизвестное или пустое значение должно приводить к startup `ValueError`, кроме отсутствующей переменной, для которой текущий default `dev` остаётся local development.

`deployed=True` только для `staging` и `production`.

### 4.3. CORS_ALLOWED_ORIGINS

Добавить в `Settings` поле:

```text
CORS_ALLOWED_ORIGINS
```

Формат env: comma-separated exact origins.

Пример:

```text
CORS_ALLOWED_ORIGINS=https://dev.astro.vasiliy-ivanov.ru,https://test.astro.vasiliy-ivanov.ru
```

Правила:

1. Никогда не использовать `*` — ни в одной среде при `allow_credentials=True`.
2. Каждый origin должен быть полным origin `scheme://host[:port]`:
   - без path;
   - без query/fragment;
   - без username/password;
   - без wildcard host;
   - без trailing slash после нормализации.
3. В `staging`/`production` разрешён только `https`.
4. В deployed environment список обязателен и не может быть пустым.
5. В deployed environment список обязан содержать `https://{APP_DOMAIN}`.
6. Duplicates удалить, сохраняя deterministic order.
7. В local development при пустом env использовать только этот default:

```text
http://localhost:3000
http://127.0.0.1:3000
http://localhost:3002
http://127.0.0.1:3002
http://localhost:3003
http://127.0.0.1:3003
```

8. Для `test` пустой список допустим; ASGI test clients не требуют browser CORS.

### 4.4. Fail-closed deployed validation

Для `staging` и `production` startup обязан завершаться ошибкой до открытия socket, если выполняется хотя бы одно условие:

- `APP_DOMAIN` пустой, localhost, loopback, содержит scheme/path или wildcard;
- CORS origins отсутствуют/невалидны/содержат `*`;
- нет exact `https://{APP_DOMAIN}`;
- `DEV_MODE=true`;
- `SESSION_COOKIE_SECURE=false`;
- `TELEGRAM_BOT_TOKEN` пуст;
- `GRACE_USER_SALT` короче 32 символов;
- `DATABASE_URL` использует SQLite.

Не проверять в этой задаче наличие LLM key: API может корректно стартовать с deterministic fallback. Не расширять P0 до provider refactor.

Сообщения startup exceptions должны называть только key/reason, но не значение secret или полный DSN.

### 4.5. Internal route policy

`internal_routes_enabled=True` только когда одновременно:

```text
canonical environment == development
DEV_MODE == true
APP_DOMAIN является localhost/127.0.0.1/::1
```

Для `test`, `staging`, `production` всегда `False`.

## 5. FastAPI composition root

Переработать `apps/api/app/main.py` в testable composition root:

```python

    policy = build_runtime_security_policy(app_settings)
    validate_canon_bundle()
    ...
    return application

```

Требования:

1. `create_app()` не меняет глобальный `settings` и пригоден для нескольких вызовов в одном pytest process.
2. CORS берёт origins только из `policy.cors_allowed_origins`.
3. `allow_credentials=True` сохранить.
4. `allow_methods`/`allow_headers` можно оставить текущими; цель этой задачи — origin policy.
5. Minimal `/api/health` всегда смонтирован и сохраняет exact текущий response contract.
6. Product routers всегда смонтированы как сейчас.
7. Эти routers импортировать и монтировать только внутри `if policy.internal_routes_enabled`:
   - `debug.router`;
   - `metrics.router`;

## 7. Privacy-safe identity logging

### 7.1. Settings и helper

Добавить в `Settings`:

```text
GRACE_USER_SALT
```

Создать `apps/api/app/core/log_identity.py` с публичными функциями:

```python
def hash_log_identifier(namespace: str, value: object) -> str:
    ...

def hash_user_id(value: object) -> str:
    ...
```

Алгоритм:

```text
HMAC-SHA256(key=GRACE_USER_SALT, message="{namespace}:{value}")
output = "h1_" + first 24 lowercase hex chars
```

Инварианты:

- не использовать plain SHA от UUID;
- namespace обязателен и нормализуется к безопасному lowercase token;
- одинаковый namespace/value/salt даёт одинаковый hash;
- разные namespace дают разные hash;
- output никогда не содержит исходное value;
- в deployed отсутствие/короткий salt уже блокируется policy;
- для local/test без salt использовать явный module constant `LOCAL_TEST_LOG_SALT`, не environment-derived secret;
- helper не логирует вход и не включает его в exception text.

### 7.2. Binding user context

В `apps/api/app/core/dependencies.py`:

1. Полностью удалить четыре raw `print` из auth resolution.
2. После успешного `resolve_session` вызвать:

```python
bind_log_context(user_id_hash=hash_user_id(session.user_id))
```

3. То же сделать в `require_session_optional` после успешного session resolution.
4. При InvalidSession не логировать cookie name, cookie list, token length/value или raw exception message.
5. Не добавлять новый event registry только ради этой задачи. `system.request` с 401 уже обеспечивает operational visibility.

В `auth_telegram` после получения DB user также bind-ить `user_id_hash`, чтобы последующие события данного request имели identity context.

### 7.3. Удаление raw identifiers из log_event

Проверить все production `log_event(...)` calls, не только четыре исходных файла.

В `payload`, `error`, `http` и `msg` запрещены raw значения следующих идентификаторов:

```text
user_id
tg_user_id
telegram_id
session_id/token
question_id
credit_id
thread_id
message_id
report_id
natal_context_id
profile_id
```

Правило исправления:

- raw `user_id` удалить; user correlation идёт через envelope `user_id_hash`;
- entity ID удалить, если он не нужен для эксплуатации;
- если entity correlation действительно нужна, использовать `hash_log_identifier(<namespace>, value)` и поле `<entity>_id_hash`;
- не использовать UUID в f-string `msg`;
- `msg` должен быть статическим либо содержать только enum/status/error type;
- raw exception `str(exc)` не помещать в logs, если exception потенциально содержит input/profile/question/provider body. Сохранять `kind`, safe `code`, safe `stage`, HTTP status;
- DB error details и stack остаются только вне публичной structured telemetry, но в этой задаче не вводить отдельный unsafe logger.

Обязательный минимум файлов:

- `services/day_scoring_runtime_service.py`;
- `services/today_service.py`;
- `services/calendar_service.py`;
- `services/horary_service.py`;
- `services/chat_service.py`;
- `services/natal_report_service.py`;
- `api/_log.py`;
- `api/natal.py`;
- `middleware/correlation.py`;
- `core/dependencies.py`.

Не менять бизнес-решения, transaction boundaries или public error payloads в этих файлах.

### 7.4. Redactor hardening

В `apps/api/app/core/redactor.py`:

1. Добавить exact-key redaction для raw identity keys из предыдущего раздела, включая snake/camel/lowercase варианты.
2. `session_id` больше не должен быть allow-key; `user_id_hash` остаётся allow-key.
3. Разрешены operational IDs:
   - `correlation_id`;
   - `operation_id`;
   - `packet_id` только если это не DB/session identifier;
   - поля, заканчивающиеся на явно перечисленные `_id_hash`.
4. Добавить value redaction для canonical UUID в произвольной строке: `[redacted-uuid]`.
5. Добавить value redaction для labeled numeric/UUID IDs (`user_id=...`, `question id ...`, и т.п.): `[redacted-identifier]`.
6. Не редактировать даты, scoring/canon versions и business enum/status.
7. Redactor остаётся pure и never-raise.

### 7.5. Correlation middleware route template

В текущем коде raw `request.url.path` сохраняется до routing. Исправить:

1. До `call_next` не использовать raw path в log context. Применять safe placeholder, например `"<unresolved>"`.
2. После `call_next` получать template из `request.scope["route"].path`.
3. На exception также повторно попробовать получить route template после routing.
4. Если template недоступен, использовать static `"<unmatched>"`, не raw URL path.
5. Перед `log_event` обновить bound `http_route` canonical template.
6. Не включать raw query string.
7. В `system.error` не передавать `str(exc)`; только exception class/kind и safe status.

Тест должен доказать, что запрос к параметризованному route логирует `/api/day/{date}` или другой canonical route template, но не конкретную дату/UUID.

## 8. Static guardrail

Расширить `scripts/check_logging_guardrails.py`.

Новый gate должен анализировать Python AST для `log_event(...)` calls и падать, если:

- dict в `payload`/`error`/`http` содержит forbidden raw identity key;
- `msg` является f-string и interpolates identifier expression (`user_id`, `question_id`, `credit.id`, `thread.id`, `report.id`, и аналогичные);
- production core/api/service/middleware использует raw `print`, кроме существующего явно documented allowlist `canon_service.py` для startup canon diagnostics.

Требования к gate:

- не искать forbidden keys во всех dict файла, только внутри аргументов `log_event`;
- не считать `user_id_hash` нарушением;
- не считать model/DB/cache dictionaries нарушением;
- выводить file:line и reason;
- добавить self-tests или маленькие fixture-based tests, доказывающие positive и negative cases;
- сохранить registry drift/backend logger/frontend console gates.

Не редактировать generated event registry: новый event для P0 не требуется.
