## goal

Один воспроизводимый прогон в ДВА плеча: ~14 реальных входов Today narrative
× 5 моделей × 2 повтора × 2 плеча (280 вызовов, оценка ≈ $0.42, жёсткий стоп
на $0.90), с автоматическими метриками (JSON/инструкции/grounding/штампы/цена/
latency), слепым human-review образца владельцем и HTML-отчётом с
рекомендацией «самая дешёвая модель выше порога качества» + вердиктом по
миграции на strict json_schema.

Плечи (одинаковые входы, правила и метрики; различается только форма ответа):
- **A — продовый shape**: `response_format={"type":"json_object"}`,
  keyed-шаблон ответа (`convergences: {"cvg_…": {...}}`, `impulses:
  {"evt_…": {...}}`) — точная реплика текущего прода.
- **B — strict json_schema**: `response_format={"type":"json_schema",
  "json_schema": …}` + `provider={"require_parameters": true}`, шаблон ответа
  на массивах (`convergences: [{groupId, summary, meaning, action}]`,
  `impulses: [{eventId, summary, meaning, action}]`, `main_event` — объект или
  null; claim = `{text, sourceEventIds}` или null). Массивы обязательны:
  strict Structured Outputs не выражают словари с произвольными ключами — это
  подтверждённое ограничение продовой ветки (`llm_service.py:416-419`).

## Требования к реализации

### 1. Сбор входов (локально, бесплатно)

Профиль владельца из dev-БД (user_id `eb3876be-e1b4-43d6-b887-1f8554e33150`,
read-only). Для ~20 кандидатских дат (09–28.08.2026) прогнать
`calculate_today_convergence` + `build_today_convergence_snapshot_document`
в памяти (без публикации), затем `build_today_narrative_prompt(...,
prompt_version="today-narrative-v5", person=TodayNarrativePerson(first_name=…))`.
Из кандидатов выбрать ~14 входов с максимальным покрытием: ≥3 convergence_today,
≥3 quiet_day, все polarity (supportive/tense/mixed), ≥8 разных facet, hero и
medium группы. `inputs.json` фиксирует: target_date, state, day_tone, facets,
polarities, input_hash — после первого scored-прогона immutable.

### 2. Прогон моделей

- Плечо A: тело запроса = продовое (`_openrouter_generate` shape):
  user-сообщение, `max_tokens=2000`, `response_format=json_object`;
  без temperature.
- Плечо B: то же, но `response_format={"type":"json_schema",
  "json_schema": {"name":"today_narrative","strict":true,"schema":…}}` +
  `provider={"require_parameters": true}`; секция «Точный JSON-шаблон ответа»
  в промпте заменяется на array-форму (вход evidence и все правила — те же).
  Схема публикуется в `task.md` и immutable вместе с task. HTTP 400/404 по
  схеме фиксируется как класс `strict_unsupported` (без retry — это
  свойство модели/провайдера, а не транзиент).
- 2 повтора на вход×модель×плечо; concurrency 2; timeout 60с; 1 retry на
  transport/5xx (помечается, считается в бюджет).
- Учёт: из каждого ответа брать `usage.prompt_tokens/completion_tokens`
  и `latency` (wall); стоимость = usage × pricing snapshot
  (`pricing-2026-08-09.toml`, immutable, цены из фактуры выше).
- **Budget guard**: перед каждым вызовом проверять накопленную сумму;
  > $0.90 — стоп с отчётом о потраченном. Ориентировочная смета ≈ $0.42
  (проверить в validate-режиме и напечатать).
- Режимы CLI: `validate` (бесплатно: собирает входы, печатает план и смету,
  НИ одного платного вызова), `run --confirm-paid-run` (платный),
  `score` (пересчёт метрик из raw), `--selftest` (scorer на синтетических
  ответах без сети).
- Raw ответы (полные тексты) — только в `.eval-runs/narrative-model-eval-v1/`;
  PII: имя владельца в committed-артефакты не попадает (маскировка на «ИМЯ»
  при компактации; raw остаётся локально gitignored).

### 3. Автоматические метрики (на ответ, потом агрегация)

Перед скорингом ответ плеча B нормализуется обратно в keyed-форму
(`groupId`/`eventId` → ключи блоков) — весь scorer для обоих плеч одинаков.

0. `strict_support` (плечо B) — доля вызовов без `strict_unsupported`;
   в плече A всегда 1.0.
1. `json_valid` — парсится, структура совпадает с шаблоном snapshot'а
   (после нормализации), нет markdown-ограждений.
2. `fill_rate` — доля заполненных claim'ов из требуемых шаблоном.
3. `claim_binding` — все sourceEventIds ⊆ selected и непустые; id блоков
   совпадают с шаблоном (в B — groupId/eventId из входа).
4. `sanitizer_pass` — для каждого claim: не `has_forbidden_narrative_tokens`
   и не `has_narrative_grounding_violation` (наш продовый судья — главная
   метрика «точности текста» по построению).
5. `length_ok` — summary ≤220, meaning ≤260, action ≤180.
6. `stamp_hits` — вхождения штампов из v5-промпта («в сфере», «может
   усилиться», «наблюдается», «играет важную роль», «указывает на важность»,
   «возможна активность», «междуличностные связи», «жизненные выборы»,
   «позитивные перемены»).
7. `datetime_leak` — часы/даты/окна в тексте claim (regex ЧЧ:ММ, даты,
   «с HH по HH»).
8. `name_rule` — firstName встречается ≤1 раза на весь ответ.
9. `lexicon_cover` — каждый claim содержит ≥1 слово из lexicon своего facet.
10. `repeatability` — Jaccard по токенам между двумя повторами (на блок).
11. `latency_ms` (p50/p95 по модели), `cost_usd` (факт, usage-based),
    `cost_per_1k_narratives` и `monthly_estimate` (×500 pregen-прогревов/день
    ×30 — масштаб DAY_PREGEN_MAX_USERS).

Композит `auto_score` (веса в rubric.md): json_valid — гейт (0 при невалидном),
далее sanitizer_pass 30, fill_rate 15, binding 10, length 10, lexicon 10,
stamps 10, leaks 10. Sanity-контроль жгута: nano обязан воспроизвести
известные живые дефекты (cross-facet тексты) — если нет, жгут сломан, стоп.

### 4. Human blind review (владелец)

Для топ-2 моделей по auto_score + baseline nano: по ~10 блоков на модель,
перемешанные, без имён моделей (`candidate-a/b/c`), оценки beauty и
accuracy 1–5 + заметки в `scorecard.md` → `review.json` (схема как в
evals/review.example.json). Идентичности раскрываются после оценки.

### 5. Отчёт

`narrative_eval_report.py` → `evals/results/<run-id>/report.html`:
таблица моделей × плеч A/B (цена/вызов, $/1k, monthly, latency p50/p95,
strict_support, все метрики, auto_score, human_score), рекомендация по
правилу «самая дешёвая выше порога» (порог: auto_score ≥ nano И
sanitizer_pass ≥ nano — считается по плечу A как продовому baseline),
отдельный вердикт по плечу B: «мигрировать на strict json_schema
да/нет и с какой моделью» (учитываются strict_support, json_valid,
деградация качества относительно A), раздел «следующие шаги»
(json_schema migration с array-шаблоном, system/user сплит,
fallback-модель). Публикация владельцу через существующий
`scripts/agent_eval_publish.sh` (CF quick tunnel).
