## 3. Current Architecture To Preserve

Main already has an important real-data calendar foundation. Preserve it.

Current product path:

- `app/(grace)/calendar/page.tsx`
- `components/calendar/calendar-screen.tsx`
- `components/calendar/lunar-calendar-strip.tsx`
- `lib/api/calendar.ts`
- `lib/contracts/calendar.ts`
- backend endpoint: `/api/calendar?month=YYYY-MM`

Required data rules:

- `CalendarScreen` must use `getMonthCalendar(year, zeroBasedMonth)`.
- `CalendarScreen` must render `CalendarPayloadReadModel.days` directly.
- Month navigation boundaries must come from `payload.allowedRange` when present.
- Day access/locked/open states must come from each `day.access` and `day.disabled`.
- Lunar UI must render backend `day.lunar` fields only.
- Missing backend lunar fields must render unavailable/empty state, not locally calculated facts.

Explicitly do not reintroduce these mock-preview data paths into product code:

- `monthMatrix()` as the source for rendered calendar cells;
- `getMonthStatuses()` as the screen's primary data source;
- `isDayAccessible(date, access)` as the source for per-day locked state;
- `computeMoonPhaseForDay()`;
- `getLunarDay()`;
- `getVoidOfCourse()`;
- `lib/mocks/*`;
- `lib/demo-data.ts`;
- MSW;
- any runtime `USE_FIXTURES`/demo-mode branch.

It is acceptable for pure presentation code to derive a glyph style from real backend fields such as `lunar.phase` or `lunar.illumination`. It is not acceptable to calculate missing astrological facts on the client.

## 4. In Scope

### 4.1 Calendar presentation

Bring `/calendar` closer to the mock-preview visual language:

- compact top month header with previous/next controls;
- segmented `Дни` / `Луна` control with clear active state;
- day grid with stable circular cells, selected/today/locked states, and mood icons;
- moon mode that shows lunar info from backend fields;
- bottom selected-day summary with CTA to open the day or preview;
- loading and unavailable states that remain visually calm and do not show stale month cells.

Do not add marketing/explainer text. No cards inside cards. No decorative gradient/orb/bokeh backgrounds.

### 4.2 Lunar strip

Use the mock-preview `LunarCalendarStrip` as a presentation reference, but back it with `CalendarDayReadModel[]`.

Acceptable implementation shape:

- `LunarCalendarStrip({ days })`;
- filter to current-month days with real lunar data;
- render a horizontal strip of days with phase/glyph/illumination/lunar-day labels when those fields exist;
- render a selected-day detail panel from the selected `day.lunar`;
- render `data-testid="lunar-calendar-strip"` when data exists;
- render `data-testid="lunar-calendar-unavailable"` when backend lunar data is absent.

Do not copy the mock-preview version that takes `{ year, month }` and computes phases locally.

### 4.3 UI Semantic/Test Contract

Ensure stable selectors and accessibility states:

- `data-testid="calendar-screen"` on the root;
- `data-load-state="loading|ready|error"` on the root;
- `data-testid="calendar-loading"` for loading;
- `data-testid="calendar-unavailable"` for terminal unavailable state;
- `data-testid="calendar-grid"` on the grid;
- `data-testid="calendar-day-YYYY-MM-DD"` on day buttons;
- `data-testid="lunar-calendar-strip"` and `data-testid="lunar-calendar-unavailable"`;
- `data-testid="calendar-selected-summary"` on the bottom summary;
- `aria-pressed` on selected day buttons and segmented controls;
- native `disabled` for disabled day buttons and navigation buttons;
- accessible names for previous/next month, `Дни`, `Луна`, and open-day CTA.

Tests must not depend on Tailwind class names.

### 4.4 Mock visual e2e for `/calendar`

Add a calendar mock-visual spec under:

```text
e2e/mock-visual/calendar.spec.ts
```

Use only `installMockApiRoutes()` from `e2e/mock-visual/route-interception.ts`.

Required fixture map for `/calendar`:

- `/api/auth/dev` if the app shell calls dev auth in local development;
- `/api/access` with a real-shaped access summary, for example:

```json
{
  "user": "trial",
  "referralDaysLeft": 8,
  "subscriptionActive": false,
  "accessStart": "2026-07-01",
  "accessUntil": "2026-07-08"
}
```

- `/api/calendar` with `calendarPayload` from `e2e/mock-visual/fixtures/calendar-2026-07.ts`.

The spec must:

- navigate to `/calendar`;
- assert the screen reaches `data-load-state="ready"`;
- assert header/grid/lunar strip/selected summary are visible;
- switch to `Луна` mode and assert backend lunar values are visible;
- assert no horizontal overflow on a mobile viewport;
- assert no missing API fixtures after a quiet wait;
- include a negative-proof test or shared assertion proving missing calendar API fixtures are recorded by `MissingRequestsTracker`.

You may reuse or extract the quiet-wait helper from `day.spec.ts`, but keep it test-only.
