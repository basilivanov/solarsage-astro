Дата: 2026-07-23

Исполнитель: кодер в tmux astro2. Коммитит ревьюер.

## Контекст и цель

В приложении есть вечерний чек-ин (accuracy «Попал/Частично/Мимо» за вчера, внутри webapp). Хотим собирать ту же оценку через бота: вечером бот присылает сообщение с inline-кнопками, тап записывает оценку в БД. Это повышает response_rate сбора фидбека.

Факты из разведки (опираться на них, не переисследовать):
- Чек-ин: таблица `evening_checkins` (`mood NOT NULL` legacy — переиспользовать её для bot-фидбека ГРЯЗНО, поэтому **новая таблица**). Таймзона юзера: `profile.current_tz or profile.birth_tz`, паттерн — `CheckinService._profile_timezone` (`apps/api/app/services/checkin_service.py:236`).
- Webhook `apps/api/app/api/telegram_webhook.py` сейчас stateless (без БД), обрабатывает только /start, отвечает Bot API method JSON (Telegram сам исполняет). Гейт: заголовок `X-Telegram-Bot-Api-Secret-Token` vs `settings.telegram_webhook_secret`, hmac.compare_digest, fail-closed.
- `scripts/telegram/setup_webhook.py:139` шлёт `allowed_updates=["message"]` — без `callback_query` нажатия кнопок не дойдут.
- Job-паттерн: `apps/api/app/jobs/billing_rebill.py` (one-shot, kill-switch, log_event, exit codes) + compose profile `billing-rebill` в `infra/production/docker-compose.app.yml:196-207`.
- Outbound Bot API: `https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/sendMessage`, egress с прода прямой. `settings.telegram_bot_token` есть.
- Лейблы accuracy: 3 «Попал ✓», 2 «Частично ~», 1 «Мимо ×» (как `ACCURACY_OPTIONS` в `lib/contracts/checkin.ts`).

## Что построить

### 1. Таблица `day_feedback` + миграция

- Модель в `apps/api/app/db/models.py`: `DayFeedback` — `id` (uuid PK, default uuid4), `user_id` (FK users.id, **ON DELETE CASCADE**, index), `target_date` (date), `accuracy` (Integer, CHECK 1..3), `source` (String(20), default "tg_bot"), `created_at`, `updated_at` (timestamptz, default now, onupdate now). `UniqueConstraint('user_id', 'target_date', name='uq_day_feedback_user_date')`.
- Миграция `apps/api/alembic/versions/0022_day_feedback.py` (предыдущая — 0021). По образцу соседних миграций (смотри 0017 как расширение/0007 как создание таблицы).

### 2. `FeedbackService` — `apps/api/app/services/feedback_service.py`

GRACE-шапка обязательна. Методы:
- `upsert(user_id, target_date, accuracy, source) -> DayFeedback` — insert или update существующей строки (по uq), accuracy валидировать 1..3.
- `get_for_date(user_id, target_date) -> DayFeedback | None`
- `local_yesterday(profile) -> date` — по `_profile_timezone`-паттерну.
- `list_users_for_reminder(session, target_hour_local) -> list[User]` — юзеры: `is_onboarded`, есть `current_tz или birth_tz`, их локальный час == target_hour_local, у них НЕТ day_feedback за локальное вчера И НЕТ evening_checkins с accuracy за локальное вчера (уже ответили в вебе). Джойн `User` + `UserProfile`.

### 3. Outbound клиент — `apps/api/app/services/telegram_client.py`

Минимум: `async def send_message(chat_id: int, text: str, reply_markup: dict | None = None) -> None` — httpx.AsyncClient, POST `https://api.telegram.org/bot{settings.telegram_bot_token}/sendMessage`, json `{"chat_id", "text", "reply_markup"?}`, timeout 15s; не-200 или `ok:false` → raise `TelegramClientError`. GRACE-шапка. Больше ничего (без ретраев/очередей).

### 4. Job — `apps/api/app/jobs/feedback_broadcast.py`

По образцу `billing_rebill.py` (GRACE-контракты, kill-switch, структурные логи, exit codes):
- Kill-switch: `settings.feedback_broadcast_enabled` (новый конфиг, env `FEEDBACK_BROADCAST_ENABLED`, default **false**) — false → лог `feedback.broadcast_skipped`, exit 0.
- Выборка через `FeedbackService.list_users_for_reminder(session, target_hour_local=20)` — у юзера 20:xx локального времени.
- Каждому: `send_message(chat_id=user.tg_user_id, text=<текст>, reply_markup={"inline_keyboard": [[{"text": "Попал ✓", "callback_data": f"fb:acc:{yesterday}:3"}, {"text": "Частично ~", "callback_data": f"fb:acc:{yesterday}:2"}, {"text": "Мимо ×", "callback_data": f"fb:acc:{yesterday}:1"}]]})`.
- Текст (канон, одна строка в коде): `Как прошёл твой день? Вчерашний разбор — совпал с реальностью?`
- Между отправками `await asyncio.sleep(0.1)`, кап на прогон 500 юзеров. Ошибку по одному юзеру логировать и продолжать.
- События: `feedback.reminder_sent` (payload {"count": n}), при skipped — `feedback.broadcast_skipped`. Оба события добавить во все ТРИ реестра (`grace/canon/observability.xml` §8.5, `apps/api/app/core/logging_events.py`, `lib/log/events.gen.ts`; owner="W-FEEDBACK").

### 5. callback_query в webhook — `apps/api/app/api/telegram_webhook.py`

- Новая ветка: если `update.get("callback_query")` — парсить `data` по формату `fb:acc:YYYY-MM-DD:N` (N ∈ 1..3). Невалидный формат → ack `{}` (200).
- Валидный: найти user по `callback_query["from"]["id"]` (tg_user_id); нет юзера → ack `{}`. Есть — `FeedbackService.upsert(user.id, date, accuracy, source="tg_bot")`, событие `feedback.received` (payload {"accuracy": N, "source": "tg_bot"} — добавить в реестры).
- Ответ: Bot API method `answerCallbackQuery` с `callback_query_id` и `text`: `Записал ✨` (Telegram исполнит, как с sendMessage).
- Модуль перестаёт быть stateless: добавить `AsyncSession` через `Depends(get_session)` — **обновить GRACE module contract** (owns/dependencies/invariants) под AGENTS.md.

## Подводные камни

- callback_data ≤ 64 байт — наш формат `fb:acc:2026-07-23:3` = 18 байт, ок.
- `answerCallbackQuery` НЕ требует outbound-вызова — возвращаем как method JSON из webhook (как sendMessage).
- Не отправлять напоминание юзерам без таймзоны (пропускать, не дефолтить молча).
- В webhook нельзя тянуть `httpx` — только БД + method JSON.
- НЕ коммитить. НЕ трогать orchestrator, systemd (timer поставит архитектор на rollout). НЕ менять existing evening_checkins логику.
