# 00_TZ — Synastry Screen Redesign: «Три динамики» вместо простыни аспектов

Дата: 2026-08-01
Статус: draft для утверждения владельцем. Визуальный референс — `wireframe/` рядом с этим файлом (HTML-макет + PNG, снятые с него).
Нормативные входы: AGENTS.md (UI Semantic/Test Contract, GRACE), `app/globals.css` (токены), `components/today-convergence/*` (образец стиля), `/opt/deep-calm/content/STYLE.md` (анти-нейрослоп, дистиллирован в §11), `/tmp`-макет заказчика от 2026-08-01 (3-экранный wireframe, разобран и учтён).

## 1. Цель и принципы

Текущий экран синастрии устроен «астрология-first»: hero → скор-панель → колесо + список аспектов → наложение домов → «человеческий перевод» (пятым экраном, ниже двух-трёх скроллов). Пользователь видит тьму аспектов раньше, чем смысл.

Новый экран инвертирует пирамиду: **смысл и узнавание наверху, астрология — слой доказательства по запросу**.

Принципы:

1. **Три динамики, не 17 аспектов.** Экран показывает ровно три линии: сила / внимание / потенциал. Полный список аспектов живёт в свёрнутом техническом слое.
2. **Сцена — крючок.** Карточка динамики открывается узнаваемой сценой из жизни, а не аспектом. Цель реакции: «вау, это про нас».
3. **Фидбек на каждой динамике** («похоже на нас / не про нас») вместо одного reality-check блока внизу.
4. **Одно действие** — конкретная фраза/ритуал на неделю.
5. **Астрология не выбрасывается, а отодвигается**: разбор каждой динамики заканчивается блоком «почему мы так говорим», полная карта и все аспекты доступны в техслое.
6. **Один экран + один шит.** Никаких многоэкранных табов: основной скролл + bottom sheet разбора + share sheet.

Опыт заказчика (макет `/tmp/synastry-screen-wireframes-preview.html`, 3 экрана: обзор/тема/почему) учтён: его содержание сохранено, но два уровня drill-down свёрнуты в один шит — в приложении уже есть паттерн `AspectDrilldownSheet`.

## 3. Контрактные оси экрана (источник правды для макетов и тестов)

| ось | значения | откуда |
|---|---|---|
| `screenState` | loading / ready / error | transport + generation pipeline |
| `generation` | pending / calculating / narrative_generating / ready / failed | `GET /status` (`SynastryGenerationRead`) |
| `precision` | exact / approximate | partner (неизвестное время рождения) |
| `access` | full / locked | `GET /capabilities` (can_calculate, credits) |

Ортогональность обязательна:

- `generation` — это staged loading-экран (существующий красивый прогресс «Сопоставили планеты → Рассчитываем аспекты → Готовим человеческий перевод»), НЕ error;
- `failed` — error-состояние с retry (refund кредита делает backend, `_fail_and_refund`);
- `precision=approximate` — плашка в hero «время рождения примерное», блок домов в техслое показывает оговорку (текущее поведение `SynastryHouseOverlays` сохраняется);
- `locked` — `Paywall compact` (как в Today), без рендера контента отчёта;
- polling `/status` каждые 2.5с до ready/failed — текущее поведение, сохраняется.

Экран показывает их все, кнопки «все сферы» НЕТ. Канонические 12 сфер (`today-formatters.tsx:39-52`) к синастрии отношения не имеют; расширение `SPHERE_DEFINITIONS` — отдельная задача, вне этого ТЗ.

### 4.1. Hero (карточка)

- Два аватара с наложением (инициалы), пилюля типа отношений (`getRelationLabel`), serif `Ты + {partnerName}`.
- Балл — компактный чип `78 / 100` (serif-цифра), НЕ отдельная 78px-панель. Старый `SynastryScorePanel` с панелью и счётчиками не используется.
- `precision=approximate` → под чипом строка-оговорка.

### 4.2. «Главное о вас» (lede)

- Источник данных: `verdict` (заголовок) + `summary` (абзац) — **поля уже есть** в отчёте, новых не нужно. `heroTitle/heroDescription` на новом экране не используются (§10).
- Карточка с рамкой 1.5px `--primary` — визуальный аналог `convergence-hero` («Что сошлось сегодня»).

### 4.3. Карточка динамики (×3, порядок фиксирован: сила → внимание → потенциал)

```text
[пилюля тона: Сила | Внимание | Потенциал]
[h3: короткий заголовок динамики]                    ≤ 42 chars (как translations.title сейчас)
[scene-box: hookScene — ОДНА сцена-зацепка]          ≤ 160 chars, bg --muted, radius 14
[«Похоже на нас»] [«Не про нас»]           [Подробнее →]
```

- Обе feedback-кнопки — чипы `aria-pressed`, выбор взаимоисключающий, повторный тап снимает выбор. Отправка — optimistic UI (текущий паттерн `handleFeedbackSelect`).
- «Подробнее →» открывает шит разбора (§6).
- Источник: новое поле `dynamics[]` в отчёте (§9). Каждая динамика привязана к конкретному `aspectId` — это же ссылка на proof и на drilldown-контент шита.

### 4.4. Действие недели (action card)

- `bg --secondary`, левый plum-бордер у цитаты. Содержит заголовок-инструкцию + фразу-скрипт в кавычках + строку привязки «Работает на динамику „…"».
- Источник: новое поле `action` в отчёте (§9). Действие всегда относится к динамике «внимание» (если она есть; иначе к потенциалу).

### 4.5. Сферы

- 4 бара (label + score), fill `--primary`, track `--muted`. Без раскрытий.

### 4.6. Техслой «Как это рассчитано» (аккордеон, по умолчанию свёрнут)

Содержимое (все блоки — существующие компоненты/данные):

1. **Колесо синастрии** (§7) — с подсветкой аспекта, если пришли из proof шита.
2. **Все аспекты** — полный список `SynastryAspectRow` (компонент сохраняется), клик → шит разбора (§6).
3. **Наложение домов** — `SynastryHouseOverlays` без изменений (включая approximate-оговорку).
4. **Как считается балл** — короткий статический текст (2–3 предложения, копирайт из §11).

`aria-expanded`/`aria-controls` обязательны (AGENTS.md UI contract).

## 8. Шаринг: ссылка с паролем и сроком жизни

Сейчас в backend инфраструктуры публичных ссылок НЕТ (проверено: ни таблиц, ни эндпоинтов; все роутеры за `require_session`). Ближайший образец — промо-кампании (`PromoCampaign`, models.py:1367): хэш секрета + окно жизни + лимит использований. Проектируем по тому же паттерну.

### 8.1. UX (владелец отчёта)

1. Тап ↗ в topbar → **share sheet**: поле «Пароль для ссылки» (4–16 символов, обязателен), выбор срока «24 часа / 7 дней / 30 дней» (default 7), кнопка «Создать ссылку».
2. После создания: готовый текст + кнопка «Поделиться» → `https://t.me/share/url?url=…&text=…` через `openTelegramLink` (паттерн `use-share-invite.ts`), плюс «Скопировать».
3. В том же шите — список активных ссылок (срок, просмотры, «Отозвать»).

Текст шаринга (ToV §11): «Считает нашу с тобой совместимость — и попадает пугающе точно. Глянь: {url}. Пароль: пришлю отдельно». Пароль НЕ подставляется в текст — отдельным сообщением (в листе подсказка об этом).

### 8.2. Публичная страница получателя

Маршрут `/shared/synastry/[token]` (Next.js page, БЕЗ сессии):

- `data-state=locked`: форма пароля (label, `aria-invalid`, `aria-describedby` с текстом ошибки; не placeholder-as-label).
- Успех → `data-state=ready`: **read-only проекция обзора** — hero (имена, тип отношений, балл), «главное о вас», три динамики (пилюля, заголовок, hookScene). БЕЗ: дат/времени/города рождения партнёра, колеса, аспектов, домов, действий, фидбека, шитов. Техслой не отдаётся вообще (нет данных в payload, не «скрыт CSS»).
- Истёк/отозван → `data-state=expired`: «Ссылка больше не действует». Не различать 404/410/неверный токен (anti-enumeration).
- Подвал: CTA «Хочешь так про свою пару?» → ссылка на бота.

### 8.3. API и БД

Новая таблица `synastry_share_links`: `id` uuid, `report_id` fk, `owner_id` fk, `token_hash` (sha256, unique; raw token — `secrets.token_urlsafe(32)`, показывается один раз), `password_hash` (тот же hasher, что в auth), `expires_at`, `created_at`, `revoked_at` nullable, `view_count` int, `failed_attempts` int (сброс при успехе).

Эндпоинты (новый роутер `api/synastry_share.py`, owner-часть за `require_session`):

- `POST /api/synastry/{partner_id}/share` `{password, ttlHours: 24|168|720}` → `{token, url, expiresAt}`. Лимит: ≤ 5 активных ссылок на отчёт.
- `GET /api/synastry/{partner_id}/share` → список активных (без token/password).
- `DELETE /api/synastry/{partner_id}/share/{link_id}` → revoke (`revoked_at`).
- Публичные (без сессии, отдельный prefix `/api/shared`):
  - `POST /api/shared/synastry/{token}/unlock` `{password}` → `{viewerToken, expiresAt}` (JWT/подписанный токен на 30 мин, scope=link id). Rate limit: 5 попыток/мин на IP+token; после 10 failed_attempts подряд — временная блокировка ссылки на 1 час.
  - `GET /api/shared/synastry/{token}?viewerToken=…` → shared projection `{partnerName, relationType, score, status, verdict, summary, dynamics[3]}` (только эти поля; birth-данные, аспекты, дома, сферы НЕ сериализуются).
  - Оба: невалидный/истёкший токен → единый 404.

Alembic-миграция + модель в `db/models.py` рядом с `SynastryFeedback`. Логирование через `log_event` (новые события `synastry.share_created`, `synastry.share_revoked`, `synastry.share_unlock_failed`, `synastry.share_viewed` — сначала в `logging_events.py`, потом в код; без PII: только id и счётчики).

## 9. Контракты: что меняем

### 9.1. Backend (`apps/api/app/schemas/synastry.py`, роутер, LLM-слой)

Добавляем в `SynastryReport`:

```python
class SynastryDynamic(CamelModel):
    kind: Literal["strength", "attention", "potential"]
    title: str            # ≤ 42 chars
    hook_scene: str       # ≤ 160 chars, сцена-зацепка
    aspect_id: str        # привязка к aspects[] → drilldown шита

class SynastryAction(CamelModel):
    title: str            # ≤ 80, что сделать
    phrase: str           # ≤ 200, фраза-скрипт
    dynamic_kind: Literal["strength", "attention", "potential"]

# в SynastryReport:
dynamics: list[SynastryDynamic]  # ровно 3: strength, attention, potential (если аспектов категории нет — валидный fallback по ранжиру scoring'а)
action: SynastryAction | None    # null при narrative failure (UI тогда прячет блок)
```

Фидбек по динамикам:

- `SynastryFeedbackWrite`: `value` + **новое** `subject: str = "report"` (значения: `"report"`, `"strength"`, `"attention"`, `"potential"`).
- `SynastryFeedback` (models.py:1685): + колонка `subject` (default `"report"`); unique-индекс `(user_id, report_id)` → `(user_id, report_id, subject)`. Миграция: существующие строки получают `subject="report"`.
- `SynastryReport.user_feedback` → `feedback: dict[str, str]` (subject → value). Поле `userFeedback` во фронт-типе — заменить.

## 11. Tone of Voice (LLM-промпт + UI-копирайт)

База: `/opt/deep-calm/content/STYLE.md` (анти-нейрослоп). Применяется к **всем** генерируемым текстам (dynamics, action, lede, scenes, repairs, sphere descriptions, share-тексты) и к нашему UI-копирайту. Внедрение: расширить `SYNASTRY_SYSTEM_PROMPT` и `BANNED_PHRASES` в `apps/api/app/services/synastry_llm.py:84-161`, добавить проверки в `validate_llm_output`/`validate_drilldown_output`.

### 11.1. Стоп-листы (добавить в `BANNED_PHRASES` / валидаторы)

- Зачины: «в современном мире», «не секрет, что», «важно отметить», «давайте разберёмся».
- Канцелярит: «является», «данный», «осуществляем», «позволяет», «способствует», «в рамках».
- Усилители-паразиты: «ключевой», «значительный», «по-настоящему», «активно».
- Формулы: «не просто X, а Y», «не только X, но и Y»; вопрос с самоответом («Почему так? Всё просто.»).
- Трёхчлены («легко, быстро и надёжно»), парные эпитеты-клише («тёплый и уютный»), парцелляция ради драмы («Близость. Доверие. Страсть.»).
- Цепочки родительного падежа 3+ подряд.
- Эмодзи — 0. Восклицательный знак — максимум один на весь отчёт, лучше ноль.

### 11.2. Астро-специфика (дополнение к STYLE.md)

- **Анти-Барнум**: каждая сцена/hookScene обязана следовать из КОНКРЕТНОГО аспекта (в промпт передаём planet meanings, знаки, дома; валидатор: сцена без конкретной детали поведения — reject). Проверка из STYLE.md: «убрал прилагательное — потерял информацию? Нет → удалить».
- Запрет фатализма и предсказаний: «всегда», «никогда», «обречены», «суждено», «точно будет» (частично уже в `BANNED_PHRASES` — расширить).
- Запрет технических префиксов и сырого жаргона в текстах: `Transit_`, `Natal_`, `orb`, «квадратура» в пользовательском тексте (только в proof-блоке — «квадрат» допустим). **Закрывает известный баг №1 из AGENTS.md**: в новом UI сырые `signal.planet` не показываются нигде; `TopFlag`-подобные строки формируются только из локализованных подписей.
- Без эзотерического пафоса («вселенная шепчет», «звёзды благословляют») — как в текущем системном промпте, сохранить.
- Осторожность формулировок (уже в системном промпте: «может», «склонен») — сохранить, но не превращать в воду: одно осторожное слово на мысль, не три.

### 11.3. Что писать вместо (позитивные правила)

1. Начинать со сцены или факта, не с объявления важности.
2. Конкретика вместо оценок: не «глубокая связь», а «замечаете настроение друг друга по первому сообщению».
3. Живые глаголы: «спор разгорается», а не «происходит эскалация конфликта».
4. Ритм: чередовать длинные и короткие предложения.
5. Одна карточка — одна мысль — один шаг пользователя.
6. CTA один, с ценой шага: «скажи эту фразу до спора», а не три повеления.
7. Человеческие маркеры: конкретная деталь/ситуация минимум в каждой сцене; шероховатость из жизни лучше гладкой общности.
8. Обращение: «ты» к пользователю, «вы» о паре. «Партнёр» без имени в LLM-текстах (инвариант PII `synastry_llm.py:18` сохраняется); имя партнёра — только в UI-chrome (hero, topbar). См. §12, D1.
9. Длины (валидатор): lede-абзац ≤ 350, hookScene ≤ 160, совет ≤ 160, action.phrase ≤ 200, заголовок динамики ≤ 42.

### 11.4. Пример (было → стало)

Было: «Ваши отношения являются уникальным союзом, который позволяет не только расти, но и развиваться! Важно отметить ключевую роль взаимопонимания.»

Стало: «Вы перебиваете друг друга с середины фразы — и обоим всё равно понятно, о чём речь.»

## 12. Открытые решения (на владельца)

- **D1. Имя партнёра в сценах.** Сейчас инвариант: PII в промпт не включается, тексты говорят «партнёр». В макете — «Ирина», это сильнее для «вау, это про нас». Вариант без передачи имени в LLM: placeholder-замена на фронте (`{Партнёр}` → имя) — ломается на падежах. Рекомендация: v1 без имени в сценах (имя в chrome: «Ты + Ирина», «Меркурий Ирины» в proof — proof собирается детерминированно, там подстановка безопасна).
- **D2. Контент shared-страницы** (§8.2): рекомендация — обзор без техслоя и birth-данных. Утвердить.
- **D3. Шаринг и доступ**: доступно только при full access (платный отчёт)? Рекомендация: да — это виральный крючок платной фичи.
- **D4. Персонализация «не про нас»**: v2-возможность — при отрицательном фидбеке показывать следующую динамику по ранжиру (нужно хранить запасные кандидаты в `deterministic_payload_json`). В v1 — только запись сигнала.
