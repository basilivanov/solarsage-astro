## 1. Цель, принципы и не-цели

Цель — перевести detail screen с «астрология-first» на **смысл-first**: hero → lede → три динамики → одно действие → сферы → доказательный техслой. Полный список аспектов и существующий drilldown остаются доступны по запросу.

Принципы:

1. Три семантические линии: сила / внимание / потенциал.
2. Каждая карточка содержит одну наблюдаемую сцену и ссылку на конкретный aspect ID.
3. Фидбек живёт на динамике и не меняет текст в v1.
4. Одно действие на неделю, с явной привязкой к dynamic kind.
5. Тон не кодируется только цветом.
6. Один основной скролл и один drilldown sheet; share sheet появляется только после отдельного security-gate.
7. Backend остаётся владельцем расчёта, ранжирования, версий и доступности контента; frontend не «додумывает» отсутствующие dynamics.

Не-цели core-release:

- новый расчёт астрологии, новые 12 сфер или изменение sidecar;
- monetization/paywall для просмотра уже созданного отчёта;
- публичный sharing;
- удаление legacy DB/fields;
- изменение `/aspect/{aspect}` payload без отдельной необходимости.

## 3. Состояния и API/UI state machine

### 3.1. Оси

| attribute | enum | источник / смысл |
|---|---|---|
| `data-screen-state` | `loading \| ready \| error` | transport + terminal pipeline |
| `data-generation` | `pending \| calculating \| narrative_generating \| ready \| failed` | status endpoint; отсутствует только пока status ещё не получен |
| `data-precision` | `exact \| approximate \| unknown` | partner profile; `unknown` не маскировать под exact |
| `data-content-state` | `ready \| unavailable` | dynamics/action availability |
| `data-report-schema-version` | `synastry/v1 \| synastry/v2` | сервер, для диагностики/mixed rollout |
| `data-error-kind` | `transport \| generation_failed \| not_ready \| contract` | стабильный error code, не LLM-текст |

`data-access` и `locked` **не входят** в core detail: текущий capabilities endpoint всегда возвращает unlocked и не является entitlement. Paywall — отдельная спецификация.

### 3.2. Переходы

1. Первым запросом UI получает status/current report; GET report не считается доказательством ready, пока `state=ready` и payload проходит schema validation.
2. `pending/calculating/narrative_generating` показывают staged loading с `role=status`, `aria-busy=true`.
3. Polling — 2.5 s, deadline 90 s (конфигурируемый тестом), затем `data-error-kind=not_ready` с CTA «Обновить». Таймер очищается при unmount.
4. `generation_failed` — terminal error: показываем код/человеческое сообщение, факт refund, «Назад» и «Обновить». Текст «Попробуйте ещё раз» не обещает retry endpoint, которого нет.
5. Transport/contract error — отдельное alert-состояние с reload; не смешивать с refund.
6. `ready` допускает `contentState=unavailable` (технический score/aspects доступны, narrative dynamics нет).

### 3.3. Readiness invariant

`GET /api/synastry/{partner_id}` возвращает:

- `200` только для current report с `state=ready` и валидной projection;
- typed `409 REPORT_NOT_READY`/`202` (выбрать один статус и зафиксировать в OpenAPI) для pending;
- typed terminal error для failed;
- `404` только если owner/partner/report действительно отсутствует.

Нельзя возвращать 200 с placeholder «Отчёт формируется». Status и report должны ссылаться на один `reportId`.

## 6. Backend/domain-контракт v2

### 6.1. Wire SoT и генерация

Редактируется только Pydantic в `apps/api/app/schemas/*`. Synastry root-модели добавляются в `PUBLIC_CONTRACT_ROOTS` **в алфавитном порядке**, затем запускаются:

```bash
pnpm contracts:generate
pnpm contracts:check
```

Frontend импортирует generated types/Zod из `packages/contracts`; `lib/api/synastry.ts` использует `instrumentedFetch` + runtime response contract. Ручные интерфейсы разрешены только как внутренние view-model после parse.

### 6.2. Модели и invariants

Нормативная форма (CamelModel/Pydantic `extra="forbid"`):

```python
class SynastryDynamic(CamelModel):
    kind: Literal["strength", "attention", "potential"]
    title: constr(strip_whitespace=True, min_length=1, max_length=42)
    hook_scene: constr(strip_whitespace=True, min_length=1, max_length=160)
    aspect_id: constr(strip_whitespace=True, min_length=1, max_length=120)

class SynastryAction(CamelModel):
    title: constr(strip_whitespace=True, min_length=1, max_length=80)
    phrase: constr(strip_whitespace=True, min_length=1, max_length=200)
    dynamic_kind: Literal["strength", "attention", "potential"]
```

В `SynastryReport` добавляются:

- `report_schema_version: Literal["synastry/v1", "synastry/v2"]`;
- `content_state: Literal["ready", "unavailable"]`;
- `dynamics: list[SynastryDynamic]` с `min_length=0, max_length=3`;
- `action: SynastryAction | None`;
- `feedback: dict[DynamicKind, DynamicFeedbackValue | None]`.

Инварианты сервиса (проверяются до сериализации и в API tests):

1. `content_state=ready` ⇒ ровно три dynamics, уникальные kinds в фиксированном порядке, каждый `aspect_id` существует в `aspects[]` и distinct, `action` не null и его kind существует.
2. `content_state=unavailable` ⇒ `dynamics=[]`, `action=null`; score/aspects/spheres могут быть доступны.
3. LLM не выбирает IDs и порядок. Deterministic selector получает scored aspects, исключает `weight <= 0`/невалидные IDs и выбирает три distinct candidates по стабильному tie-break (`effective_weight`, confidence, original index). Для каждого kind сохраняется proof binding.
4. При 0/1/2 usable aspects не дублировать proof и не выдавать «ровно три» за счёт текста.
5. Length checks считают Unicode после NFKC/trim; control characters, bidi overrides и NUL отклоняются.
6. При approximate/unknown не использовать unreliable Moon/ASC/house evidence; UI показывает оговорку.

Текущие scoring semantics (включая score 50 для empty) не менять в этом срезе; добавить отдельные tests для empty/zero-weight.

### 6.3. Prompt и validation

`build_report_prompt` сейчас передаёт только aspects/overlays (`apps/api/app/services/synastry_llm.py:164-217`). Для v2 передавать curated, deterministic evidence для каждого выбранного ID: localized planet/aspect labels, sign/house только если reliable, orb/confidence и `aspect_id`. PII и имя партнёра в LLM не передавать.

LLM возвращает narrative text, но не IDs. Runtime validator проверяет только механически доказуемое: JSON shape, exact IDs/kinds, cardinality, lengths, Unicode, banned phrases, language/precision rules. «Анти-Барнум» и claim-binding дополнительно принимаются golden/offline rubric tests с human-reviewed fixtures; runtime не должен заявлять, что он доказал семантическую конкретность.

На narrative failure report переходит в `failed` и refund по существующему `_fail_and_refund`; «ready с action=null из-за LLM» запрещён, кроме честного `contentState=unavailable`.

### 6.4. Versioning, regeneration и mixed rollout

Ввести constants:

```text
CURRENT_ENGINE_VERSION
CURRENT_CALCULATION_VERSION
CURRENT_PROMPT_VERSION
CURRENT_REPORT_SCHEMA_VERSION = synastry/v2
```

Все `current` queries фильтруют полный tuple версий, а не только `created_at`. `report_schema_version` должен участвовать в DB uniqueness либо current selection должен быть доказан отдельным partial/index strategy; миграция и `alembic check` обязательны.

Добавить idempotent owner-scoped `ensure-current`/regenerate operation (точный route и response фиксируются в OpenAPI):

- повторный вызов для current report не создаёт строку и не списывает credit;
- upgrade v1 → v2 создаёт новый report с тем же partner, `SynastryCreditSpend` не создаётся;
- old feedback, share (если когда-нибудь включён) и audit history не теряются;
- concurrent calls сериализуются (`SELECT ... FOR UPDATE`/unique retry);
- старый in-flight report не запускается новым builder без явного policy: либо дожидается старого pipeline, либо помечается stale и безопасно пересоздаётся.

Backfill job работает пакетами, resumable/idempotent, с metrics/logs и dry-run. До включения v2 UI acceptance подтверждает: каждый активный partner либо имеет current-ready v2, либо имеет понятный current pending/failed path. Reconcile фильтрует version и не обрабатывает v1 строку новым v2 builder молча.

## 7. Feedback и durable signals

Существующий `SynastryFeedback` (`apps/api/app/db/models.py:1685-1720`) сохраняет один общий reality-check. Его не ломать и не превращать в multi-row subject table в core release.

Добавить additive `SynastryDynamicFeedback`:

```text
user_id, report_id, dynamic_kind, aspect_id, value, created_at, updated_at
UNIQUE(user_id, report_id, dynamic_kind)
```

`value: Literal["matches", "not_matches"]`. Контракт:

- `PUT /api/synastry/{partner_id}/reports/{report_id}/dynamics/{kind}/feedback` `{value, aspectId}` — idempotent upsert;
- `DELETE` того же resource — retract (повторный DELETE idempotent);
- server проверяет owner, `state=ready`, current report, kind и exact aspect binding;
- response содержит exact `reportId`, `kind`, `aspectId`, value/null, `updatedAt`;
- не разрешать route, который ищет «последний report» без exact ID.

Frontend optimistic flow: сохранить previous value, отправить PUT/DELETE, rollback при HTTP/transport/contract error, `role=alert`/toast с retry; не оставлять ложное selected state. `aria-pressed`, `aria-busy` и disabled отражают mutation.

Старый `report` feedback и dynamic feedback — разные quality signals; не объединять их в одну колонку. Migration roundtrip и rollback старого API обязательны.

## 8. Sharing — отдельный security/infra slice (не часть core acceptance)

Исходный sharing-раздел **не принимается**: token в path попадает в Nginx URI log, `failed_attempts` без `blocked_until` не реализует блокировку, password hasher отсутствует, а JWT не является текущим auth-паттерном.

Перед любой реализацией владелец утверждает отдельное `SHARE_TZ` с собственным premortem, threat model, migration/rollback и security acceptance. Минимальные обязательные требования:

1. Raw secret не находится в path/query/referrer: внешний URL использует fragment (`/shared/synastry#token=...`), unlock передаёт token/password в POST body на фиксированный endpoint; после unlock fragment очищается через history API.
2. Token — 32 random bytes, в DB только hash; viewer access — opaque server-side session, отдельная cookie с `HttpOnly; Secure; SameSite=Lax`, короткий TTL, GET каждый раз проверяет expiry/revocation. JWT/новую криптосхему не вводить без ADR.
3. Password — pinned memory-hard hasher (рекомендация Argon2id с параметрами и dependency lock), нормализация NFKC, 6–64 символа, запрет control/bidi; не использовать SHA-256 token hash как password hash.
4. Missing/expired/revoked/wrong password дают одинаковые status/body/timing envelope; для отсутствующего token выполняется dummy hash verify. `Cache-Control: no-store`, `X-Robots-Tag: noindex, nofollow`, no sitemap, safe validation route (аналог `SafePromoRoute`).
5. Rate limit защищается Nginx shared zone для public unlock + durable/global lock (`failed_attempts`, `blocked_until`) в DB; trusted proxy/IP policy документирована. In-memory per-user limiter недостаточен.
6. ≤5 active links enforced transactionally with PostgreSQL lock/unique retry. Revoke немедленно инвалидирует viewer sessions; partner soft-delete revokes links in same transaction.
7. Link binds immutable exact `report_id`/projection. Regeneration не подменяет содержимое старой ссылки молча; policy `freeze` или explicit rebind фиксируется в SHARE_TZ.
8. `view_count` имеет точную семантику (один раз на viewer session, не refresh/bot), cleanup/retention для links/sessions описаны.
9. Shared projection не содержит birth date/time/city, wheel, aspects, houses, spheres, actions или feedback. Owner display label должен быть отдельно privacy-reviewed; не обещать owner name, если его нет в payload.
10. Acceptance включает log/redaction test, URL/referrer test, brute-force/concurrency test, revoke-while-viewing test, expiry test, cache/indexing test и rollback floor. Core screen может быть принят без sharing control.

## 9. Аналитика и observability: что сохраняется после релиза

### 9.1. Фактическое состояние

Сейчас нет durable product-analytics store для synastry. После core-release сохраняются:

- в DB — текущие строки общего feedback и dynamic feedback (последнее состояние, не история);
- в backend stdout — pipeline/error events;
- в frontend — generic `instrumentedFetch`/error logs, если logging path включён;
- на self-hosted production — Docker JSON logs с ограниченной ротацией, не аналитическое хранилище.

Это означает: по текущему коду нельзя гарантировать funnel, retention, unique viewers, исторические feedback changes или долгосрочные conversion cohorts. Не называть stdout «сохранённой аналитикой».

### 9.2. Новые события

Если нужны продуктовые события, сначала открыть отдельный spec-only `W-CANON-LOG-EXT-N`: изменить `grace/canon/observability.xml §8.5`, сгенерировать Python/TS registry и пройти parity guard (`scripts/check_logging_guardrails.py:232-293`). Нельзя добавлять событие только в `logging_events.py`/`events.gen.ts`; это прямо запрещено `grace/development-plan.canon-log.patch.md:133`.

Минимальный core event set:

```text
synastry.detail_viewed
synastry.dynamic_opened
synastry.dynamic_feedback_changed
synastry.tech_details_opened
synastry.aspect_drilldown_opened
synastry.action_viewed
synastry.report_unavailable
```

Каждое событие содержит `slice`, `module`, `block`, `event`, `correlation_id`, hashed IDs/version/state/kind и не содержит raw initData, names, birth data, text LLM, cookies или secrets. `detail_viewed` — один раз на mounted report/session по определённому client dedupe; `dynamic_feedback_changed` — после server success, а не на optimistic click.

### 9.3. Что считать success

В acceptance фиксируются определения:

- view: ready report прошёл schema validation и отрисован;
- dynamic open: sheet действительно открылся;
- feedback success: PUT/DELETE получил 2xx и DB commit;
- tech open: accordion toggled;
- unavailable: typed content state, не generic network error.

Если владельцу нужна долговременная воронка, retention, cohort или export, это отдельная задача с выбранным sink/TTL/DPA. В core-TЗ это не подразумевается.

## 10. Tone of Voice и качество LLM

База — `/opt/deep-calm/content/STYLE.md` и существующий `SYNASTRY_SYSTEM_PROMPT`. Сохраняются: русский язык, «ты» к пользователю, «партнёр» вместо имени в LLM, отсутствие фатализма/диагнозов/измены, конкретное поведение вместо личности.

Стоп-лист: «в современном мире», «не секрет, что», «важно отметить», канцелярит, «не просто X, а Y», эмодзи, драматическая парцелляция, технические `Transit_`/`Natal_`/сырой `orb` в пользовательском тексте. Исключение для `notMeans` оформляется отдельным validator path, как в текущем `validate_drilldown_output` (`synastry_llm.py:294-315`).

Runtime validator проверяет форму, длины, banned terms, exact proof IDs, language/precision и JSON. Анти-Барнум принимается только golden/offline rubric:

- у каждой сцены есть наблюдаемая ситуация/действие;
- claim можно проследить к переданному evidence;
- нет fabricated sign/house/planet;
- при approximate нет time-dependent claim.

Длины нормализуются после NFKC: lede ≤350, dynamic title ≤42, hook ≤160, action title ≤80, phrase ≤200. Одно осторожное слово на мысль, не «вата».

## 12. Cleanup и rollback

Core rollout — expand/contract:

1. **Expand:** добавить v2 fields/projection, generated contracts, additive dynamic feedback table, compatibility readers, current-version constants and tests.
2. **Backfill/canary:** no-charge v2 regeneration and durable reconcile; old UI remains capable of reading v1.
3. **Cutover:** enable new UI only after backfill/readiness gate; preserve legacy fields/projection.
4. **Observe:** error/latency/feedback metrics and rollback drill.
5. **Cleanup (отдельный release):** удалить translations/hero legacy/old components only after rollback window, DB evidence and explicit migration review.

До cleanup не удалять `translations`, `heroTitle`, `heroDescription`, `userFeedback`, `scenario` или `advice`; v2 может не заполнять их для нового UI, но compatibility projection для старого image обязана быть валидной. Sharing нельзя включать в image, который не умеет его routes/revocation; rollback floor — share-compatible image после его запуска.

Partner deletion, report invalidation и future share revocation должны быть транзакционно согласованы. Migration имеет `upgrade → downgrade/rollback evidence` (где downgrade безопасен) и не удаляет user data.

## 15. Definition of Done

Core redesign is accepted only when all are true:

1. W0–W5 gates and verification-matrix rows are green.
2. Every ready report satisfies the v2 0-or-3 dynamics invariant; unavailable is honest and visible.
3. No current query or UI path silently mixes versions; upgrade is no-charge and idempotent.
4. API restart/reconcile, refund, migration rollback and feedback race have executable proofs.
5. Generated contracts/Zod and frontend DOM contract are in sync.
6. Detail visual specs are in CI for chromium/mobile; baselines do not mask redesigned content.
7. Real e2e/post-deploy smoke covers an actual authenticated report.
8. Analytics documentation states exactly what is durable and what is merely rotated logs; any new event passed canon extension.
9. Sharing is either absent from the release or accepted through SHARE_TZ. No `locked`/paywall claim is shipped without an entitlement contract.
10. Cleanup is not bundled with first cutover.

## 16. Зафиксированные решения и вопросы владельцу

Зафиксировано по умолчанию:

- имя партнёра не передаётся в LLM; оно только в UI chrome;
- `<3` usable proof aspects ⇒ `contentState=unavailable`, без дублирования;
- detail не имеет `access=locked`;
- feedback dynamic — `matches/not_matches`, exact report binding, PUT/DELETE;
- wire SoT — Pydantic + generated artifacts;
- wireframe не является baseline;
- sharing вынесен в отдельный security slice.

Требуется отдельное решение владельца до соответствующих волн:

1. Нужен ли durable analytics sink и какой retention/DPA (иначе остаются DB latest-state + rotated logs)?

3. Для SHARE_TZ: публичный owner label, password policy/Argon2id parameters, link freeze/rebind policy, viewer-session TTL и retention.
4. После rollout — дата/условия cleanup и допустимый rollback window.
