## 0. Authority и назначение

Этот документ — corrective delta к уже выпущенной синастрии. Он не повторяет
полное исходное ТЗ и не проектирует новую астрологическую фичу. Его задача —
закрыть подтверждённые разрывы между уже принятым контрактом, текущим кодом и
публичным пользовательским flow.

При конфликте требований действует следующий порядок:

1. `AGENTS.md` — runtime, production, UI semantic/test и GRACE canon.
2. Это ТЗ — corrective scope credit/billing и `planet.house`.
3. `2026-07-26_p0-feature-release-foundation/00_TZ.md` — rollout, auth,
   quarantine, build и deploy foundation; не дублируется здесь.
4. Исходные synastry-ТЗ — формула, privacy, state machine и UX-контракт.
5. Deep research report — продуктовая гипотеза, но не source of truth по
   текущему checkout.

Документ не разрешает production deploy, изменение live `/etc/solarsage/app.env`,
ручные SQL-правки production DB или денежные refund. Такие действия выполняет
владелец отдельно через канонический production path.

## 2. Наблюдаемые дефекты и последствия

### 2.1. `SYN-CREDIT-01`: некорректное списание общего кредита

`SynastryService.create_partner_and_report()` выбирает первую строку
`HoraryCredit` по `created_at` и вручную увеличивает `used_amount`.

В результате код:

- не использует принятый порядок `weekly-free → bonus по expiry → paid FIFO`;
- может выбрать истёкший bonus/weekly credit;
- не создаёт текущий weekly-free credit для активного подписчика;
- не использует `SELECT ... FOR UPDATE` и допускает конкурентное overspend;
- расходится с хораром и элективкой, хотя кошелёк общий;
- возвращает строковый 402 вместо стабильного domain error.

### 2.2. `SYN-CREDIT-02`: race при первом weekly-free касании

`HoraryCreditService.get_or_create_current_weekly_free()` делает check-then-insert
без безопасной обработки unique race. Два первых параллельных запроса могут
столкнуться на `uq_horary_credits_weekly_free` и дать 500.

### 2.3. `SYN-CREDIT-03`: refund не защищён от двух воркеров

`_fail_and_refund()` читает незарефанденный spend без row lock. При повторном
запуске/reconcile два воркера могут одновременно увидеть `refunded_at IS NULL`
и дважды уменьшить `used_amount`.

### 2.4. `SYN-BILLING-01`: продукт существует, но купить его нельзя

Текущий каталог содержит inactive slug `synastry` с ценой `39900` копеек;
миграция `0025_synastry_schema` добавляет ему quota `1`, но:

- `is_active=false`;
- `PurchaseStartRequest` не принимает ни `election_1`, ни synastry slug;
- `OneTimeProductSlug` не содержит synastry;
- frontend синастрии не имеет purchase sheet;
- fulfillment не пишет product/purchase attribution в `metadata_json` кредита.

Отдельно подтверждается уже описанный исходным ТЗ баг: frontend умеет отправить
`election_1`, но backend Literal отклоняет его как 422.

### 2.5. `SYN-UX-01`: нулевой баланс — тупик

`getSynastryCapabilities()` и `/quota` реализованы, но `SynastryScreen` сразу
загружает partners, всегда показывает Add CTA и не читает баланс. При 402 форма
остаётся с техническим текстом ошибки и без способа купить расчёт.

### 2.6. `NATAL-HOUSE-01`: тестовый sidecar contract не совпадает с реальным

Реальный `/v1/natal` возвращает `planets` без `house`, хотя API schema допускает
`house`, `NatalContextService` переносит `p.house`, а golden fixtures уже вручную
содержат дома. Из-за этого тесты подтверждают вымышленный boundary contract, а
production API повторно вычисляет дома в нескольких местах или получает `None`.

## 3. Цели и Definition of Outcome

После corrective-релиза:

1. Любая из трёх фич общего кошелька списывает только spendable credit и в одном
   и том же порядке.
2. Один credit невозможно потратить дважды конкурентными synastry request.
3. Повторный fail/reconcile возвращает credit не более одного раза.
4. Активный подписчик получает текущий weekly-free credit без предварительного
   захода в horary/election.
5. Пользователь без credit видит цену и рабочий путь покупки, а не тупиковую 402.
6. Оплаченный synastry product выдаёт ровно один общий credit только после
   verified YooKassa webhook; frontend считает покупку успешной только по
   локальному authenticated purchase-status.
7. Sidecar `/v1/natal` сам отдаёт дом каждой планеты; API fallback сохраняет
   совместимость на время rollout и никогда не придумывает `house=1` при
   отсутствии валидных cusp.
8. Старые cached natal contexts без домов не продолжают бесконечно обслуживаться.
9. Закрытые root/TopFlag исправления не регрессируют.

## 5. Непереговорные инварианты

### 5.1. Credits и деньги

- Источник истины по spendability — `HoraryCreditService`.
- Порядок: активный weekly-free, затем неистёкший bonus с ближайшим expiry,
  затем неистёкший paid FIFO.
- Credit selection, increment, partner/report/spend insert входят в одну DB
  transaction; внешние sidecar/LLM calls начинаются только после commit.
- `idempotency_key` обязателен для frontend create; один key + тот же payload
  возвращает исходный результат без нового spend; тот же key + другой payload
  отвечает 409 `IDEMPOTENCY_CONFLICT`.
- `SynastryCreditSpend` хранит `request_hash`/fingerprint payload (для legacy
  rows допустим nullable transitional default); одного `idempotency_key` без
  сравнения payload недостаточно для этого инварианта.
- Unique/dedup race переводится в стабильный 409 и не расходует credit.
- 402 всегда имеет JSON detail `{code, message}`, где code = `NO_CREDITS`.
- Refund блокирует spend row, ставит `refunded_at` и уменьшает credit ровно один
  раз в одной transaction.
- Provider webhook payload сам по себе ничего не выдаёт; действуют текущие
  verified-fetch и idempotent fulfillment invariants billing service.
- Цена и доступность читаются только из `/api/payment/products`, не хардкодятся
  во frontend.
- Canonical deployed product slug для hotfix — `synastry`. Не переименовывать в
  `synastry_1`: уже установленная миграция и catalog используют `synastry`.

### 5.2. Natal house contract

- Sidecar `Planet.house` — additive field, integer `1..12`.
- House вычисляется из фактического `house_system` и cusp текущей карты.
- Cusp interval — `[current_cusp, next_cusp)`, включая wrap `360° → 0°`.
- Normal/high-latitude fallback дают валидные дома для всех возвращённых планет.
- API во время rolling compatibility принимает старый ответ без `house`, один
  раз вычисляет fallback по cusp и не подставляет ложный `1`.
- Новые sidecar ответы проверяются boundary-тестом без fixture-enrichment.
- Natal entitlement остаётся привязанным к profile hash; cache-version bump не
  заставляет уже оплатившего пользователя покупать отчёт повторно.

### 5.3. Privacy, UI и логи

- В событиях нет имени партнёра, birth date/time/city/coordinates, raw Telegram
  initData, session данных и payment secrets.
- Допустимы internal `partner_id`, `report_id`, relation enum, precision enum,
  product slug, credit source и state.
- `data-testid` и state attributes — публичный UI contract; новые locked/error/
  purchase состояния покрываются тестами.
- Ошибка покупки/генерации показывается через `role="alert"`; ожидание оплаты и
  расчёта — `role="status"`/`aria-busy`.
- Ошибка логирования не ломает пользовательский flow.

## 7. Slice 1 — shared-credit correctness

### 7.1. Weekly-free race

В `HoraryCreditService.get_or_create_current_weekly_free()`:

- оставить current-week resolver единственным владельцем week boundaries;
- сделать insert concurrency-safe через savepoint/nested transaction;
- при unique conflict перечитать уже созданную строку;
- не делать rollback всей внешней business transaction;
- вернуть ровно одну canonical row обоим конкурентным callers.

Обязателен реальный Postgres concurrency test. SQLite unit не является
доказательством `FOR UPDATE`/unique-race semantics.

### 7.2. Synastry spend

В `SynastryService.create_partner_and_report()`:

1. Сначала проверить idempotency replay/conflict и active-partner dedup.
2. Лениво разрешить current weekly-free через shared service.
3. Взять `select_spendable_credit(user_id, now, lock=True)`.
4. Если credit отсутствует — 402 `NO_CREDITS`, никаких partner/report/spend rows.
5. Создать partner, report и `SynastryCreditSpend`, увеличить `used_amount`.
6. Commit один раз до постановки background task.
7. Поймать DB unique race и перевести его в 409 без частичного spend.

Для replay/conflict lookup используется уникальный `idempotency_key` вместе с
сохранённым `request_hash`; hash строится из нормализованных значимых полей
partner payload и не содержит raw персональные данные в логах. Migration для
`request_hash` должна быть backward-compatible с уже существующими spend rows.

Frontend генерирует `crypto.randomUUID()` один раз при открытии/первой отправке
формы и сохраняет key на retry до изменения payload. При изменении любого
значимого поля создаётся новый key.

### 7.3. Balance/capabilities

`GET /api/synastry/quota` и `GET /api/synastry/capabilities` не считают баланс
собственным SQL. Они используют один `HoraryCreditService.get_balance()` и одну
pure-функцию агрегации общего количества:

```text
credit_balance = int(weeklyFreeAvailable) + bonusCredits + paidCredits
```

Capabilities additive contract:

- `creditBalance: int >= 0`;
- `canPurchase: bool` из billing runtime (`YooKassa enabled`), не constant;
- `canCalculate: bool` учитывает credit и partner limit;
- `blockedReason: null | "no_credits" | "partner_limit"`.

Rollout state из foundation-ТЗ позже остаётся отдельной осью и не смешивается с
entitlement/credit. Если rollout registry уже реализован к моменту этого slice,
его deny имеет приоритет над credit state.

### 7.4. Refund

`_fail_and_refund()`:

- выбирает spend `FOR UPDATE`;
- при `refunded_at != null` делает no-op;
- блокирует credit row перед decrement;
- не допускает `used_amount < 0`;
- state fail + refund commit атомарны;
- эмитит `synastry.credit_refunded` ровно один раз.

Успешный spend эмитит `synastry.credit_spent` только после успешного commit.
События сначала добавляются в `grace/canon/observability.xml`, затем registry
генерируется штатным способом; generated files руками не редактировать.

## 9. Slice 3 — убрать zero-credit dead end

`SynastryScreen` сначала получает capabilities, затем partners при разрешённом
rollout. Уже созданные reports остаются читаемыми и при нулевом credit.

Обязательные состояния:

- screen root остаётся `data-testid="synastry-screen"`;
- quota block: `data-testid="synastry-credit-gate"`;
- `data-state="loading|ready|empty|error|locked"`;
- `empty` означает нулевой balance, а не отсутствие старых reports;
- при `creditBalance > 0` Add CTA открывает partner sheet;
- при `creditBalance == 0 && canPurchase` Add CTA открывает purchase sheet и
  явно показывает цену из catalog;
- при `creditBalance == 0 && !canPurchase` показывается честный unavailable
  state без неработающей кнопки;
- при partner limit CTA disabled с `aria-disabled` и объяснением;
- транспортная ошибка capabilities fail-closed для нового расчёта, но не
  удаляет локально уже показанные данные.

В `lib/api/synastry.ts` ввести typed `SynastryApiError` с `status`, `code` и
безопасным message. Нельзя превращать object detail в строку `[object Object]`.
`SynastryAddSheet` на `NO_CREDITS` вызывает purchase callback, сохраняет поля и
не показывает технический английский текст.

## 10. Slice 4 — sidecar-owned `planet.house`

### 10.1. Sidecar calculation

Создать небольшой pure helper, например
`apps/solarsage/solarsage/utils/houses.py::find_house()`:

- принимает longitude и cusp list (`cusp` или `longitude`);
- сортирует по cusp, поддерживает wrap-around;
- возвращает `None` на пустых/невалидных houses;
- возвращает только `1..12`;
- имеет GRACE contracts и owned tests.

В `NatalService.calculate_natal_chart()` после расчёта houses добавить `house`
в каждую копию planet position. Исходные ephemeris dict не мутировать вне
владельца chart assembly.

В sidecar `schemas/natal.py::Planet` добавить обязательное поле
`house: int = Field(ge=1, le=12)`. `/v1/natal` boundary test должен вызывать
реальный service path и проверять дом всех планет, а не подмешивать поле fixture.

### 10.2. API compatibility и cache

- `SolarSagePlanetPosition.house` временно оставить optional для rolling
  compatibility.
- В `NatalContextService` выбрать emitted `p.house`, а при его отсутствии —
  вычислить через API `find_house()` из validated cusp.
- В `NormalizationService._planets_in_houses()` также предпочесть emitted field
  и использовать одинаковый fallback; убрать `or 1`.
- Если house определить нельзя, не создавать ложный `planet_in_house` signal.
- После rollout bump `CALCULATION_VERSION` natal context, чтобы contexts с
  `house=null` не попадали в cache hit.
- Regression test доказывает, что существующий natal purchase по неизменному
  profile hash остаётся entitlement после cache-version bump.

API fallback удаляется только отдельным будущим cleanup после подтверждения,
что все production sidecar images отдают новый contract.

| `synastry.purchase_shown` | purchase sheet ready | `product_slug` |
| `synastry.purchase_started` | до billing POST | `product_slug` |
| `synastry.partner_submit_failed` | domain/transport failure | `error_code`, `precision`, `relation_type` |

Generic `billing.purchase_started/fulfilled` остаются source of truth для денег;
synastry events нужны для product funnel и не заменяют billing audit trail.

Каждый backend log получает `slice`, `module`, `block`, `correlation_id` через
существующий logging context. Frontend использует `logEvent`/instrumented fetch.

## 15. Rollout и rollback

### Release A — correctness, product inactive

1. Выпустить credit concurrency/refund и sidecar `planet.house` changes.
2. Оставить paid product inactive.
3. Проверить dev real auth, weekly/paid/expired cases и natal cache rebuild.

### Release B — paid surface

1. Миграция `0026` и app image в одном orchestrated release.
2. Smoke `/api/payment/products`: один active `synastry`, цена/quota корректны.
3. Реальная минимальная YooKassa покупка владельцем.
4. Проверить purchase row, payment verification, ровно один credit и безопасные
   logs; затем выполнить synastry calculation этим credit.
5. Наблюдать 24 часа: 402 rate, duplicate spend, refund, stalled purchases,
   generation ready rate, Bugsink.

### Rollback

- Сначала деактивировать paid product штатным corrective config/migration path;
  не удалять purchases или credits.
- Feature kill switch — только через rollout registry из foundation-ТЗ, если он
  уже установлен.
- Не делать DB downgrade после реальных покупок без отдельного owner decision.
- Additive `planet.house` не требует отката consumer; API fallback сохраняется.
- Денежный refund выполняется владельцем вручную в YooKassa по runbook.
