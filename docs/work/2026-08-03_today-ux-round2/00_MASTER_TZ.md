## 57 ✅ Summary импульсов: заземление + валидация (оба фикса)

**Проблема (фактура):** `apps/api/app/services/today_narrative_service.py` отдаёт в промпт по импульсу только `kind/sphere/polarity/eventTime`; LLM сочиняет generic-текст, и ничто не ловит уход в чужую сферу/полярность (пример владельца: «Меркурий в гармонии с твоим Ураном · Документы · поддержка» получил summary «Встречи в сфере отношений могут стать более напряжёнными»).

**Делаем оба фикса:**
1. Grounding: в prompt input каждого блока (convergence/mainEvent/impulse) добавить детерминированный `title` (из 55B, напр. «Меркурий в гармонии с твоим Ураном») + краткие темы планет драйвера из канона (Меркурий — мысли, документы, контакты; Уран — новое, неожиданные повороты). Summary должен кратко объяснять, что за планеты и почему это про эту сферу.
2. Fail-closed валидация: summary/claim, содержащий словарь чужой сферы (словарь строится из labels 12 сфер) или polarity-антоним («напряж*» при supportive и т.п.), — reject → одна регенерация → иначе claim=null (honest pending). Покрыть тестами на уровне `narrative_sanitizer`/`today_narrative_service`.

## 58 🔶 Канон «Документы» — НЕ делать до решения владельца

**Простое объяснение проблемы.** Астрология считает по домам и планетам, а продукт показывает 12 человеческих «полочек» (Работа, Деньги, Документы…). Связывает их таблица соответствия — замороженный канон `grace/canon/today_convergence.v1.yml`. Сейчас в ней «Документы» записаны дважды:
- `thinking_speech_learning: [communication, study, documents]` — дома 3 и 9 (мысли, речь, учёба, ближние поездки), планеты Меркурий/Юпитер/Луна;
- `money_security_resources: [money, shopping, documents]` — дома 2 и 8 (деньги, ценности, ресурсы), планеты Венера/Юпитер/Сатурн.

Когда backend собирает факты для страницы «Документы», он берёт ОБЕ записи: дома {2,3,8,9} и планет {Меркурий, Юпитер, Луна, Венера, Сатурн} плюс все аспекты с ними. LLM получает кучу фактов про ценности/ресурсы и пишет про них — текст «уезжает» из документов в деньги/отношения. Дополнительно модель может додумывать (у владельца в тексте появился «седьмой дом во Льве», которого вообще нет во входных фактах) — промпт не запрещает ссылаться на дома вне списка.

**Открытый вопрос к владельцу:** что такое «Документы» в продукте?
- Вариант А: бумаги/заявления/админ → оставить только `thinking_speech_learning` (убрать из `money_security_resources`).
- Вариант Б: документы как юридические договоры/недвижимость → тогда логичны дома 7 (договоры) и 4/8; это другая правка канона.
- В любом варианте добавить fail-closed валидацию словаря сферы для натал-текстов (как в 57) и запрет домов вне факт-пака в промпте.

Правка канона = изменение frozen-артефакта → новая formula/canon-ревизия по процессу, миграция/перегенерация sphere narratives.

## 59 ✅ «Сейчас действует»: техника один раз, per-item — персонально, без шаблонов

**Проблема (фактура):** `components/today-convergence/period-technique-copy.ts` — статический словарь из 4 записей по технике; «Соляр: Венера» и «Соляр: 7 дом» показывают одинаковый generic-текст.

**Решение владельца:**
1. Техника объясняется ОДИН раз и коротко (что такое соляр: год от дня рождения до дня рождения, задаёт фон года; что такое фирдар: длинный период-управитель + короткий подпериод внутри него).
2. Каждый item — персональное объяснение под человека (не шаблон): что значит ИМЕННО его соляр Венеры / его 7 дом, поддержка это или работа, и во что это выкладывается. LLM, заземлённый на детерминированные факты периода (title, technique, даты, дом/планета, связанные натальные факты).
3. Синтез: одна строка/блок «фон твоего года» — как соляр + фирдар складываются вместе для этого человека.

Backend: расширить period items (`TodaySpherePeriodItem`) полем `summary` (LLM, claim-bound к fact ids) или отдельным period-narrative endpoint; frontend рендерит summary вместо статического словаря; статический словарь уходит в честный fallback «объяснение готовится».

## 63 ✅ Процесс прототипирования (принять как стандарт)

Проблема владельца: HTML-макеты и моки плохо переносятся в React (не 1:1, много правок при подключении API/контрактов).

**Решение — прототипировать сразу в живых компонентах через fixture-песочницу:**
1. Dev-only маршрут-песочница `/sandbox/<screen>?fixture=<name>`: рендерит НАСТОЯЩИЙ React-компонент с локальным JSON-фикстурным payload, без auth и без API (задел уже есть: `FixtureShell` в `app/(grace)/layout.tsx` + mock-visual harness).
2. Цикл итерации: `next dev` на :3000 (fast refresh ~1 сек) → правка компонента → скриншот/CF-tunnel владельцу → правки → апрув.
3. После апрува перенос = 0: прототип УЖЕ production-код с реальным Tailwind/шрифтами/токенами; остаётся подключить реальный контракт/API.
4. Sandbox активен только в dev-режиме (guard `NODE_ENV=development` или отдельный dev-host), в prod-сборке маршрут неактивен; фикстуры лежат в `__tests__/fixtures/` и переиспользуются тестами.

Первый кандидат на поток: 61 (иконки календаря), затем 62 и 60 (вид sheet).
