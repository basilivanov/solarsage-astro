# ТЗ: frontend diagnostic boundaries поверх канонического logging spine

Дата: 2026-07-24
Роль исполнителя: кодер в `tmux astro2`
Роль постановщика: архитектор/ревьюер

## 1. Цель

Закрыть структурными событиями основные диагностические границы браузерного
frontend без добавления Sentry-подобной параллельной системы:

- глобальные browser errors и unhandled promise rejections;
- React/Next render boundaries;
- network/HTTP/timeout/abort и invalid-response границы общего API wrapper;
- надёжная доставка батчей при временной недоступности log intake;
- privacy-safe fingerprint, deduplication и opt-in sampling.

Результат должен использовать существующие `lib/log/*`, канонический envelope,
closed event registry, redactor и `/api/_log` intake. Логгер никогда не должен
ломать пользовательский flow.

## 2. Найденное исходное состояние

1. `lib/log/index.ts` уже создаёт canonical envelope, но публичный `meta` не
   раскрывает существующие поля `error`, `http`, `operation_id`, `phase`.
2. `lib/api-fetch.ts` уже умеет correlation header и `ui.fetch_*`, но ни один
   product-callsite его не использует.
3. `app/layout.tsx` содержит inline `window.error`/`unhandledrejection` capture,
   отправляющий неканонические поля `timestamp/message/extra` и null
   `correlation_id`. Такой batch не соответствует `apps/api/app/api/_log.py` и
   не является рабочей LDD-границей.
4. `lib/log/shipper.ts` requeue-ит transient failures, но не ставит новый retry
   timer; retry фактически зависит от появления следующего события.
5. Реестры CLOSED ENUM живут одновременно в:
   - `grace/canon/observability.xml`;
   - `apps/api/app/core/logging_events.py`;
   - `lib/log/events.gen.ts`.
   Все три должны остаться идентичными.

## 3. Обязательный scope

### 3.1. Event registry

Добавить во все три реестра (owner `W-FRONTEND-OBSERVABILITY`) события:

```text
frontend.runtime_failed
frontend.render_failed
frontend.promise_rejected
frontend.api_request_failed
frontend.api_response_invalid
frontend.flow_failed
frontend.flow_abandoned
```

`frontend.flow_failed` и `frontend.flow_abandoned` в этом foundation-change
только открывают типизированный контракт для следующей волны flow
instrumentation. Не придумывать ложные flow events из каждого сетевого сбоя и
не размазывать flow tracking по компонентам в этой задаче.

Для error events payload описывает только безопасный контекст, например:

```text
route, operation, boundary, component_area, source, retryable,
reason_code, attempt, reset_attempted, contract_name, contract_version,
missing_fields, invalid_field_types, payload_shape_hash
```

Сама нормализованная ошибка должна находиться в top-level `error` envelope, а
HTTP context — в top-level `http`, не в бесформенном payload.

### 3.2. Расширить публичный logger API

Изменить `lib/log/index.ts`:

- выделить и экспортировать строгий `LogEventMeta`;
- сохранить существующие `level/msg/slice/module/block/duration_ms`;
- добавить `error`, `http`, `operation_id`, `phase`;
- добавить опциональный `sample_rate` в диапазоне `[0, 1]`;
- redaction должен применяться отдельно к `payload`, `error`, `http`, `msg`
  до console/ship;
- `error`/`fatal` нельзя отбрасывать sampling-ом;
- invalid `sample_rate` безопасно clamp-ить либо игнорировать, но не бросать;
- сохранить backward compatibility существующих вызовов и legacy `logger`.

`http` ограничить безопасными полями (`method`, `route_template`, `status`), не
принимать/логировать request/response headers и URL с query values.

`operation_id` — идентификатор логической операции, `correlation_id` остаётся
идентификатором end-to-end request chain. Не помещать correlation ID в payload.

Обновить module contract/map и реальные `emitted_logs` согласно AGENTS.md.

### 3.3. Privacy-safe error normalization

Создать `lib/log/capture-error.ts` с GRACE header/contracts и API примерно
следующей семантики (точные имена типов можно улучшить без смены контракта):

```ts
type FrontendErrorSource =
  | "caught"
  | "window.error"
  | "unhandledrejection"
  | "react-boundary"
  | "network"
  | "contract"

type StructuredFrontendError = {
  kind: string
  code?: string
  fingerprint: string
  stack_frames?: Array<{
    file: string
    function?: string
    line?: number
    column?: number
  }>
  source: FrontendErrorSource
  retryable?: boolean
}
```

Экспортировать `captureFrontendError(error: unknown, context)` и, при
необходимости, чистую `normalizeFrontendError` для unit tests.

Инварианты:

- не логировать `error.message`, raw stack или serialized Error/Promise reason;
- fingerprint строится синхронно и детерминированно из low-PII признаков:
  `kind`, безопасный `code`, несколько sanitised stack locations/functions;
- не включать raw message в fingerprint input: хэш низкоэнтропийного секрета
  не является redaction;
- stack frames: максимум 8, убрать query/hash, origin, webpack noise и
  абсолютные локальные пути; оставить безопасный relative/basename + line/col;
- non-Error rejection нормализуется к безопасному kind, без `String(reason)`;
- одинаковый fingerprint отправлять не более 3 раз за browser session/module
  lifetime; reset попытка boundary не должна случайно потеряться из-за dedup;
- любые ошибки normalization/logging swallowing/handled;
- пользовательские вопросы, props/state, API bodies, initData, tokens, PII,
  точные координаты, payment fields, prompt/LLM text не передавать.

### 3.4. Global browser capture

Создать client component
`components/telemetry/frontend-error-capture.tsx`:

- `useEffect` регистрирует `window.error` и `unhandledrejection`;
- cleanup удаляет ровно те же handlers;
- `window.error` вызывает `captureFrontendError` с
  `frontend.runtime_failed`, source `window.error`;
- rejection вызывает `frontend.promise_rejected`, source
  `unhandledrejection`;
- safe payload: `route: window.location.pathname`, source и retryable;
- meta: `level=error`, `slice=W-FRONTEND`,
  `module=M-FRONTEND-RUNTIME`, соответствующий block;
- компонент ничего не рендерит;
- не использовать прямой `fetch('/api/_log')` и не хранить raw errors в
  `window.__astroErrors`.

Подключить компонент один раз в `app/layout.tsx`. Полностью удалить старый
inline `dangerouslySetInnerHTML` crash capture. Обновить contract layout:
`emitted_logs` и dependencies должны соответствовать коду.

### 3.5. Next/React error boundaries

Создать:

- `app/error.tsx` — route-tree boundary;
- `app/global-error.tsx` — root/global boundary по контракту Next 16.

Оба файла — client components, принимают `error` и `reset`, в `useEffect`
пишут `frontend.render_failed` через `captureFrontendError`, source
`react-boundary`. Safe context:

```text
route (pathname), boundary, component_area, reset_attempted=false
```

Кнопка повторной попытки перед `reset()` пишет структурное событие с тем же
нормализованным top-level `error` и `reset_attempted=true`; этот explicit reset
event не должен быть подавлен fingerprint dedup. Никакого raw error text в UI
или логах.

UI contract обоих fallback:

- `role="alert"`;
- `data-testid="app-error-boundary"` / `global-error-boundary`;
- `data-state="error"`;
- реальная button с доступным русским именем `Попробовать снова`;
- `global-error.tsx` должен вернуть собственные `<html lang="ru"><body>...`
  согласно Next global-error contract;
- статичный нейтральный пользовательский текст, без `error.message`.

Не менять существующий presentation-компонент
`components/grace/ErrorBoundary.tsx` вне необходимой совместимости.

### 3.6. Instrumented network boundary

Создать `lib/log/instrumented-fetch.ts`. Существующий `lib/api-fetch.ts`
оставить backward-compatible facade либо перевести на новый implementation без
поломки его публичной сигнатуры.

Новый primary API должен требовать безопасные отдельные поля:

```ts
instrumentedFetch({
  operation: "today.load",
  routeTemplate: "GET /api/day/{date}",
  url,
  init,
  timeoutMs,
  attempt,
  responseContract?,
})
```

Обязательное поведение:

1. Не логировать `url`, body, headers, response body.
2. Проставлять `X-Correlation-Id`, сохраняя пользовательские headers.
3. Считать `X-Correlation-Id` из ответа и обновлять frontend context до
   success/failure log.
4. Сохранять старые `ui.fetch_started` / `ui.fetch_succeeded` как lifecycle
   события; success в prod использовать `sample_rate=0.2`, в dev/test — 1.
5. На HTTP/network/timeout/abort писать `frontend.api_request_failed` с:
   - payload: `operation`, `attempt`, `retryable`, `reason_code`;
   - top-level `http`: method, route_template, optional status;
   - top-level `duration_ms`, `operation_id`, `phase`;
   - top-level structured error с source `network`;
   - затем сохранять исходную fetch-семантику: HTTP Response возвращается,
     network/abort exception rethrow.
6. Отличать reason codes `http`, `network`, `timeout`, `aborted`. External
   AbortSignal не терять. Timeout cleanup выполнять и на success, и на throw.
7. Не логировать обычный caller abort как fatal; event остаётся error/warn по
   обоснованной политике, но exception не swallowing.
8. Опциональная response-contract граница должна уметь проверить clone/parsed
   JSON, не потребляя оригинальный Response. При invalid JSON/schema:
   `frontend.api_response_invalid`, source `contract`, safe fields
   `contract_name/version`, capped `missing_fields`, `invalid_field_types`,
   `payload_shape_hash`. Hash строится из shape (`key -> type`), не values.
   Validator error rethrow/return behavior документировать; существующие API
   clients не должны молча принять invalid payload.

Не инструментировать сам `/api/_log`, иначе получится рекурсивный logging loop.

Мигрировать на `instrumentedFetch` browser-side product clients в `lib/api/*.ts`
и `lib/grace/api/client.ts`, где это безопасно механически. Минимально должны
быть реально покрыты цепочки:

- today/day и calendar;
- profile/onboarding и access;
- natal, horary, election;
- payment;
- checkin, geo и chat.

Для каждого callsite задать стабильные `operation` и `routeTemplate` без
динамических ID/query values. Сохранить status handling, credentials, body,
streaming, caller AbortSignal и публичные return/error contracts. Не менять
business behavior. Dev-only Next route handlers и shipper не мигрировать.

Для клиентов с уже существующими Zod schemas подключить response contract
validation без двойного потребления response. Для legacy typed-only clients
не писать фиктивный validator — оставить явный follow-up.

### 3.7. Shipper retry

Исправить `lib/log/shipper.ts`:

- transient: network error, `429`, `5xx` -> requeue с attempt counter;
- scheduled retry без нового пользовательского event;
- exponential backoff + bounded jitter;
- base около 1s, cap не больше 30s, максимум 5 повторов на batch/envelope;
- один активный retry timer, без timer storm;
- после исчерпания попыток batch безопасно drop-ается, приложение не падает;
- non-retryable `4xx` (кроме 429) не requeue;
- новый `enqueue` не сбрасывает более поздний/ранний retry некорректно;
- success очищает retry state и при наличии очереди планирует следующий batch;
- `beforeunload/pagehide` отправляет только canonical envelopes через beacon;
- никаких логов через этот же shipper о его собственных ошибках.

Backoff/jitter constants сделать тестируемыми без production API leakage. Не
использовать blocking sleep.

## 4. Privacy guardrails

Запрещено отправлять даже с redactor:

- user questions/messages, React props/state;
- Telegram initData, access/session/bot tokens, cookies;
- request/response bodies and headers;
- email, phone, name, exact coordinates;
- payment data;
- full prompt or LLM response;
- raw Error message/stack/rejection object.

Redactor — дополнительная страховка. Capture API по конструкции не должен
передавать эти данные.

## 5. GRACE requirements

Новые code files и существенные изменения должны иметь:

- `AI_HEADER`;
- `START_MODULE_CONTRACT` / `END_MODULE_CONTRACT`;
- `START_MODULE_MAP` / `END_MODULE_MAP`;
- `START_BLOCK` и function contracts для нетривиального public API;

- реальные `slice/module/block` во всех новых log calls.

Не импортировать несуществующий `grace_control`. Использовать только текущий
frontend logging spine.

## 7. Критерии приёмки

1. Старый неканонический inline crash sender отсутствует; оба browser global
   events идут через `captureFrontendError -> logEvent -> shipper`.
2. Route/global render failures имеют рабочий user fallback и structured error
   без raw error text.
3. Canon envelope реально использует top-level `error`, `http`,
   `operation_id`, `phase` с redaction.
4. Product API clients реально используют один wrapper, correlation header
   проходит туда/обратно, динамические URL/values не попадают в logs.
5. Contract failure отличим от HTTP failure и не содержит response payload.
6. Transient shipper failure сам ставит retry; есть bounded exponential
   backoff/jitter/max attempts.
7. Три event registry идентичны.
8. Logger/capture/shipper не бросают собственные ошибки в user flow.
9. Все новые/изменённые тесты зелёные, TypeScript и guardrails зелёные.
