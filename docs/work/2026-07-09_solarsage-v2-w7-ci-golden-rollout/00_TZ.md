## Required Architecture

### 1. Golden fixture layout

Create a dedicated W7 golden fixture area. Prefer the doc-15 paths unless existing test conventions make a small adapter cleaner:

```text
apps/api/tests/fixtures/golden/basil_2026_07_08_v1.json
apps/api/tests/fixtures/golden/basil_2026_07_08_v2.json
apps/api/tests/fixtures/golden/mercury_convergence_case_v2.json
apps/api/tests/fixtures/golden/antidominance_case_v2.json
```

Rules:

- Golden files must be deterministic JSON with sorted keys where practical.
- If a fixture is derived from Basil artifacts, scrub identity/profile data. Keep technical outputs only: date, status, scores, top signals, activation ids/techniques, V1/V2 diff summary.
- Synthetic edge-case fixtures are acceptable and preferred for convergence/anti-dominance if they avoid private data and isolate the behavior.
- Include metadata inside each fixture:
  - `fixture_id`;
  - `source`;
  - `generated_from_commit` or `baseline_commit`;
  - `tolerances`;
  - `canon_versions`;
  - `payload_version` / `scoring_version`.

### 2. Golden tests

Add focused deterministic tests:

```text
apps/api/tests/test_golden_basil_2026_07_08.py
apps/api/tests/test_golden_v2_convergence.py
```

Test requirements:

- Compare V1/V2 fixture data with tolerances from doc-15:
  - sphere score <= 0.02;
  - day_status exact;
  - top signal order exact unless a documented tie;
  - activation count exact;
  - aspect orb <= 0.02 where present;
  - Moon phase <= 0.5 percentage points where present.
- Validate every V2 status flip has non-empty activation evidence or an explicit `explained: true` diff reason.
- Validate convergence fixtures show independent technique families, not duplicate technique members from the same family.
- Validate anti-dominance fixtures prove one dominant sphere is capped or otherwise reported according to current V2 scoring contract.
- Do not call LLM.
- Do not require live sidecar unless the test is explicitly skipped with a clear reason. Prefer fixture-backed script paths.

### 5. Performance budget checks

Add a lightweight deterministic performance budget check that can run locally and in CI without external LLM.

Acceptable implementation:

```text
scripts/check_v2_performance_budgets.py
apps/api/tests/test_v2_performance_budgets.py
```

Requirements:

- Check deterministic local functions/fixture paths, not external LLM latency.
- Record budgets from doc-15:
  - `/v1/activation-layer` p95 target < 1500ms initially;
  - API `/day` fresh V2 p95 target < 5s without LLM;
  - cached `/day` no meaningful regression.
- If true endpoint p95 cannot be measured in CI, measure script/function fixture path and emit an explicit `mode: fixture`.
- Fail on clear budget regression; do not produce flaky timing tests. Use small sample counts and generous fixture-mode thresholds.

### 6. Rollout gates

Add a machine-checkable rollout gate file and checker, for example:

```text
docs/rollout/solarsage_v2_rollout_gates.md
scripts/check_solarsage_v2_rollout_gates.py
```

The checker must fail if a rollout readiness file claims V2 is ready but any required gate is missing:

- W0-W6 accept docs exist;
- dual-run evidence exists for internal fixture days;
- no unexplained status flips;
- every status flip has activation evidence;
- frontend old/new compatibility tests exist;
- rollback procedure is documented;
- performance budget check exists and passes.

This checker should not enable V2. It only validates readiness metadata.
