## 1. Goal

Build a complete, evidence-backed audit for `/calendar` before any new implementation work.

The target is not "roughly similar". The target for the later implementation wave is:

```text
3002/main /calendar must look and behave 1:1 with the 3001 mock-preview oracle,
while using real API/backend data and contracts.
```

This wave must produce the detailed map of what to port, what to keep, what to delete, and which backend/frontend contracts are missing. Do not edit product source code in this wave.

## 2. Non-Negotiable Architecture Constraints

- `3001` is the visual and interaction oracle for this audit.
- `3002` is current main/prod frontend and must remain real-data-backed.
- Production frontend must not import runtime mocks, demo APIs, static astrology, MSW, or client-side astrological calculations.
- Test-only Playwright route interception is allowed only under e2e/mock-visual or equivalent test files.
- Calendar facts must come from backend contracts and cached backend calculations.
- Frontend may format/present backend data, but must not invent astrological meaning.
- If an oracle UI element requires data that main/backend does not currently expose, mark it as `CONTRACT_GAP` with an exact proposed contract instead of hardcoding.
- Preserve Telegram auth and the real access model. Do not add a production bypass.
- Do not restart or replace systemd services.
- Do not push or deploy.
- Do not stage unrelated files: `.grace/`, `grace.db`, `skills/`, `docs/superpowers/`.

Audit `/calendar` completely. Do not only capture the first viewport.

At minimum cover:

- initial page load;
- loading state;
- error/unavailable state if reachable without unsafe changes;
- current month view;
- previous/next month navigation;
- selected day state;
- today state;
- days outside current month;
- locked/inaccessible days;
- subscription/access boundary days;

- day cell mood/status colors;

- segmented controls or tabs, including `Дни` and `Луна`;

- bottom tab navigation state;
- mobile Telegram viewport constraints;
- desktop/mobile width behavior;
- hover/focus/tap effects if visible;
- keyboard/accessibility semantics where applicable;
- data-testid / semantic test contract expected by tests.

## 7. Interaction Audit Requirements

For 3001 and 3002, compare behavior, not just screenshots:

- Tap previous month.
- Tap next month.
- Tap a normal available date.
- Tap today.
- Tap a locked/inaccessible date if visible.
- Tap a Sunday in the visible month.
- Switch `Дни` to `Луна` and back.
- Tap a lunar strip item if the oracle has this interaction.
- Tap selected-day CTA/open-day action.
- Check whether browser navigates to `/day/YYYY-MM-DD` or only updates selected state.
- Check whether focus rings or outlines appear after mouse/tap and whether oracle suppresses or preserves them.
- Check whether any expand/collapse control exists.

Record exact differences in the report.

## 8. Data And Contract Audit Requirements

Map the calendar UI to backend data.

For every visible oracle concept, classify it as one of:

- `HAS_REAL_CONTRACT`: current API already exposes the data needed.
- `FRONTEND_PRESENTATION_ONLY`: pure styling/layout can be ported without data changes.
- `CONTRACT_GAP`: backend/API does not expose the data honestly yet.
- `DEMO_ONLY_DO_NOT_PORT`: mock-preview behavior is demo-only and must not enter production.
- `REMOVE_FROM_MAIN`: current 3002 code is non-oracle or dead UI that should be deleted later.

For each `CONTRACT_GAP`, propose an exact contract shape:

- backend schema field;
- JSON path;
- type;
- nullable/optional behavior;
- caching/versioning implications;
- source of truth in backend service or sidecar;
- frontend adapter/type changes;
- tests needed.

Do not propose frontend-only fake data as a solution.
