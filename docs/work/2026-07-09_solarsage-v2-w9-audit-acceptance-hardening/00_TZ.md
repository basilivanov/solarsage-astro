# W9 TZ — SolarSage V2 Audit Acceptance Hardening

Status: DRAFT_FOR_REWORK
Date: 2026-07-09
Parent context: W8 final acceptance audit
Scope type: audit / acceptance / contract hardening
Target repo: `basilivanov/solarsage-astro`

## 0. Executive summary

W8 brought SolarSage V2 close to acceptance: activation contracts exist, Scoring V2 exists, TodayService can dual-run V1/V2, frontend V2 payload contracts exist, and a large acceptance evidence set was committed.

However, final acceptance is blocked by proof-quality gaps in the audit harness. The current documented acceptance can say that local tests and frozen artifacts passed, but it cannot yet prove a live end-to-end production V2 TodayPayload with the same rigor.

This W9 rework must make acceptance evidence honest, reproducible, and hard to misread:

- split live production audit from frozen deterministic baseline audit;
- ensure canonical activation artifacts come from the sidecar full V2 activation layer, not only from API fallback;
- make version identity explicit and consistent across cache keys, activation layer, payload meta, and audit artifacts;
- add edge-case protection for Feb 29 profections;
- add regression tests that fail if the audit silently substitutes baseline/fallback artifacts while claiming production proof;
- produce remote CI / GitHub Actions evidence for the final head.

Acceptance is not about adding more astrology features. Acceptance is about proving that the existing V2 path is what the docs say it is.

## 1. Current observed blockers

### 1.1 `make audit-day` default mode can use a frozen baseline instead of the real production payload

Current behavior:

- default audit mode requires `11_final_today_payload.json` to already exist;
- default audit mode does not call `TodayService.get_today_payload()` for the final payload;
- default audit mode uses the frozen baseline payload as `payload_json`;
- W8 acceptance text can therefore be read as proving production `final_today_payload.json`, while the default command may only be proving a baseline fixture.

This is a trust blocker. Frozen deterministic baseline mode is useful, but it must never be presented as a live production payload proof.

Required outcome:

- frozen mode and live mode must be separate commands, names, output metadata, and acceptance language;
- a command that claims live production proof must call `TodayService.get_today_payload()` and must write the resulting payload artifact.

### 1.2 `16_activation_layer.json` can be the local API fallback, not the full sidecar V2 activation layer

Current risk:

- API fallback `ActivationLayerService` builds only W2-style day-signal activation evidence, mainly transit-to-natal and transit planet-in-house;
- the full W3+ sidecar activation builder supports profection, firdar, returns, progressions, and eclipse windows;
- audit artifacts may save the API fallback layer as `16_activation_layer.json`, which makes the artifact weaker than the V2 product claim.

Required outcome:

- audit must fetch and validate the sidecar activation layer directly;
- `16_activation_layer.json` must represent the selected full V2 activation layer used for acceptance evidence;
- any local fallback layer must be explicitly named as fallback/debug and must not be confused with accepted sidecar proof.

### 1.3 Calculation/version identity is still partly legacy

Current risk:

- `TodayPayload.meta.calculation_version` may still be `1` even when V2 activation/scoring paths are used;
- sidecar `ActivationLayer.calculation_version` may still be `"1"`;
- cache identity uses calculation/scoring/frontend/canon fields, so vague version strings weaken cache invalidation and audit traceability.

Required outcome:

- V2 calculation identity must be explicit, for example `ss-calc-1.1.0`;
- V2 scoring identity must remain explicit, for example `ss-scoring-2.0`;
- `ActivationLayer.calculation_version`, `TodayPayload.meta.calculation_version`, audit artifacts, and cache key read/write must agree on the same version identity when they refer to the same calculation path.

### 1.4 No remote CI evidence for the final accepted head

Current risk:

- W8 acceptance records local command output, but the acceptance commit has no associated GitHub workflow run evidence;
- local proof is not enough for final acceptance of this size.

Required outcome:

- final W9 acceptance must include GitHub Actions / remote CI evidence, or explicitly mark CI as unavailable and not claim full remote acceptance;
- if CI cannot run automatically, add a manual workflow dispatch or document the exact manual remote run evidence.

### 1.5 Profection date boundary can crash on Feb 29 birth dates

Current risk:

- profection logic uses direct `date.replace(year=...)`;
- a Feb 29 birth date in a non-leap target year can raise `ValueError`;
- astrology user profiles can include Feb 29, so this must be handled before production acceptance.

Required outcome:

- introduce a safe year replacement helper with an explicit Feb 29 policy;
- add tests for annual and monthly profection on Feb 29 birth data.

## 2. Non-goals

W9 must not broaden product scope. Do not add new astrology techniques beyond already implemented W3/W4/V2 work.

Do not tune scoring formulas unless a failing test proves that a formula violates the existing canon.

Do not rewrite frontend UI design except where tests need stable selectors or labels for V2 proof.

Do not deploy as part of W9 unless a separate deploy TZ explicitly requests it.

Do not hide audit nondeterminism by deleting or overwriting evidence. If something is nondeterministic, label it as live sample and separate it from deterministic baseline artifacts.

## 3. Required implementation

## 3.1 Split audit modes and Makefile targets

### 3.1.1 Add explicit audit modes

Update `scripts/audit_today.py` to support explicit modes:

```bash
scripts/audit_today.py --mode live-production --user-id ... --date ... --out ...
scripts/audit_today.py --mode frozen-baseline --user-id ... --date ... --out ...
```

Backward-compatible aliases may exist, but hidden behavior must not.

Recommended aliases:

```bash
--live-llm-sample        # legacy alias for --mode live-production
--frozen-baseline        # alias for --mode frozen-baseline
```

Default behavior must be one of these two options:

Option A, preferred for safety:

- no `--mode` means fail fast with a clear error listing valid modes;
- Makefile targets always pass mode explicitly.

Option B, acceptable if team wants convenience:

- no `--mode` defaults to `live-production`;
- frozen mode must always require an explicit flag.

Do not keep current behavior where the default command silently uses the frozen payload.

### 3.1.2 Add Makefile targets

Add or update targets:

```make
.PHONY: audit-day-live audit-day-freeze audit-day

audit-day-live:
	apps/api/.venv/bin/python scripts/audit_today.py --mode live-production --user-id $(USER_ID) --date $(DATE) --out artifacts/audit/$(DATE)

audit-day-freeze:
	apps/api/.venv/bin/python scripts/audit_today.py --mode frozen-baseline --user-id $(USER_ID) --date $(DATE) --out artifacts/audit/$(DATE)

audit-day:
	@echo "ERROR: choose audit-day-live or audit-day-freeze explicitly."
	@exit 1
```

If keeping `audit-day` as a real command is required, it must call `audit-day-live`, not frozen mode.

### 3.1.3 Artifact source metadata

Every audit run must write:

```text
artifact_source.json
```

Required fields:

```json
{
  "mode": "live-production | frozen-baseline",
  "final_payload_source": "TodayService.get_today_payload | committed_baseline_fixture",
  "activation_layer_source": "sidecar | local_fallback | payload_v2 | unavailable",

```

In frozen mode, `final_payload_source` must explicitly be `committed_baseline_fixture`.

In live mode, `final_payload_source` must explicitly be `TodayService.get_today_payload`.

## 3.2 Live production payload audit

In `live-production` mode:

1. Load user/profile/access/natal/transits as today.
2. Invalidate TodayPayload cache before calling TodayService, unless an explicit `--allow-cache` flag is provided.
3. Call:

```python
TodayService(db).get_today_payload(
    user_id=user.id,
    target_date=target_date,
    access_state=access_state,
    skip_prefetch=True,
)
```

4. Write the returned payload to:

```text
debug/final_today_payload.json
11_final_today_payload.json
```

5. Normalize only inherently nondeterministic metadata for repeatable diff review, but do not hide the source:

- `meta.generated_at` may be normalized in a copy only if the raw payload is also preserved;
- recommended outputs:

```text
debug/final_today_payload.raw.json
debug/final_today_payload.normalized.json
11_final_today_payload.json
```

6. If live LLM text is generated, label the run as live/non-deterministic in `artifact_source.json`.

Live mode acceptance must prove the actual production TodayService path, not just reconstructed intermediates.

## 3.3 Frozen baseline audit

Frozen baseline mode remains useful for deterministic checks, but it must be honest.

In `frozen-baseline` mode:

1. Require existing `11_final_today_payload.json`.
2. Validate that baseline has at least:

```text
meta
headline
day_status
concrete_advice
why_this_happens
```

3. Use it only as a frozen payload fixture.
4. Write `artifact_source.json` with `final_payload_source=committed_baseline_fixture`.
5. Claims audit must say:

```text
This is a frozen baseline payload review. It is not a fresh TodayService production payload.
```

6. W8/W9 acceptance docs must not cite frozen mode as proof that current production payload still emits the same final user-facing content.

## 3.6 Feb 29 profection hardening

### 3.6.1 Add safe date helper

Introduce helper:

```python
def safe_replace_year(d: date, year: int, *, feb29_policy: Literal["feb28", "mar01"] = "feb28") -> date:
    try:
        return d.replace(year=year)
    except ValueError:
        if d.month == 2 and d.day == 29:
            if feb29_policy == "feb28":
                return date(year, 2, 28)
            if feb29_policy == "mar01":
                return date(year, 3, 1)
        raise
```

Use it anywhere profection logic currently uses `birth_local.replace(year=...)`.

Recommended default policy: `feb28`, unless the project canon explicitly requires `mar01`.

### 3.6.2 Required tests

Add tests for:

- annual profection for Feb 29 birth on non-leap target year;
- monthly profection for Feb 29 birth on non-leap target year;
- leap-year target still preserves Feb 29;
- annual year start is stable and documented for the chosen policy.

## 8. Risks and guardrails

### Risk: live LLM text is nondeterministic

Guardrail:

- live mode can be used for proof of path, not byte-for-byte golden text stability;
- preserve raw and normalized versions separately;
- frozen mode remains for deterministic baseline checks.

### Risk: sidecar unavailable in CI

Guardrail:

- unit-test sidecar artifact logic with mocked client;
- integration audit requiring real sidecar can be marked as local/remote environment dependent;
- acceptance must say which proof is mocked and which is live.

### Risk: audit starts mutating tracked artifacts unexpectedly

Guardrail:

- default commands must document whether they write tracked baseline files;
- live samples should preferably write under `artifacts/audit/<DATE>/live/<timestamp>/`;
- frozen canonical output should be stable and diff-clean.

### Risk: privacy leakage in golden fixtures

Guardrail:

- do not commit raw private profile details into golden fixtures unless already explicitly accepted;
- scrub or synthesize fixtures for tests;
- run privacy scans before acceptance.

### Risk: fallback hides sidecar outage

Guardrail:

- live-production + V2 enabled must fail loudly on sidecar activation failure;
- fallback requires explicit opt-in and must be reflected in `artifact_source.json`.
