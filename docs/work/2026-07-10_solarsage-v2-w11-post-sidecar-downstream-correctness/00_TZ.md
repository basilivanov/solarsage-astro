# W11 TZ — SolarSage V2 Post-Sidecar Downstream Correctness Audit

Status: DRAFT_FOR_IMPLEMENTATION
Date: 2026-07-10
Parent context: W10 final contract proof accepted
Scope type: post-sidecar correctness / scoring proof / payload and frontend traceability
Target repo: `basilivanov/solarsage-astro`

## 0. Executive summary

W8-W10 proved that SolarSage V2 wiring is structurally sound:

- V2 can run behind flags;
- `TodayPayload.v2` is non-null when V2 is selected;
- cache identity is consistent;
- sidecar activation ids can reach payload evidence;
- audit artifacts can distinguish live and frozen modes.

W11 is a different proof layer.

W11 does **not** verify sidecar astronomy. For this wave, the sidecar `ActivationLayer` is treated as a trusted boundary and source of truth.

W11 must prove that everything **after** sidecar is correct:

```text
sidecar ActivationLayer
  -> API ActivationLayerService validation
  -> ScoringV2Service sphere mapping
  -> activation contribution math
  -> convergence math
  -> dominance cap math
  -> V2 day status math
  -> TodayService selected payload
  -> TodayPayload.v2 evidence
  -> frontend fixture / UI renderability
```

In plain language: if sidecar gives us the right astrology, W11 proves that our API/frontend manipulations do not lose, distort, mis-map, or mis-score it.

## 1. Core question W11 must answer

Given a trusted sidecar `ActivationLayer`:

1. Did API keep exactly the same activation ids, or did it fall back/rebuild/lose something?
2. Did every active activation that can map to a sphere produce a scoring contribution?
3. Did every contribution go to the correct sphere according to canon?
4. Is every contribution amount mathematically correct?
5. Is convergence based on unique `technique_family`, not raw activation count?
6. Is dominance cap applied correctly and traceably?
7. Does V2 `day_status` include activation support/tension correctly?
8. Does `TodayPayload.v2.activationEvidence` preserve sidecar activation ids?
9. Does `TodayPayload.v2.scoreBreakdown` explain how activations affected final scores?
10. Can frontend fixtures render V2 evidence without losing the trace?

W11 must produce machine-readable artifacts that answer these questions.

## 2. Non-goals

Do not validate planetary positions, house cusps, lots, profections, firdars, returns, progressions, eclipses, or Swiss Ephemeris outputs.

Do not alter sidecar calculation logic.

Do not tune scoring formula weights unless a test proves the current code violates canon.

Do not redesign frontend UI.

Do not change V2 rollout flags or deploy.

Do not replace W10 audit. W11 adds a downstream correctness audit on top of W10.

## 3. Trusted boundary

For W11, this is the trusted input:

```text
ActivationLayer from sidecar endpoint /v1/activation-layer
```

W11 assumes:

- activation ids are meaningful;
- `target_type`, `target_key`, `technique`, `technique_family`, `strength`, `polarity`, `phase`, `orb`, and `evidence` are already astrologically valid;
- sidecar has already decided which activations exist for the target date.

W11 must not second-guess those astronomical decisions.

W11 must only prove that API/frontend downstream logic handles this trusted input correctly.

## 8. Independent downstream recalculation

W11 audit must not simply trust `ScoringV2Result`.

It must independently recalculate downstream expectations from:

- sidecar `ActivationLayer`;
- day signals;
- canon YAML files.

This recalculation may reuse simple shared data structures and schemas, but it must not call `ScoringV2Service.score_day()` for the expected values after actual result has been produced.

Recommended approach:

1. Call production `ScoringV2Service.score_day(...)` once to get actual result.
2. Independently recompute expected activation-to-sphere mapping in audit script.
3. Independently recompute contribution amounts.
4. Independently recompute convergence bonus.
5. Independently recompute dominance cap.
6. Independently recompute status breakdown.
7. Compare expected vs actual.

Avoid copying production helper functions if possible. The audit can read canon directly and implement small explicit reducers in the script.

## 9. Hard invariants

W11 must fail if any hard invariant is violated.

### 9.1 Sidecar preservation invariant

```text
set(sidecar.activations[].id) == set(api_activation_layer.activations[].id)
```

### 9.2 Active mapped activation contribution invariant

For every active activation with one or more mapped spheres:

```text
activation.id in scoring_v2_result.sphere_scores[*].contributions[source=activation].source_id
```

### 9.3 Contribution amount invariant

For every activation contribution:

```text
actual_amount == round(strength * family_weight * target_weight * polarity_modifier, 4)
```

Tolerance:

```text
<= 0.0001
```

### 9.4 Unmapped invariant

If active activation maps to no sphere:

```text
activation.id in scoring_v2_result.debug.unmapped_activations
```

If `--fail-on-unmapped=true`, audit fails even if debug contains it.

### 9.5 Convergence invariant

Convergence is by unique family only.

These cases must pass:

```text
transit + transit + transit => family_count=1 => bonus=0
transit + profection + firdar => family_count=3 => bonus according to canon
annual_profection + monthly_profection => family_count=1 => bonus=0
```

### 9.6 Cap invariant

If raw sphere score exceeds cap threshold:

```text
final_score == cap_value
dominance_capped == true
contributions includes source=cap
```

### 9.7 Payload evidence invariant

```text
set(sidecar.activations[].id) <= set(payload.v2.activationEvidence[].id)
```

For W11 preferred policy is equality, unless there is an explicit accepted filtering policy.

### 9.8 V2 payload invariant

If V2 scoring is selected:

```text
payload.meta.payload_version == today.v2
payload.v2 != null
payload.v2.scoreBreakdown != empty
payload.v2.activationEvidence != empty if sidecar activations exist
```
