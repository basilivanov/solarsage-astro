# ТЗ — post-deploy smoke gate для прода

Дата: 2026-07-23
Исполнитель: кодер в tmux astro2
Архитектор: ревью + запуск на проде (у кодера нет доступа к прод-хосту)

## 1. Контекст

Первый деплой в прод показал: зелёные тесты в CI ≠ рабочий прод (мёртвый LLM из-за geo-block, недоставленный Telegram webhook, сломанный offsite backup — всё прод-специфика). Нужен скрипт, который после каждого деплоя (и в любой момент) проверяет прод end-to-end и падает громко, если что-то не так.

Прод: `https://astro.vasiliy-ivanov.ru`, хост `2.26.20.80` (Ubuntu 22.04, bash 5.1, есть python3, docker, curl; **нет jq**). Секреты в `/etc/solarsage/app.env` (формат KEY=value). Репо на проде лежит в `/opt/solarsage-astro`. Контейнеры: `solarsage-api`, `solarsage-sidecar`, `solarsage-frontend`, `solarsage-db`. Sidecar health: `http://127.0.0.1:18091/v1/health` (есть поля ephemeris_artifact_id, ephemeris_manifest_sha256). API health: `https://astro.vasiliy-ivanov.ru/api/health` → JSON с `status` и `release_sha`. Дампы БД: `/var/backups/solarsage/db-*.dump`.

## 2. Что создать

Один файл: `scripts/deploy/prod-smoke.sh` (bash, с GRACE AI_HEADER по AGENTS.md — см. соседний scripts/deploy/prod-orchestrator.sh для стиля шапки). Назначение: запуск root'ом на прод-хосте; код выхода 0 только если ВСЕ проверки зелёные; в конце — сводка `PASS n/n` или `FAIL (список упавших проверок)`.

Режимы: `./prod-smoke.sh` — полный прогон; `./prod-smoke.sh --quick` — только инфраструктурные проверки (без auth/day); `./prod-smoke.sh --expected-sha <sha>` — сверить release_sha из /api/health с переданным (без флага — сверять с `active` из `/var/lib/solarsage/orchestrator/release-record`).

## 3. Проверки (порядок и содержание)

Инфраструктурные (host-only):

1. **containers**: `docker ps --format '{{.Names}} {{.Status}}'` — все 4 контейнера `solarsage-api|sidecar|frontend|db` существуют и Status содержит `healthy` (для db — `healthy` тоже). Учти: формат вывода docker — `Up X (healthy)`.
2. **sidecar**: `curl -sf --max-time 5 http://127.0.0.1:18091/v1/health` → 200 и JSON непустой.
3. **egress-openrouter**: `curl -s -o /dev/null -w %{http_code} --max-time 10 https://openrouter.ai/api/v1/models` → код 200 или 401 (оба значат «доступен»).
4. **egress-telegram**: то же к `https://api.telegram.org/` → код 302 или 200.
5. **egress-yookassa**: `https://api.yookassa.ru/` → код 404 или 401 (root path отдаёт 404 — это норма).
6. **backup-freshness**: новейший `/var/backups/solarsage/db-*.dump` моложе 48 часов (`find ... -mtime -2` или по имени файла — выбери надёжное; имя содержит UTC-метку `db-YYYYMMDDTHHMMSSZ.dump`).

Внешние (через публичный домен):

7. **frontend**: `curl -sf -o /dev/null --max-time 10 https://astro.vasiliy-ivanov.ru/` → 200.
8. **api-health**: `curl -sf --max-time 10 https://astro.vasiliy-ivanov.ru/api/health` → JSON, `status` == "ok"; если задан expected-sha — `release_sha` совпадает. JSON парсить через `python3 -c "import json,sys; ..."` (jq НЕТ на проде).
9. **webhook-fail-closed**: `POST https://astro.vasiliy-ivanov.ru/api/telegram/webhook` с JSON-телом `{"update_id":1}` БЕЗ заголовка секрета → ровно 403. С валидным `TELEGRAM_WEBHOOK_SECRET` из app.env (заголовок `X-Telegram-Bot-Api-Secret-Token`) и синтетическим /start-update → 200 и тело содержит `sendMessage`. Синтетический update: `{"update_id":900000001,"message":{"message_id":1,"from":{"id":1,"is_bot":false,"first_name":"Smoke"},"chat":{"id":1,"type":"private"},"date":1784900000,"text":"/start"}}` — chat_id фейковый, реальным юзерам ничего не улетит.

E2E (только полный режим):

10. **auth**: сгенерировать initData: `. /etc/solarsage/app.env && export TELEGRAM_BOT_TOKEN && python3 /opt/solarsage-astro/scripts/generate-telegram-test-initdata.py` — генератор печатает комментарии (`#...`), сам initData (строка начинается с `query_id=` или `user=`) и URL; брать строку, начинающуюся с `query_id=` или `user=`. Затем `POST /api/auth/telegram` с JSON `{"initData": "..."}` → 200, в ответе есть `userId`. Cookie из ответа сохранить (`curl -c jar`).
11. **profile**: `GET /api/profile` с cookie-jar → 200.

## 4. Правила скрипта

- `set -u` (НЕ `set -e` — нужно добежать до сводки), каждая проверка — функция `check_<name>`, печатает `PASS <name>` или `FAIL <name> <причина>`; счётчик падений; exit code = число упавших (cap 99).
- Каждый curl — с `--max-time` (скрипт не имеет права зависнуть).
- **Запрещено выводить значения секретов** (токены, ключи, initData целиком — в FAIL-причине максимум HTTP-код). app.env source'ить через `set -a; . /etc/solarsage/app.env; set +a`.
- Если файл/путь отсутствует (например запуск не на проде) — соответствующая проверка `FAIL <name> <чего нет>`, не падение скрипта с трассой.
- Без оверинжениринга: никаких конфигов, фреймворков, лог-файлов, ретраев, параллелизма. Один bash-файл, plain output.

## 5. Подводные камни

- `docker ps` требует root — скрипт и так запускается root'ом, но при запуске не-root: host-проверки с docker должны дать внятный FAIL, не крах.
- `release-record` — shell-формат `active=<sha>`; читать через `grep '^active=' | cut -d= -f2`, НЕ source'ить (там длинные строки).
- Имя дампа: метка UTC в имени — не путать с mtime; используй `-mtime` у файла.
- В `--quick` режиме проверки 10-11 пропускаются с выводом `SKIP auth/profile (quick mode)`.
- Не коммитить — коммит делает ревьюер.

## 6. Критерии приёмки

1. `bash -n scripts/deploy/prod-smoke.sh` — синтаксис чист.
2. Кодер прогоняет скрипт локально на dev (прода нет): host-проверки падают с ВНЯТНЫМИ причинами (нет docker-контейнеров solarsage-*), внешние (frontend, api-health, webhook-fail-closed против боевого домена) — проходят или дают осмысленный FAIL, сводка корректна, exit code != 0 (мы не на проде) — это ожидаемо. Показать вывод.
3. Никаких секретов в выводе.
4. `git status` — один новый файл.
