# ТЗ — smoke gate: контентная проверка V2-пейлоада дня

Дата: 2026-07-23
Ветка: `feat/smoke-v2-content` (создаёт ревьюер от main)
Исполнитель: кодер в tmux astro2. Коммитит ревьюер.

## Контекст

Инцидент: прод жил на V1, тесты — на V2 (флаги не были проброшены). Smoke gate (`scripts/deploy/prod-smoke.sh`) проверяет инфраструктуру и auth/profile, но не содержимое дня. Добавить контентную проверку: пейлоад дня реально V2.

## Правка (один файл — `scripts/deploy/prod-smoke.sh`)

Новая проверка `day-v2-content`, вызывается в main() после `check_auth_and_profile` (только полный режим; в `--quick` → SKIP).

Логика (переиспользовать подход check_auth_and_profile: initData генерация, cookie jar через mktemp, python3 для JSON):

1. Auth: как в check_auth_and_profile (initData из `/opt/solarsage-astro/scripts/generate-telegram-test-initdata.py`, строка `query_id=`/`user=`; POST /api/auth/telegram, cookie в jar).
2. Onboard (идемпотентно): `PUT /api/profile` с телом ровно:
   `{"firstName":"Smoke","gender":"female","birth":{"birthday":"1990-05-15","birthTime":"14:30","birthCity":"Москва","birthLat":55.7558,"birthLon":37.6173,"birthTz":"Europe/Moscow"}}`
   Ожидание: 200. Не 200 → FAIL с кодом.
3. `GET /api/day/$(date -u +%F)` с cookie, `--max-time 120` (генерация с LLM долгая). Не 200 → FAIL с кодом.
4. Контент: тело ответа содержит `"ss-scoring-2.0"` (grep -q) И `"v2"` как ключ верхнего уровня (проверка через python3: `json.loads(...)["v2"]` существует). Оба есть → PASS `day-v2-content`, иначе FAIL с указанием чего нет.

## Правила

- Те же, что в скрипте: `set -u`, функции check_*, без `set -e`, `--max-time` везде, никаких секретов в выводе, jar удалить.
- FAIL причиной пишем только HTTP-код/имя маркера.
- Сводка PASS/FAIL и exit codes — как есть, новая проверка просто добавляется в счётчик (итого станет 12).
