Current product path:

- `app/(grace)/profile/page.tsx`
- `components/profile/profile-screen.tsx`

- `hooks/use-access.ts`
- `lib/api/profile.ts`
- `lib/api/profile-meta.ts`
- `lib/api/access.ts`
- `lib/api/checkin.ts`
- backend endpoints:
  - `GET /api/profile`
  - `PUT /api/profile`
  - `GET /api/access`
  - `GET /api/horary/quota`
  - `GET /api/referral`
  - `GET /api/checkin/metrics`

Required data rules:

- `useProfile()` must keep loading `/api/profile` through `getProfile()`.
- Profile edits must keep saving through `updateProfile()`.
- Access state must come from `/api/access` via `useAccess()` and `getAccess()`.
- Horary/referral meta must come from `getProfileMeta()`, which currently composes `/api/horary/quota` and `/api/referral`.
- Check-in statistics must come from `/api/checkin/metrics`.
- The profile screen may display unavailable/empty states when real data is absent.
- The profile screen must not backfill absent profile/transit/lunar-node facts with static mock data.

## 4. Mock Preview Pieces And Decisions

The mock-preview profile contains useful presentation and non-product demo pieces. Treat them differently.

Port as presentation reference:

- profile header density, avatar sizing, typography, and section spacing;
- access/referral/horary card visual hierarchy;
- check-in statistics presentation if it remains backed by `/api/checkin/metrics`;
- profile data rows and edit sheet polish;
- service section composition if labels/actions remain production-safe.

Do not port into product runtime in Wave 03:

- `DevModeSwitcher`;
- `onChangeState` access switching in `ProfilePage`;
- onboarding reset controls from mock-preview profile page;
- mock-preview `TransitTimeline` as-is;
- mock-preview `LunarNodeWidget` as-is;
- `lib/lunar-nodes.ts` client calculation;
- hardcoded `NATAL_LONGITUDES`, `MEAN_MOTION`, `J2000_LONGITUDE`, or any static astrology calculations;
- `YookassaPaywall` / subscription payment API integration from mock-preview;
- root layout/theme-provider changes from mock-preview;
- `ThemeToggle` if it requires broad root layout/theme behavior changes.

If a visual block from mock-preview needs astrology data that current real contracts do not expose, hide/defer that block and mention the gap in the report. Do not fill it with mock or locally calculated data. A backend contract for real profile transit/natal-node facts belongs in a later backend/data wave unless the architect explicitly approves broadening this wave.

## 5. In Scope

### 5.1 Profile presentation

Bring `/profile` closer to the mock-preview visual language:

- compact top profile header with clear `Профиль` label, avatar, display name, and Telegram handle;
- access card matching the oracle's density and hierarchy while preserving real access state and current disabled subscription behavior;
- referral card using real `/api/referral` values;
- horary card using real `/api/horary/quota` values;
- check-in statistics card using real `/api/checkin/metrics` values;
- profile data section with stable rows and disabled/loading behavior before `/api/profile` hydration;
- service section with production-safe rows only;
- edit sheet remains functional and saves through the real profile API.

The text content does not need to match the mock screenshot exactly. Composition, density, spacing, hierarchy, interaction semantics, and mobile fit should match the oracle.

### 5.2 Profile meta cleanup

Make `lib/api/profile-meta.ts` and `app/(grace)/profile/page.tsx` avoid user-visible stale mock-ish defaults.

Required:

- initial/default referral reward days should be `14`, matching current backend `daysPerInvite`;
- when `/api/referral` returns `daysPerInvite`, map it into `ProfileMeta.referral.rewardDays`;
- `bonusDays` should be `totalInvited * rewardDays`, not hardcoded if the backend sends `daysPerInvite`;
- failures may still fall back to empty values, but fallback values must not look like demo data.

Do not create a new `/api/profile/meta` endpoint in this wave.

### 5.3 UI Semantic/Test Contract

Ensure stable selectors and accessibility states:

- `data-testid="profile-screen"` on the root;
- `data-state="loading|ready|error"` on the root, based on profile hydration:
  - `loading`: profile not loaded and no terminal error;
  - `ready`: profile loaded;
  - `error`: profile failed to load;
- `data-access-state="trial|subscription|expired|none"` on the root or access section;
- `data-testid="profile-header"`;
- `data-testid="profile-access-card"`;
- `data-testid="profile-referral-card"`;
- `data-testid="profile-horary-card"`;
- `data-testid="profile-checkin-statistics"` when metrics render;
- `data-testid="profile-data-section"`;
- `data-testid="profile-data-row-birth-date"`;
- `data-testid="profile-data-row-birth-time"`;
- `data-testid="profile-data-row-birth-place"`;
- `data-testid="profile-data-row-current-city"`;
- `data-testid="profile-data-row-birthday-city"`;
- `data-testid="profile-service-section"`;
- `data-testid="profile-edit-sheet"` on the edit sheet dialog container;
- `role="status"` for loading hints;
- `role="alert"` for terminal profile load/save errors;
- native `disabled` for rows/buttons that cannot be used yet;
- `aria-disabled` when a disabled-looking element is not a native disabled control;
- accessible names for icon-only buttons.

Tests must not depend on Tailwind class names.
