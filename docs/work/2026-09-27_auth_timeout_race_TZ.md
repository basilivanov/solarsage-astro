# ТЗ: Гонка таймаута авторизации (фронт 5с vs холодный auth 4.4с)

Дата: 2026-09-27. Статус: ТЗ записано, реализации не было. Порядок: сначала дев, проверка, затем прод через `prod-deploy`.

## 1. Инцидент и доказательства

- Жалоба: белый экран у `@ani96O` на проде; затем владелец сам получил «Ошибку авторизации» при заходе.
- Прод не лежал: 5/5 контейнеров healthy, API и фронт 200 локально и через nginx.
- По логам `solarsage-api` (время UTC, 2026-09-27):
  - `20:20:35` — `POST /api/auth/telegram → 200`, `auth.tg_login_succeeded`, но `duration_ms = 4452` (холодные коннекты к БД после простоя);
  - фронт `use-telegram-auth.ts:96–103` ставит таймер 5000 мс → `error: 'Authentication timeout'`, экран «Ошибка авторизации»;
  - `20:20:54.472` — `[TGAuth] Auth SUCCESS` (ответ успел прийти за ~300 мс до дедлайна), но в `20:20:54.785` таймер всё равно сработал: между приходом ответа и `clearTimeout` есть искусственный слип 500 мс (`use-telegram-auth.ts:219`), и коммит состояния опоздал;
  - повторная попытка прошла за 59 мс (пул прогрет) — итог SUCCESS, пользователь внутри.
- Вывод: эффективный бюджет фронта не 5 с, а ~4.5 с; холодный auth на проде занимает 4.4–4.7 с. Любой первый заход после простоя (а по промо-ссылке таких будет много) лотереит «ошибку авторизации» при фактически успешном бэкенде.
- Попутно: заход владельца был без `start_param` (`has_start_param: false`) — промо-окно в таком заходе не показывается по дизайну, это не баг.

## 2. Объём работ

### 2.1. Фронт (`hooks/use-telegram-auth.ts`)

1. Поднять `AUTH_TIMEOUT` с 5000 мс до 12000–15000 мс (вынести в именованную константу).
2. Гасить таймер (`clearTimeout`) сразу по приходу ответа fetch, ДО любых слипов и коммитов состояния — убрать гонку SUCCESS-then-TIMEOUT.
3. Отменять таймер при размонтировании / повторном `authenticate()` (защита от двойного срабатывания).
4. На экране ошибки (`app/(grace)/layout.tsx`, `data-testid="auth-error"`) добавить кнопку «Попробовать снова» (повторный `authenticate()` без перезагрузки Mini App).
5. Залогировать клиентскую длительность auth (время от `authenticate() started` до ответа) — сейчас её приходится выводить вычитанием.

### 2.2. Бэкенд (холодный auth 4.4 с)

1. Прогрев пула коннектов на старте API (min_size > 0 / warmup-запрос при startup), чтобы первый `POST /api/auth/telegram` после простоя не создавал коннекты с нуля.
2. Проверить auth-path на лишние тяжёлые запросы (что именно съело 4.4 с: коннект vs upsert vs профиль) и зафиксировать бюджет: тёплый p95 `POST /api/auth/telegram` < 1500 мс.
3. Без изменения контракта auth и без новых внешних зависимостей.

### 2.3. Наблюдаемость (чтобы следующий разбор занимал минуты, а не десятки минут)

Мотивация: инцидент 2026-09-27 разобран только ручной склейкой двух лент (фронт/бэкенд) с разными `correlation_id`. Закрыть три пробела:

1. В момент срабатывания таймаута писать в лог бюджет и факт: `timeout_budget_ms`, `elapsed_ms`, попытка по счёту. Значение 5000/12000 должно быть видно в строке `TIMEOUT`, а не только в коде.
2. Сквозной correlation ID: фронт генерирует `auth_attempt_id` на каждый `authenticate()` и передаёт в `POST /api/auth/telegram` (заголовок или поле), бэкенд прикладывает его к `auth.tg_login_succeeded` / ошибкам и к `system.request`. Тогда цепочка «попытка фронта → запрос бэкенда» грепается одним ID.
3. Бэкенд: в `auth.tg_login_succeeded` и в ошибках auth добавить разбивку задержки (`db_connect_ms`, `db_query_ms`) — чтобы сразу отличать «холодный пул» от «тяжёлый запрос». Без PII: только `is_new_user` / `has_start_param`, как сейчас.
4. Новое событие — в реестр (`lib/log/events.gen.ts`, `apps/api/app/core/logging_events.py`), затем в код; в `emitted_logs` контрактов — точные имена.

### 2.4. Пустое окно вместо экрана ошибки (инцидент 2026-09-27, вечер)

Симптом: Mini App висит пустым окном, без спиннера и без ошибки; прерывисто, сразу у нескольких людей; сервер при этом здоров (auth 200 за миллисекунды, рестартов 0).

Механика (подтверждена кодом, `app/(grace)/layout.tsx:99`): экран `auth-error` рендерится только при `error && inTelegram`. Если сеть пользователя медленная/рваная: SDK-провайдер ещё не `loaded` → `inTelegram=false`; TIMEOUT 5 с срабатывает → `error` установлен, но экран ошибки подавлен → рендерится «контент» без сессии → запросы 401 → экраны пустые. Итог: вместо честной ошибки с ретраем — вечное пустое окно. SSR-шелл (`grace-shell-loading` — пустой div) усиливает эффект при незавершённой гидратации.

Работы:
1. Рендерить `auth-error` при `error` независимо от `inTelegram`; текст различать: внутри Telegram — «ошибка входа, попробуйте снова», вне — «откройте через бот».
2. Кнопка «Попробовать снова» (уже п. 2.1.4) — обязательна именно для этого кейса.
3. Экраны данных при 401 без сессии показывают состояние `error`/`locked`, а не пустоту (проверить day/chat/profile/synastry).
4. Тест: заблокированный `telegram.org` + медленный auth → пользователь всегда видит ошибку с ретраем, пустого окна нет.

### 2.5. Натал по промо: состояние «оплачено, ждёт генерации» (инцидент 2026-09-28, Настя)

Симптом: пользователь выкупил промо (доступ + кредиты + `natal_full_report` delivered — всё в базе), открывает Разборы → Натальная карта и видит превью + закрытые главы + кнопку с ценой. Вывод пользователя: «натала нет, просят деньги».

Механика (подтверждена кодом): `NatalService.get_preview` (`apps/api/app/services/natal_service.py:476`) выставляет `full_report_available=true` только при READY-строке в `natal_reports` для текущего контекста. Право по промо-покупке превью не проверяет вообще. CTA страницы (`app/(grace)/readings/natal/page.tsx:102-107`): `hasReport → generating`, иначе → `startPurchase` (оплата). Владелец промо падает в ветку «купить»; дальше его спасает только 409 ALREADY_ENTITLED (`apps/api/app/api/payment.py:296`) → generating. Работает, но выглядит как «плати за своё».

Работы:
1. Бэкенд: в `NatalPreviewRead` добавить `full_report_entitled` — delivered/succeeded `natal_full_report`-покупка под ТЕКУЩИЙ хеш профиля есть, READY-отчёта ещё нет (переиспользовать `BillingService.has_natal_entitlement`). Контракт версионировать, owned-тесты превью обновить.
2. Фронт: при `entitled && !available` CTA — «Сгенерировать отчёт» (без цены), клик ведёт straight на `/readings/natal/generating`, минуя `startPurchase`.
3. Текст кнопки при `!entitled && purchasable` не трогать.
4. Тест: пользователь с promo-покупкой без READY-отчёта видит «Сгенерировать», генерация завершается READY; пользователь без покупки видит прежнюю цену.

## 3. Критерии приёмки

- [ ] Холодный `POST /api/auth/telegram` на деве укладывается в половину нового фронтального таймаута.
- [ ] Ответ, пришедший до дедлайна, никогда не превращается в `Authentication timeout` (гонка закрыта тестом).
- [ ] Экран ошибки имеет рабочую кнопку повтора.
- [ ] Нет «пустого окна»: при рваной сети и `inTelegram=false` пользователь видит ошибку с ретраем, а не пустоту.
- [ ] Строка `TIMEOUT` содержит `timeout_budget_ms` и `elapsed_ms`; попытка фронта находится в бэкенд-логах по одному `auth_attempt_id`; `auth.tg_login_succeeded` содержит разбивку `db_connect_ms` / `db_query_ms`.
- [ ] Владелец промо-натала без READY-отчёта видит «Сгенерировать отчёт» (без цены), генерация доводится до READY.
- [ ] `npx vitest run` + `pytest` без новых падений; контракт `data-testid="auth-error"` / `auth-loading` не переименован.
- [ ] Выкат в прод только через скилл `prod-deploy` (preflight + smoke), фронт и API одним релизом.
