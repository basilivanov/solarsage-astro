# TZ: Frontend Migration Wave 01 - `/day/[date]` real-data visual migration

Date: 2026-07-07
Status: ready for coder
Owner: architect
Recommended coder model: DeepSeek 4.2 Flash
Recommended reviewer model: GPT-5.5 xhigh
Branch: create a feature branch from current `main`

## 1. Goal

Migrate the `/day/[date]` screen in `main` to the visual language captured from the old mock-preview, while keeping the screen fully connected to real SolarSage/API data.

This is the first vertical slice of the broader frontend migration. It should prove the pattern before the same approach is applied to calendar, profile, readings, horary, and natal screens.

The target visual reference is the committed oracle package:

- `docs/superpowers/specs/2026-07-07-mock-preview-reference.md`
- `docs/superpowers/specs/assets/2026-07-07-mock-preview/day-2026-07-05.png`
- `docs/superpowers/specs/assets/2026-07-07-mock-preview/manifest.json`

## 2. Current architecture to preserve

Canonical runtime:

- Frontend: Next.js on port `3002`.
- API: FastAPI on port `8000`.
- Auth: Telegram WebApp HMAC via `/api/auth/telegram`.
- Development auth: `/api/auth/dev` only in development.
- SolarSage sidecar: internal calculation service on `18091`.

Current `/day/[date]` code path:

- `app/(grace)/day/[date]/page.tsx`
- `lib/grace/hooks/useDay.ts`
- `lib/adapters/today-payload.ts`
- `lib/contracts/today.ts`
- `components/today/today-screen.tsx`
- supporting `components/today/*`
- backend contract source: `apps/api/app/schemas/today.py`
- backend endpoint: `apps/api/app/api/day.py`
- backend service: `apps/api/app/services/today_service.py`

Keep the same real-data direction:

```text
Telegram/auth -> /api/day/:date -> TodayPayload -> adaptTodayPayload -> Today UI
```

The frontend must not calculate astrology. SolarSage/API calculate facts; frontend only adapts and renders.

## 3. In scope

### 3.1 Day screen presentation

Rework `/day/[date]` presentation so the mobile layout follows the mock-preview visual oracle:

- compact top date header with previous/next controls;
- large calm day card composition;
- access/trial/subscription card where real access state exists;
- day summary block similar to the oracle's "day overview" card;
- "concretely today" or equivalent practical list built from real `sphereScores`, `topFlags`, `notes`, `reading`, or other real TodayPayload fields;
- bottom navigation remains consistent with the app shell;
- loading, error, locked, and inaccessible states still work.

The text content does not need to match the mock screenshot. The composition, density, spacing, hierarchy, and interaction behavior should match the oracle. All facts and labels must come from real contracts or deterministic UI copy.

### 3.2 Adapter and contract alignment

Use `adaptTodayPayload` as the frontend boundary.

If the current `TodayPayload` lacks a field needed for a visual block:

1. First map from existing real fields if semantically correct.
2. If not possible, either hide that visual block or add a narrow backend contract field produced from real API/SolarSage data.
3. Do not invent mock/demo astrology to fill the gap.

Any backend contract extension must update:

- `apps/api/app/schemas/today.py`
- backend service construction in `apps/api/app/services/today_service.py`
- generated/shared frontend contract path currently used by the repo;
- relevant backend and frontend tests.

### 3.3 UI Semantic/Test Contract

The migrated screen must expose stable test semantics:

- `data-testid="today-screen"` on the screen root;
- `data-state="loading|ready|locked|error"` or equivalent stable state marker;
- stable `data-testid` for major sections:
  - day header;
  - access card;
  - day overview card;
  - practical list;
  - important events section if shown;
  - bottom navigation;
- `aria-expanded`, `aria-selected`, `aria-disabled`, or native disabled states for interactive controls;
- accessible roles/names for navigation buttons and expandable rows.

Avoid selectors based on styling classes or visual text alone in new tests.

### 3.4 Mock visual e2e for this route

Add a first real spec under:

```text
e2e/mock-visual/
```

Use only Playwright route interception from:

```text
e2e/mock-visual/route-interception.ts
```

Requirements:

- no MSW;
- no product runtime mock mode;
- no imports from `lib/mocks/*`, `lib/demo-data.ts`, or mock-preview source;
- fixtures must be contract-valid representations of the real API response shape;
- unmatched API requests in mock visual tests should fail fast.

The mock visual test should at minimum:

- navigate to `/day/2026-07-05`;
- install API fixtures before navigation;
- assert the screen reaches ready state;
- assert major semantic sections are visible;
- assert no obvious horizontal overflow on mobile viewport;
- create or update an intentional Playwright screenshot baseline only if the repository's current Playwright config supports it cleanly.

The old PNG oracle is a visual reference, not a pixel-perfect assertion target.

## 5. UX constraints

- The first mobile viewport must immediately communicate the selected day and its main state.
- Use the oracle for visual hierarchy, not for factual content.
- Cards may be used for actual grouped content, but do not nest cards inside cards.
- No decorative gradient/orb/bokeh backgrounds.
- No visible in-app text explaining implementation, tests, mocks, or how to use the app.
- Text must not overflow buttons/cards on mobile.
- Calendar oracle overflow is explicitly not a requirement to reproduce.
- If chart data is incomplete or visually unreliable, hide the chart for this wave instead of rendering fake chart data.

## 6. Implementation hints

Recommended order:

1. Read `AGENTS.md`, `docs/ADR-001_Headless_Testing.md`, `docs/visual-regression-testing.md`, and the mock-preview reference package.
2. Capture the current `/day/2026-07-05` state on the working branch for your own comparison.
3. Audit current `TodayPayload` and `adaptTodayPayload` fields.
4. Rework `components/today/today-screen.tsx` and small supporting `components/today/*` components.
5. Keep data adaptation in `lib/adapters/today-payload.ts`, not inside presentational components.
6. Add/adjust tests after the public DOM contract is stable.
7. Run gates and write the agent report.

Prefer small focused components if a section becomes hard to reason about. Do not introduce a broad design system refactor.

## 8. Acceptance criteria

Wave 01 is acceptable only if:

- `/day/2026-07-05` visually follows the committed mock-preview day oracle on mobile;
- the route uses real API data through the existing `TodayPayload` flow;
- no product path imports runtime mocks/demo data;
- no MSW or runtime mock mode is introduced;
- `adaptTodayPayload` remains the frontend adaptation boundary;
- loading, error, locked, and ready states remain handled;
- the screen exposes stable semantic/test selectors and ARIA/native state;
- mock visual e2e for `/day/2026-07-05` exists and passes;
- TypeScript passes;
- unit tests pass;
- backend tests pass if backend was touched;
- no systemd/nginx/bot/port changes are included;
- `main` can remain green after merge.
