## Architecture

### 1. New return calculation service

Create:

```text
apps/solarsage/solarsage/services/returns.py
```

This module owns:

- natal Sun/Moon longitude lookup;
- exact solar return search;
- most recent lunar return search;
- return chart construction at exact return JD;
- return timestamp conversion;
- return location context;
- pure return calculation result models/data structures.

Follow the repository GRACE comment contract:

- module header;
- module contract;
- module map;
- function contracts for non-trivial functions;
- no `grace_control` import.

Keep astronomical calculation in the sidecar. Do not put return math in API or frontend.

### 2. Exact return search

#### Solar return

For target year:

- find the exact UT moment when transit Sun longitude equals natal Sun longitude;
- use a deterministic bracket + root refinement or an equivalent Swiss Ephemeris method;
- handle longitude wrap-around correctly;
- search around the birthday, but fail clearly if a valid bracket cannot be found;
- target precision: longitude residual `<= 0.001°`;
- store exact `return_jd` and UTC ISO timestamp.

For Basil:

```text
birth: 1980-10-30 19:50 Europe/Moscow
target year: 2026
historical fixture solar_return_2026.return_jd:
2461344.3452186584
```

Use a documented tolerance when comparing with the historical fixture. Do not hardcode the fixture result in production code.

#### Lunar return

For target datetime:

- find the most recent UT moment at or before target JD when transit Moon longitude equals natal Moon longitude;
- search backwards far enough to cover a full synodic/sidereal return window;
- choose the latest valid crossing, not an arbitrary crossing;
- handle longitude wrap-around correctly;
- target precision: longitude residual `<= 0.001°`;
- require `return_jd <= target_jd`;
- require `target_jd - return_jd < 30 days`;
- store exact `return_jd` and UTC ISO timestamp.

The calculation must be deterministic across `PYTHONHASHSEED`.

### 3. Return chart

At the exact return JD calculate:

- all supported planets;
- return houses;
- return ASC and MC;
- each return planet's return-chart house;
- return angle longitude;
- mapping of return ASC/MC into natal houses.

Use the requested house system where supported. Preserve the existing high-latitude resolution behavior and expose the resolved house system in debug.

Do not silently use a different house system.

### 4. Location policy

Canonical policy:

```text
current_location_if_known_else_birth_location
```

Extend the sidecar request backward-compatibly with an optional current/return location object if needed:

```text
current_location:
  lat: float
  lon: float
  tz: str | null
```

Behavior:

- if current location is supplied, build SR/LR houses at current location;
- otherwise use birth latitude/longitude;
- never silently fall back.

Every return activation debug payload must include:

```text
return_location_policy: current_location_if_known_else_birth_location
return_location_source: current_location | birth_location
return_location_reason: explicit_current_location | current_location_missing
return_lat
return_lon
return_tz
```

When birth location is used because current location is absent, add one deterministic layer warning:

```text
return_location_fallback:birth_location:current_location_missing
```

Do not duplicate the same warning for every activation.

### Solar return activations

Required minimum:

1. SR ASC mapped to natal house.
2. SR MC mapped to natal house.
3. SR chart ruler planet.
4. SR Moon return-chart house.
5. Every SR planet in an angular return house: 1, 4, 7, 10.

Stable IDs:

```text
solar_return__ANGLE_ASC__NATAL_HOUSE_<N>
solar_return__ANGLE_MC__NATAL_HOUSE_<N>
solar_return__CHART_RULER__<PLANET>
solar_return__MOON_HOUSE__<N>
solar_return__ANGULAR_PLANET__<PLANET>__HOUSE_<N>
```

Kinds:

```text
return_angle_in_natal_house
return_chart_ruler
return_moon_house
return_angular_planet
```

Frames:

- SR ASC/MC in natal house: `source_frame=solar_return`, `target_frame=natal`;
- SR Moon/angular planets in return houses: `source_frame=solar_return`, `target_frame=solar_return`;
- chart ruler planet: `source_frame=solar_return`, `target_frame=natal`.

Indexes:

- house targets go to `by_house`;
- chart ruler goes to `by_planet`;
- do not place IDs in an unrelated index.

### Lunar return activations

Required minimum:

1. LR Moon return-chart house.
2. LR ASC mapped to natal house.
3. LR MC mapped to natal house.
4. Every LR planet in an angular return house: 1, 4, 7, 10.

Stable IDs:

```text
lunar_return__MOON_HOUSE__<N>
lunar_return__ANGLE_ASC__NATAL_HOUSE_<N>
lunar_return__ANGLE_MC__NATAL_HOUSE_<N>
lunar_return__ANGULAR_PLANET__<PLANET>__HOUSE_<N>
```

Kinds:

```text
return_moon_house
return_angle_in_natal_house
return_angular_planet
```

Frames:

- LR ASC/MC in natal house: `source_frame=lunar_return`, `target_frame=natal`;
- LR Moon/angular planets in return houses: `source_frame=lunar_return`, `target_frame=lunar_return`.

### Evidence strings

Evidence must be explicit and frame-aware. Examples:

```text
Solar Return ASC falls in natal house 3
Solar Return MC falls in natal house 12
Mars is Solar Return chart ruler
Solar Return Moon is in Solar Return house 10
Solar Return Jupiter is angular in Solar Return house 1
Lunar Return Moon is in Lunar Return house 7
Lunar Return ASC falls in natal house 4
Lunar Return Saturn is angular in Lunar Return house 10
```

Do not use ambiguous text such as:

```text
Moon in house 7
ASC in house 4
```
