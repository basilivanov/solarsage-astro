# ТЗ — Election v2: личный транзитный фактор в ранжировании дат

Дата: 2026-07-24
Ветка: `feat/election-personal` (создаёт ревьюер от main)
Исполнитель: кодер в tmux astro2. Коммитит ревьюер.

## Контекст

Сейчас election ранжирует даты только по универсальному небу (Луна/VOC/ретро). По классике элективной нужен и личный слой: транзиты дня к наталу юзера. Инфраструктура есть: `CalendarService` уже считает per-day статус (supportive/steady/tense) для юзера через транзиты к натальному контексту (`apps/api/app/services/calendar_service.py`, `_compute_and_cache_day_status`, см. также `scoring_service.py` и `day_scoring_runtime_service.py`). `election_service.run_search_task` уже получает натальный контекст юзера (`get_or_build_natal_context`, есть в main).

## 1. Engine: personal_status per day

`apps/api/app/services/election_engine.py`:

- Новая опция в `scan(...)`: `personal_days: dict[str, str] | None` — маппинг date_str → status ("supportive"|"steady"|"tense") на КАЖДЫЙ день окна.
- Бонус к score (в канон `grace/canon/election_rules.v1.yml` секция `scoring`):
  ```yaml
  personal:
    supportive: +15
    steady: 0
    tense: -20
  ```
- В день-дикт добавить `personal_status` (или null) и reason-строку при nonzero: supportive → «По твоим транзитам день поддерживает», tense → «По твоим транзитам день тяжёлый».
- `facts.days` и `best_days`/`avoid_days` несут `personal_status`.

## 2. Service: вычисление personal_days

`apps/api/app/services/election_service.py` в `run_search_task`:

- После получения натального контекста: для каждой даты окна вычислить статус дня через ТОТ ЖЕ механизм, что и календарь (найди как `CalendarService` получает per-day status; переиспользуй его метод/сервис, не дублируй логику; таймзона — из профиля, fallback Europe/Moscow).
- Ограничение производительности: вычислять только если юзер онбордед и есть натальный контекст; иначе personal_days=None (engine работает как раньше).
- Ошибка вычисления одного дня → этот день без personal_status (не валить весь поиск); ошибка всякого — log warn и personal_days=None.

## 3. Narrative

`apps/api/app/services/llm/election.py` промпт: в фактах hero-дня передавать `personal_status`; правило: для supportive — одно предложение «по твоим личным транзитам день поддерживает» в hero_personal (естественно вплести, не отдельным полем); для tense — hero_personal должен мягко сказать про личную тяжесть дня. Схему narrative НЕ менять.

## 4. Frontend

`election-result-view.tsx`: в hero-дне под строкой Луны — строка про личные транзиты (иконка 👤): supportive → «По твоим транзитам — поддерживает», tense → «По твоим транзитам — тяжёлый день», steady/null → ничего. В карточках best_days — та же строка маленьким текстом при supportive/tense. В календаре НЕ менять.

## 5. Канон-тексты reason'ов

Reason-строки про personal — из канона (`personal_reasons: {supportive: "...", tense: "..."}` в election_rules.v1.yml), не хардкод в engine.

## 6. Тесты

- `test_election_engine.py`: scan с personal_days — supportive/tense влияют на score и reasons, null не ломает.
- `test_election_service.py`: run_search_task вызывает personal-вычисление (мок), personal_status попадает в payload; падение personal-вычисления → поиск завершается done без personal.
- vitest для result-view: строка транзитов при supportive/tense, отсутствует при steady.
