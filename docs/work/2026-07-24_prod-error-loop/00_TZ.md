# Prod Error Loop — мастер-план реализации

Дата: 2026-07-24
Статус: approved к реализации; нарезка на coder-срезы ниже
Владелец контура: архитектор (Kimi), кодер — opencode/Gemini по coder-loop

## 1. Цель

Замкнуть контур наблюдаемости прода:

```
ошибки у пользователей в проде
  → агрегация и хранение (Bugsink, self-hosted)
  → авто-триаж в GitHub Issues (cron на dev-хосте)
  → авто-фикс через coder-loop (opencode headless) с PR'ами
  → ручной батч-мерж и деплой через prod-orchestrator
  → resolve в Bugsink после деплоя
```

Принятые решения (с пользователем, 2026-07-24):

- Хранилище ошибок: **Bugsink self-hosted** (один контейнер, SQLite). Не GlitchTip (тяжелее), не Sentry SaaS (данные у третьей стороны, автофикс платный), не своя таблица в Postgres (велосипед: группировка/дедуп/регрессии из коробки только в трекере).
- Автономия: **сразу этап 2** — агент сам чинит и открывает PR; человек мержит батчем и деплоит вручную. Merge и deploy НЕ автоматизируем.
- GitHub private repo — не ограничение (проверено: issues enabled, `gh` scope `repo`+`workflow`; Actions-минуты не нужны, cron на dev-хосте).

## 2. Исходное состояние (проверено по коду)

Уже есть (main, в проде появится с ближайшим деплоем):

- Сбор ошибок фронта: `components/telemetry/frontend-error-capture.tsx` (window.onerror/unhandledrejection), `app/error.tsx`, `app/global-error.tsx` (react-boundary), `lib/log/instrumented-fetch.ts` (api_request_failed / api_response_invalid).
- Нормализация: `lib/log/capture-error.ts` — envelope несёт `error.{kind,code,source,fingerprint,stack_frames[{file,function,line,column}]}`, `payload.route`, `http.{method,route_template,status}`, `duration_ms`, `level`. PII-редкация и дедуп уже на фронте.
- Транспорт: `lib/log/shipper.ts` → `POST /api/_log` → `apps/api/app/api/_log.py` → `apps/api/app/services/log_intake.py` → stdout (JSON line). Kill-switch `NEXT_PUBLIC_GRACE_LOG_SHIPPING=true` уже в prod-сборке фронта.

Чего нет (ради чего и строится этот план):

- Хранения и агрегации: `log_intake.py` только переливает в stdout (Decision A, `grace/packets/W-1.7.md`; «external sinks → PHASE-6+»). Retention — docker json-file 10m×3.
- `sentry-sdk` в `apps/api/pyproject.toml` отсутствует.
- На dev-хосте: `opencode` 1.18.3 (headless `opencode run -m provider/model "task"` поддерживается), `gh` 2.78 (авторизован), tmux. Репо `github.com:basilivanov/solarsage-astro` (PRIVATE).
- Prod app compose (`infra/production/docker-compose.app.yml`) имеет invariant «только immutable per-SHA digest-образы» → Bugsink туда НЕ добавляем, живёт отдельным compose-проектом.
- App network `solarsage-app_app`, subnet pinned `172.31.235.0/24`.

## 3. Целевая архитектура

```
браузер → /api/_log → log_intake.py ──→ stdout (как сейчас, не трогаем)
                           └─ level∈{error,fatal} ∧ event^="frontend."
                              → app/services/error_tracking.py → sentry-sdk → Bugsink
FastAPI 5xx/exception → sentry-sdk FastAPIIntegration ──────────────→ Bugsink
                          (dsn из ERROR_TRACKING_DSN в /etc/solarsage/app.env; пусто = выключено)

Bugsink (compose-проект solarsage-bugsink на прод-хосте):
  SQLite volume, 127.0.0.1:18095 (UI по SSH-туннелю),
  external network solarsage-app_app (alias bugsink) → API ходит на http://bugsink:8000
        │ REST API /api/canonical/0/ (token auth)
cron на dev-хосте → scripts/prod-errors/triage.py:
  топ unresolved → дедуп против GitHub issues (label prod-error, маркер bugsink-issue:<id>)
  → создать issue (стек, route, count, first/last seen, release)
  → top N → fix_runner.py <issue>:
      git worktree от origin/main → ТЗ docs/work/... → opencode run (headless)
      → targeted checks → commit/push → gh pr create (label prod-fix, "Fixes #N")
      → провал → gh issue comment с логом, PR нет
  → дайджест прогона в stdout (опционально Telegram)
человек: ревью+мерж батча PR → prod-orchestrator deploy <sha> --manual-confirm
  → scripts/prod-errors/resolve_after_deploy.py <sha> → resolved в Bugsink
```

State всей системы — stateless-derivable: Bugsink = правда об ошибках, GitHub = правда о работе (маркеры `bugsink-issue:<id>` в issues/PR). Отдельной БД для runner'а не нужно.

## 4. Срезы реализации

Каждый срез — отдельная coder-итерация по coder-loop (свой ТЗ-файл `NN_..._TZ.md` рядом с этим документом, создаётся при выдаче кодеру).

### Slice 1 — Bugsink на проде (инфра)

Файлы:

- `infra/production/docker-compose.bugsink.yml` (новый), проект `solarsage-bugsink`:
  - `image: bugsink/bugsink:<pinned>` — запинить конкретную версию, не latest
  - `container_name: solarsage-bugsink`, `restart: unless-stopped`
  - env: `SECRET_KEY=${BUGSINK_SECRET_KEY:?}`, `CREATE_SUPERUSER=${BUGSINK_SUPERUSER:?}` (только первый старт), `PORT=8000`, `ALLOWED_HOSTS=127.0.0.1,localhost,bugsink`
  - `volumes: bugsink-data:/data` (SQLite в /data по умолчанию)
  - `ports: 127.0.0.1:18095:8000` (UI только через SSH-туннель, наружу не светим)
  - `networks`: external `solarsage-app_app` с alias `bugsink`
  - logging json-file 10m×3, `security_opt: no-new-privileges:true`
- `infra/systemd/solarsage-bugsink.service` (новый, по образцу `solarsage-db.service`): compose up -d для проекта
- `AGENTS.md`: порт 18095 в таблицу prod-сервисов; Bugsink в «Что где лежит на проде»
- `docs/PRODUCTION_RUNBOOK.md`: раздел «Error tracking (Bugsink)» — установка, туннель
  `ssh -L 18095:127.0.0.1:18095 root@2.26.20.80 -i ~/.ssh/solarsage_prod_server_ed25519`,
  создание проекта/DSN/API-токена

Ручные шаги оператора (владелец, документируем в runbook):

1. Скопировать compose + unit на прод, `systemctl enable --now solarsage-bugsink`
2. UI по туннелю → создать проект `solarsage` → получить DSN `http://<key>@bugsink:8000/<project_id>`
3. Создать API token для триажа (Settings → API tokens)
4. В `/etc/solarsage/app.env` добавить `ERROR_TRACKING_DSN=http://<key>@bugsink:8000/<project_id>`

Приёмка: `curl -s http://127.0.0.1:18095/` на проде → login page; из контейнера api доступен `http://bugsink:8000/`.

### Slice 2 — Backend: форвардинг error/fatal в Bugsink

Файлы:

- `apps/api/pyproject.toml`: + `sentry-sdk[fastapi]` (2.x)
- `apps/api/app/services/error_tracking.py` (новый, GRACE-разметка обязательна):
  - `init_error_tracking(dsn: str, release: str)` — `sentry_sdk.init(dsn, release=release, integrations=[FastApiIntegration()], send_default_pii=False)`; пустой DSN → no-op
  - `capture_frontend_envelope(envelope: dict)` — маппинг:
    - `message = f"{event}: {error.kind}"`, `fingerprint = [error.fingerprint]`
    - `exception.values[0]` с `type=error.kind`, stacktrace из `error.stack_frames` (filename/function/lineno/colno)
    - tags: `event`, `error.source`, `route` (payload.route), `module`, `slice`; extras: `http`, `duration_ms`, `correlation_id`
    - весь вызов в try/except, fire-and-forget; ошибка форвардинга НЕ влияет на intake
  - фильтр: только `level ∈ {error, fatal}` и `event` начинается с `frontend.`
- `apps/api/app/services/log_intake.py`: после `_emit_line(redacted)` — если фильтр прошёл, `capture_frontend_envelope(redacted)`; обновить module contract (новый side_effect + dependency M-ERROR-TRACKING)
- `apps/api/app/main.py`: `init_error_tracking(os.environ.get("ERROR_TRACKING_DSN", ""), os.environ.get("RELEASE_SHA", ""))` при старте
- `infra/production/docker-compose.app.yml`: в `api-env` строка `ERROR_TRACKING_DSN: ${ERROR_TRACKING_DSN:-}` (fail-open, preflight не ломается)
- `apps/api/tests/services/test_error_tracking.py` (новый): маппинг envelope→event (frames, fingerprint, tags), фильтр по level и prefix, no-op без DSN, исключение внутри форвардера не пробрасывается

Приёмка: `cd apps/api && source .venv/bin/activate && python -m pytest tests/ -q` зелёный; после деплоя тестовая фронт-ошибка видна в Bugsink с группировкой/release/стеком; backend 5xx тоже виден.

### Slice 3 — Триаж + авто-фикс runner (dev-хост)

Новая директория `scripts/prod-errors/`:

- `bugsink_client.py` — REST `/api/canonical/0/`, token auth: `list_unresolved(sort=count, min_events)`, `get_issue(id)`, `resolve(id)`
- `triage.py`:
  1. топ unresolved (лимит 10, порог ≥3 события)
  2. дедуп: `gh issue list --label prod-error --state all --search "bugsink-issue:<id>"` → пропуск
  3. `gh issue create --label prod-error`: title `<kind> at <top frame file:function> (<route>)`; тело: fingerprint, frames, route, count, first/last seen, release, ссылка на Bugsink issue, маркер `bugsink-issue:<id>`
  4. топ-N новых (MAX_FIXES_PER_RUN, default 3) → `fix_runner.py <issue_number>`
  5. дайджест в stdout; опционально Telegram (существующий TELEGRAM_BOT_TOKEN, chat id владельца из env)
- `fix_runner.py`:
  1. `git fetch origin && git worktree add .worktrees/prod-error-<id> -b fix/prod-error-<id> origin/main`
  2. ТЗ `docs/work/YYYY-MM-DD_prod-error-<id>_TZ.md` внутри worktree по шаблону coder-loop: цель, контекст (стек/route/count), разрешённые файлы (выведены из stack frames), запрет коммита
  3. `opencode run -m $PROD_ERRORS_MODEL "$(cat ТЗ)"` в worktree, таймаут 20 мин
  4. checks: `*.ts/tsx` → `npx tsc --noEmit` + targeted vitest; `apps/api/**` → targeted pytest
  5. зелёно → commit `fix(frontend|api): <kind> at <frame> (prod-error #N)` → push → `gh pr create --label prod-fix --body "Fixes #N\n\n<контекст>"`
  6. красно → `gh issue comment #N` с логом проверки → worktree cleanup
  7. предохранители: не трогать `apps/api/app/**/billing*`, `**/auth*` (список в конфиге runner'а — такие issue только триажатся, фикс вручную)
- `opencode.prod-errors.json` — permission-профиль headless: edit allow; bash allow whitelist (`npx`, `npm`, `pytest`, `git status`, `git diff`); deny `git push`/`git commit` (git делает скрипт)
- `resolve_after_deploy.py <sha>` — merged PR с label `prod-fix`, вошедшие в `<sha>` → `bugsink.resolve(id)`; issues закрываются сами через «Fixes #N»
- `run.sh` — `flock` + вызов triage.py; cron-строка (ставит владелец): `17 */4 * * * /opt/solarsage-astro/scripts/prod-errors/run.sh >> /var/log/prod-errors.log 2>&1`
- `.env.example` (реальный `.env` в .gitignore): `BUGSINK_URL=http://127.0.0.1:18095` (SSH-туннель с dev-хоста на прод), `BUGSINK_TOKEN`, `GH_REPO=basilivanov/solarsage-astro`, `PROD_ERRORS_MODEL`, `MAX_FIXES_PER_RUN=3`, `TELEGRAM_DIGEST_CHAT_ID` (опц.)

Приёмка: `triage.py --dry-run` печатает план без side effects; живой прогон с `MAX_FIXES_PER_RUN=1` на первой реальной ошибке: issue создан, повторный прогон дубль не создаёт, PR открыт или честный comment о провале.

## 5. Что НЕ делаем (явно)

- Sentry SDK на фронт — envelope уже санитизирован, второй транспорт не нужен
- Своя таблица/дашборд в Postgres — это и есть велосипед, отдаём Bugsink
- Изменения stdout-пути логов — остаётся как есть
- Bugsink внутрь `docker-compose.app.yml` — нарушит invariant immutable images
- Авто-мерж PR и авто-деплой — ручной гейт остаётся
- Loki/Grafana для общих (не-error) логов — вне цели этого контура

## 6. Порядок выполнения

1. Slice 1 — независим, можно сразу (часть шагов ручные на проде)
2. Slice 2 — PR в main, поедет ближайшим деплоем (вместе с уже запушенным log shipping)
3. Slice 3 — PR в main; осмыслен после Slice 1+2 в проде
4. Slice 4 — в том же PR, что Slice 3

## 7. Критерии приёмки контура целиком

1. Тестовая ошибка фронта в проде видна в Bugsink: группировка, стек, route, release
2. Backend 5xx виден в Bugsink
3. `triage.py` создаёт GitHub issue; повторный прогон не плодит дубли
4. `fix_runner.py` на реальном issue открывает PR с зелёными проверками; на нефиксабельном — честный comment, PR нет
5. После `prod-orchestrator deploy <sha>` + `resolve_after_deploy.py <sha>` issue в Bugsink resolved
6. `pytest` API и `npx vitest run` зелёные
