## Non-Negotiable Architecture

- Production must use backend `/api/calendar` contract. No runtime mocks, no static astrology, no `lib/mocks/*`, no client date-based lunar calculations.
- Frontend can map backend `lunar.phaseIndex/phaseLabel/illumination/lunarDay` to presentation glyphs and text.
- Frontend can map backend `dayStatus/access` to display markers, but must not invent access or status.
- If a visual difference is caused by real access state for `basil_ivanov`, classify it as a data difference. Do not fake full access.
- If a visual difference is purely styling/presentation, fix it.

## Expected Fix Focus

Based on architect review, likely fix areas are:

### Day-mode secondary markers

3002 currently shows status-style markers such as sparkles/dashes under day numbers. The oracle day-mode uses a quieter lunar/access marker language. Verify from oracle screenshots and, if available, the `3001` mock-preview source.

Fix the presentation so day-mode cells match oracle styling while still deriving values from backend fields:

- accessible/full days should not invent decorative status icons if oracle shows lunar phase markers;
- locked days should retain lock treatment with oracle-like size/opacity/position;
- selected day should preserve the oracle purple circle and any selected-state secondary glyph.

### Moon-mode phase glyph palette

3002 phase glyphs are structurally close but visually colder/flatter than 3001. Match:

- warm/dark moon fill colors;
- size;
- stroke width;
- selected ring spacing;
- disabled/out-of-access opacity;
- current-day orange marker placement.

### Footer and viewport fit

The footer must remain visible above bottom nav in both day and moon modes. Do not hide content under the tab bar.
