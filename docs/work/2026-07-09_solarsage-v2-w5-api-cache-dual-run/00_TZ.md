## Required Architecture

### 1. Feature flags

Add settings in `apps/api/app/core/config.py`:

```python
solarsage_v2_enabled: bool = Field(False, alias="SOLARSAGE_V2_ENABLED")
solarsage_v2_dual_run: bool = Field(True, alias="SOLARSAGE_V2_DUAL_RUN")
solarsage_v2_frontend_enabled: bool = Field(False, alias="SOLARSAGE_V2_FRONTEND_ENABLED")
solarsage_audit_artifacts_enabled: bool = Field(False, alias="SOLARSAGE_AUDIT_ARTIFACTS_ENABLED")
```

Test defaults must force these to safe values in `apps/api/tests/conftest.py` so env leakage cannot silently enable V2.

Behavior:

| Condition | Required behavior |
|---|---|
| `V2_ENABLED=false`, `V2_DUAL_RUN=false` | compute V1 only, return V1 |
| `V2_ENABLED=false`, `V2_DUAL_RUN=true` | compute V1 and V2, log diff, return V1 |
| `V2_ENABLED=true` | compute V2 and return V2-selected legacy payload values |
| `V2_FRONTEND_ENABLED=false` | do not expose new W6/V2 frontend-only fields |
| `V2_FRONTEND_ENABLED=true` | flag exists but W6 owns actual frontend V2 fields; do not invent them in W5 |

Dual-run must be fail-open only when `V2_ENABLED=false`: if V2 computation fails during shadow scoring, log/record the failure and return V1. If `V2_ENABLED=true`, V2 failures must fail loudly.

### 2. Shared runtime scorer

Add a shared backend helper/service so `TodayService` and `CalendarService` cannot diverge.

Preferred file:

```text
apps/api/app/services/day_scoring_runtime_service.py
```

Required responsibilities:

- accept `day_signals`, `activation_layer`, `user_id`, `target_date`;
- always compute V1 when selected output can be V1;
- compute V2 when `solarsage_v2_dual_run` or `solarsage_v2_enabled`;
- return a small typed/dataclass result containing:
  - `selected_result`: legacy V1-shaped dict for existing services:
    - `day_status`
    - `sphere_scores`
    - `top_signals`
  - `selected_scoring_version`: `1` for V1 or `"ss-scoring-2.0"` for V2;
  - `v1_result`;
  - optional `v2_result`;
  - optional `diff`;
  - optional V2 error metadata for shadow failures.
- convert `ScoringV2Result` into the existing legacy scorer shape when V2 is selected:
  - `day_status = v2.day_status`
  - `sphere_scores = {key: score.final_score for key, score in v2.sphere_scores.items()}`
  - `top_signals = v2.top_signals`

Do not duplicate this selection logic in `TodayService` and `CalendarService`.

### 4. Cache key and invalidation

The current cache key `(user_id, target_date, profile_hash)` is not enough for V2 rollout. Implement a versioned cache key, not just a loose `content_version` check.

Add a helper, preferably in the same runtime/cache module:

```python
build_today_cache_key(
    *,
    user_id,
    target_date,
    profile_hash,
    calculation_version,
    activation_layer_version,
    scoring_version,
    canon_versions,
    llm_prompt_version,
    frontend_payload_version,
) -> TodayCacheKey
```

Required deterministic fields:

- `user_id`
- `target_date`
- `profile_hash`
- `calculation_version`
- `activation_layer_version`
- `scoring_version`
- `canon_versions_hash` from `json.dumps(get_canon_versions(), sort_keys=True)`
- `llm_prompt_version`
- `frontend_payload_version`

Required DB change:

- Add an Alembic migration after `0018`.
- Add inspectable cache key columns to `TodayPayloadCache`:
  - `cache_key_hash`
  - `calculation_version`
  - `activation_layer_version`
  - `scoring_version`
  - `canon_versions_hash`
  - `llm_prompt_version`
  - `frontend_payload_version`
- Replace the old unique constraint with a unique constraint that includes `cache_key_hash`.
- Keep downgrade working.
- Use `op.batch_alter_table(...)` where needed so SQLite round-trip remains green.

Recommended unique shape:

```text
(user_id, target_date, profile_hash, cache_key_hash)
```

Do not rely only on JSON meta validation once these columns exist.

Semantic cache:

- Do not add a table migration unless necessary.
- Store the same version/cache metadata inside `SemanticLayerCache.semantic_json`.
- Calendar must only trust semantic cache when profile hash and all version/cache fields match.
- Stale semantic cache must not win over a new scoring/canon/prompt/frontend version.

Bump `TODAY_CONTENT_VERSION` from `8` to `9` after implementing W5 cache semantics.

```text

```

Required coverage:

1. Defaults:
   - `SOLARSAGE_V2_ENABLED=false`
   - `SOLARSAGE_V2_DUAL_RUN=true`
   - V2 is computed
   - selected payload/scoring result remains V1
   - `meta.scoring_version == 1`
   - diff is built/logged

2. V1-only mode:
   - `SOLARSAGE_V2_ENABLED=false`
   - `SOLARSAGE_V2_DUAL_RUN=false`
   - V2 scorer is not called
   - selected result is V1

3. V2-enabled mode:
   - `SOLARSAGE_V2_ENABLED=true`
   - selected result uses V2 day status and V2 final sphere scores
   - `meta.scoring_version == "ss-scoring-2.0"`

4. Shadow failure:
   - V2 scorer raises while `V2_ENABLED=false`
   - service returns V1
   - failure is visible in result/log metadata

5. Enabled failure:
   - V2 scorer raises while `V2_ENABLED=true`
   - service fails loudly

6. Cache key:
   - same user/date/profile but different selected scoring version produces different `cache_key_hash`;
   - changing canon versions hash misses cache;
   - changing prompt/frontend/content version misses cache;
   - old rows without matching key are ignored;
   - stale semantic cache does not supply calendar status after version mismatch.

7. Calendar parity:
   - default dual-run calendar selected status matches V1 `/day` semantics;
   - V2-enabled calendar selected status can change to V2 status through the shared runtime helper.

8. Logging registry:
   - `scoring.v2_diff` is accepted by `log_event`;
   - guardrail/canon test passes.

9. Migration:
   - Alembic round-trip passes.

Update existing assertions that expect `TODAY_CONTENT_VERSION == 8` or old cache uniqueness.
